Canonical Definition

The Artifact Version Integrity Module (AVIM) governs the identification,

version attribution, content correspondence, integrity verification,
evidence preservation, and lifecycle continuity of software artifacts
and their version relationships.

AVIM establishes the methodological conditions under which a software

artifact can be recognized as an identifiable, version-associated,
evidence-supported object whose claimed identity and version remain
distinguishable from its actual content, recorded provenance, and
observed integrity state.

It governs the relationships among artifact identity, artifact content,

version identifiers, build references, configuration baselines,
artifact transformations, repository records, integrity evidence, and
subsequent artifact states.

AVIM distinguishes artifact naming from artifact identity, version labeling

from verified version correspondence, content integrity from software
correctness, and an artifact's recorded origin from independently
supported provenance.

It applies to software artifacts created, transformed, stored, copied,

packaged, or referenced by humans, organizations, automated pipelines,
AI coding assistants, autonomous development agents, and software
infrastructure systems.

Its principal output is:

Governed Artifact Version Integrity State

Its foundational distinction is:

Declared Artifact Version ≠ Verified Artifact Version Integrity.

Operational Role

The operational role of AVIM is:

To ensure that material software artifacts remain identifiable,
correctly associated with their claimed versions, supported by
competent integrity and correspondence evidence, and traceable through
relevant transformations and lifecycle transitions without confusing
artifact integrity with software correctness, security, or release
authorization.

AVIM provides the artifact-version integrity governance mechanism of
SCFS.

It establishes whether an artifact's identity, content, version reference,

and material lifecycle relationships can be sufficiently supported.

AVIM does not independently authorize software creation, execute
builds, approve configuration changes, validate software quality,
certify security, or authorize release and deployment.

It provides an evidence-supported artifact-version integrity state for

competent downstream SCFS and SLGA™ governance.

Operational Question

How can a software artifact's identity, claimed version, actual
content, build relationship, and lifecycle continuity remain
sufficiently established and verifiable so that a version label or
repository record is not mistaken for proof of artifact integrity?

Software Artifact Governance Object

Every material AVIM assessment shall establish a Software Artifact

Governance Object.

The object represents an identifiable software artifact and the governance

conditions under which its version integrity may be assessed.

It should identify:

Artifact Identity: The software artifact being assessed.

Artifact Purpose: The artifact's intended function.

Artifact Type: The recognized artifact form.

Artifact Scope: The boundaries of the assessed artifact.

Artifact Classification: The artifact's intended lifecycle role.

Content Identity: The identifiable artifact content.

Version Identity: The claimed or established version.

Build Reference: The relevant build relationship.

Baseline Reference: The applicable configuration baseline
relationship.

Provenance Reference: The recorded artifact origin and transformation

history.

Integrity Evidence: Evidence supporting artifact integrity.

Verification State: The condition of integrity assessment.

Lifecycle References: Relevant artifact transitions.

Governance State: The recognized artifact-version integrity condition.

The governance object shall remain distinguishable from a filename, version

label, repository entry, or checksum.

Artifact Governance Object ≠ Artifact Filename.

Artifact Purpose Governance

AVIM shall identify the purpose for which the artifact exists.

Purposes may include:

  • Development
  • Testing
  • Integration
  • Distribution
  • Release preparation
  • Deployment
  • Maintenance
  • Recovery
  • Historical preservation

Artifact purpose shall remain distinguishable from its technical properties

and authorization status.

Artifact Purpose ≠ Artifact Authorization.

Artifact Type Governance

AVIM shall identify the relevant artifact type.

Types may include:

  • Executable binaries
  • Libraries
  • Software packages
  • Container images
  • Compiled assets
  • Generated code
  • Deployable bundles
  • Configuration packages
  • Firmware images
  • Software installation packages

Artifact type shall remain sufficiently precise for competent identity and

integrity assessment.

Artifact Type ≠ Artifact Identity.

Artifact Scope Governance

AVIM shall establish the boundaries of the artifact being assessed.

Scope may concern:

  • A single file
  • A software package
  • A container image
  • A multi-file bundle
  • A composite artifact
  • A generated software component
  • A deployable software unit

Scope shall identify which constituent elements are included in the
integrity assessment.

Artifact Scope Definition ≠ Verified Artifact Composition.

Artifact Classification

AVIM shall recognize the artifact's intended lifecycle classification.

Classifications may include:

  • Development artifact
  • Test artifact
  • Integration artifact
  • Release candidate
  • Production artifact
  • Maintenance artifact
  • Recovery artifact
  • Historical artifact

Classification shall not independently establish artifact validity or

release authorization.

Artifact Classification ≠ Artifact Governance State.

Artifact Identity Governance

AVIM shall establish an identifiable reference for each material
artifact.

Identity may involve:

  • Artifact identifier
  • Artifact namespace
  • Artifact type
  • Artifact content reference
  • Artifact creation reference
  • Artifact repository reference
  • Relevant lifecycle context

An artifact's identity shall remain distinguishable from its human-readable

name.

Artifact Name ≠ Verified Artifact Identity.

Artifact Content Identity

AVIM shall establish the identity of the artifact's material content.

Content identity may be supported through:

  • Cryptographic digests
  • Content-addressed references
  • Signed manifests
  • Verified package records
  • Direct artifact inspection
  • Competent equivalent mechanisms

The selected method shall be appropriate to the artifact type and integrity

claim.

Artifact Label ≠ Artifact Content Identity.

Artifact Version Identity

AVIM shall identify the version attributed to a material artifact.

Version references may include:

  • Semantic versions
  • Build versions
  • Release candidate identifiers
  • Internal revision identifiers
  • Package versions
  • Container tags
  • Artifact generation identifiers

Version identity shall remain associated with the artifact to which it

applies.

Version Identifier ≠ Verified Artifact Version.

Version Attribution Governance

AVIM shall preserve the basis upon which a version is attributed to an
artifact.

Attribution may originate from:

  • Build records
  • Version manifests
  • Repository metadata
  • Package metadata
  • Release preparation records
  • Authorized version assignment

Attribution shall remain distinguishable from independent content

verification.

Version Attribution Record ≠ Version Correspondence Evidence.

Version Correspondence

AVIM shall assess whether an artifact corresponds to its claimed
version.

Correspondence may involve:

  • Claimed version
  • Expected artifact identity
  • Expected content reference
  • Build identity
  • Applicable baseline
  • Version assignment evidence
  • Observed artifact content

Version correspondence shall be evaluated within the relevant artifact
scope.

Matching Version Label ≠ Verified Version Correspondence.

Artifact Composition References

AVIM shall identify material constituent elements of composite artifacts

where necessary for integrity assessment.

Composition may include:

  • Files
  • Libraries
  • Embedded components
  • Generated resources
  • Package metadata
  • Container layers
  • Configuration resources

AVIM governs the integrity and identity relationships of the resulting

artifact.

Dependency origin and suitability remain governed by SDS.

Composite Artifact Identity ≠ Verified Constituent Integrity.

Configuration Baseline Correspondence

AVIM shall preserve the relationship between an artifact and its relevant

configuration baseline.

The relationship may identify:

  • Baseline identity
  • Expected artifact reference
  • Relevant version constraints
  • Material configuration relationships
  • Applicable environment assumptions

Baseline correspondence shall remain distinguishable from actual runtime

configuration conformity.

Artifact Baseline Correspondence ≠ Verified Runtime Configuration.

Build Correspondence

AVIM shall preserve evidence-supported relationships between artifacts and

their originating build events.

Relevant information may include:

  • Build identity
  • Build output reference
  • Source input references
  • Toolchain references
  • Relevant execution conditions
  • Artifact creation evidence

BMM governs the build execution process.

AVIM governs whether the resulting artifact identity and version

relationship remain sufficiently supported.

Build Reference ≠ Verified Artifact Build Origin.

Artifact Provenance

AVIM shall preserve material evidence concerning artifact origin and

relevant transformations.

Provenance may involve:

  • Originating build
  • Producing system
  • Source references
  • Artifact transformation events
  • Repository transfers
  • Relevant signing events
  • Custody relationships

A recorded provenance claim shall remain distinguishable from independently

verified provenance.

Recorded Artifact Provenance ≠ Verified Artifact Provenance.

Artifact Transformation Governance

AVIM shall identify material transformations that may affect artifact
identity or content.

Transformations may include:

  • Packaging
  • Compression
  • Re-signing
  • Rebundling
  • Recompilation
  • Container layering
  • Metadata modification
  • Binary patching

Transformations shall preserve the relationship between predecessor and

successor artifacts.

Artifact Transformation ≠ Artifact Identity Preservation.

Artifact Derivation

AVIM shall establish material relationships between derived artifacts and

their source artifacts.

Derivation may involve:

  • Parent artifact identity
  • Transformation method
  • Transformation event
  • Derived artifact identity
  • Resulting content reference
  • Supporting evidence

Derived artifacts shall not automatically inherit the integrity status of

their predecessors.

Verified Source Artifact ≠ Verified Derived Artifact.

Artifact Equivalence

AVIM shall distinguish different forms of artifact equivalence.

Equivalence may concern:

  • Identical content
  • Identical package composition
  • Identical executable behavior
  • Equivalent functional output
  • Equivalent deployment suitability

These claims require different evidence.

AVIM governs artifact identity and content correspondence.

Broader functional equivalence remains subject to competent software

quality governance.

Functional Equivalence ≠ Content Identity.

Artifact Duplication

AVIM shall recognize when multiple artifact instances claim the same
identity or version.

Instances may exist in:

  • Different repositories
  • Build systems
  • Artifact stores
  • Deployment environments
  • Backup systems
  • Distribution channels

Matching labels shall not establish identical content.

Duplicate Version Labels ≠ Identical Artifact Content.

Artifact Storage References

AVIM shall preserve material storage references relevant to artifact

integrity and retrieval.

References may include:

  • Repository location
  • Artifact store identity
  • Storage object reference
  • Content address
  • Relevant access conditions
  • Retention context

Storage references shall remain distinguishable from verified artifact

content.

Artifact Storage Location ≠ Artifact Identity.

Artifact Repository Governance

AVIM shall assess material repository records supporting artifact identity

and version claims.

Relevant records may include:

  • Artifact registration
  • Version assignment
  • Content digest
  • Upload event
  • Modification event
  • Repository promotion
  • Deletion or replacement event

Repository records shall remain subject to evidence integrity
assessment.

Repository Record ≠ Independent Artifact Verification.

Artifact Retrieval Governance

AVIM shall recognize the artifact actually retrieved from a storage or

distribution source.

Retrieval assessment may involve:

  • Requested artifact identity
  • Requested version
  • Source location
  • Retrieved content
  • Observed digest
  • Retrieval time
  • Verification result

The retrieved artifact shall not automatically be treated as identical to

the intended artifact.

Requested Artifact ≠ Retrieved Artifact.

Artifact Integrity Evidence

AVIM shall preserve evidence supporting material artifact integrity
claims.

Evidence may include:

  • Cryptographic digests
  • Digital signatures
  • Signed manifests
  • Verified build references
  • Repository integrity records
  • Artifact inspection results
  • Relevant custody records

Evidence shall remain associated with the specific artifact and integrity

claim it supports.

Integrity Evidence Presence ≠ Verified Artifact Integrity.

Integrity Verification

AVIM shall establish whether the material artifact integrity claim has been

sufficiently verified.

Verification may assess:

  • Artifact content identity
  • Expected digest correspondence
  • Signature validity
  • Manifest correspondence
  • Version reference correspondence
  • Artifact transformation history
  • Relevant evidence integrity

Verification shall remain bounded by the method and evidence used.

Successful Integrity Check ≠ Complete Artifact Trustworthiness.

Verification Method Suitability

AVIM shall assess whether the selected verification method is
appropriate for the relevant artifact and claim.

Relevant considerations may include:

  • Artifact type
  • Content scope
  • Verification mechanism
  • Algorithm suitability
  • Reference authenticity
  • Key or credential validity
  • Material threat conditions

A technically successful verification using an unsuitable or untrusted

reference may not establish the intended integrity claim.

Verification Mechanism Execution ≠ Competent Integrity Verification.

Integrity Reference Authenticity

AVIM shall distinguish the integrity of an artifact from the authenticity

of the reference against which it is checked.

For example:

A downloaded artifact may match a published checksum.

However, if the checksum was obtained from an untrusted or compromised

source, the match does not independently establish that the artifact
is the intended authorized version.

Digest Match ≠ Trusted Artifact Origin.

Artifact Signing References

AVIM shall preserve relevant signing information where signatures are
used to support artifact integrity or provenance claims.

Relevant information may include:

  • Signing identity
  • Signing authority
  • Signed artifact scope
  • Signature validity
  • Signing time
  • Certificate or key status
  • Applicable trust conditions

A valid signature does not independently establish software
correctness or legitimate release approval.

Valid Artifact Signature ≠ Authorized Software Release.

Verification Authority

AVIM shall identify the competent authority or accepted mechanism

responsible for material integrity determinations.

Authority may concern:

  • Approved verification procedures
  • Trusted reference sources
  • Assigned artifact integrity responsibilities
  • Defined organizational controls
  • Applicable automated verification mechanisms

Technical ability to perform verification shall remain distinguishable from

authority to certify or accept its result.

Verification Capability ≠ Verification Authority.

Artifact Modification Recognition

AVIM shall identify material changes affecting artifact content or
identity.

Modifications may include:

  • Binary patching
  • Metadata alteration
  • Package modification
  • File replacement
  • Container layer changes
  • Signature replacement
  • Configuration resource modification

A modified artifact shall be reassessed where its previous integrity
determination no longer applies.

Previous Artifact Integrity ≠ Current Artifact Integrity.

Artifact Replacement

AVIM shall preserve the relationship between an existing artifact and its

replacement.

Replacement should identify:

  • Previous artifact
  • Replacement artifact
  • Material content differences
  • Version relationship
  • Replacement event
  • Relevant authority reference
  • Supporting evidence

Artifact replacement shall not silently preserve the previous artifact's

identity or integrity state.

Artifact Replacement ≠ Artifact Identity Continuity.

Artifact Promotion References

AVIM shall recognize material transitions in which an artifact is
promoted between lifecycle contexts.

Examples may include:

  • Development to testing
  • Testing to staging
  • Staging to release preparation
  • Release preparation to production artifact storage

AVIM preserves artifact identity and integrity across these
transitions.

Authorization of release and deployment remains governed by the relevant

SLGA™ standards.

Artifact Promotion ≠ Release Authorization.

Artifact Distribution References

AVIM shall preserve material integrity relationships when artifacts
are distributed or transferred.

Relevant information may include:

  • Origin artifact
  • Distribution source
  • Transfer event
  • Destination reference
  • Received artifact
  • Content verification
  • Relevant custody evidence

Distribution shall not automatically establish that the recipient
obtained the intended artifact.

Artifact Distribution ≠ Verified Artifact Receipt.

Artifact Version Conflict

An Artifact Version Conflict exists where material version claims or
supporting evidence are incompatible.

Examples may include:

  • One version label associated with different artifact content
  • Conflicting version manifests
  • Contradictory repository metadata
  • Incompatible build-to-version references
  • Conflicting artifact signing information

AVIM shall preserve the conflict and its supporting evidence.

Conflicting Version Records ≠ Permission to Select the Preferred
Version.

Artifact Identity Conflict

An Artifact Identity Conflict exists where material claims concerning
artifact identity or content correspondence are incompatible.

Examples may include:

  • Identical artifact identifiers with different content
  • Conflicting content digests
  • Inconsistent package composition
  • Contradictory provenance records
  • Different retrieved content under the same repository reference

AVIM shall preserve the conflict for competent assessment.

Shared Artifact Identifier ≠ Shared Artifact Identity.

Artifact Integrity Uncertainty

AVIM shall preserve material uncertainty concerning artifact identity,

version correspondence, provenance, or integrity.

Uncertainty may arise where:

  • Artifact content cannot be inspected
  • Expected digests are unavailable
  • Version attribution is ambiguous
  • Build origin is unresolved
  • Signing references cannot be validated
  • Transformation history is incomplete
  • Retrieved content differs from expectations

Uncertainty shall not be silently converted into verified integrity.

Unresolved Artifact Integrity ≠ Verified Artifact Integrity.

Artifact Evidence Gap

An Artifact Evidence Gap exists where material information required
for competent artifact-version integrity assessment remains
insufficiently established.

Examples may include:

  • Missing content identity evidence
  • Missing version attribution records
  • Unresolved build correspondence
  • Missing transformation evidence
  • Incomplete repository records
  • Unverified integrity references

AVIM shall identify the gap and its material significance.

Artifact Evidence Gap ≠ Proven Artifact Compromise.

Critical Artifact Integrity Gap

A Critical Artifact Integrity Gap exists where missing evidence
prevents competent assessment of a materially consequential artifact.

Examples may include:

- A production executable without sufficiently established content

identity. - A release candidate whose version cannot be reliably
connected to its build. - A critical software package with unresolved
signature authenticity. - A deployment artifact whose retrieved
content cannot be matched to its approved reference.

AVIM shall preserve the critical gap for competent downstream
assessment.

It does not independently determine software compromise, operational
shutdown, or legal liability.

Critical Artifact Integrity Gap ≠ Automatic Artifact Compromise.

Artifact Integrity Failure

An Artifact Integrity Failure exists where competent evidence
establishes that a material artifact integrity requirement is not
satisfied.

Examples may include:

  • A verified digest mismatch
  • An invalid signature where signature validity is required
  • A demonstrated artifact-version mismatch
  • A confirmed unauthorized content alteration within the assessed

integrity scope.

AVIM shall distinguish established integrity failure from uncertainty or

missing evidence.

Verified Integrity Failure ≠ Mere Integrity Uncertainty.

Artifact Integrity Validation

AVIM shall determine whether material artifact-version integrity conditions

are sufficiently supported.

Validation may consider:

  • Artifact identity
  • Content identity
  • Version attribution
  • Version correspondence
  • Build correspondence
  • Baseline correspondence
  • Provenance
  • Transformation relationships
  • Integrity evidence
  • Verification method suitability
  • Material uncertainty

Validation shall remain limited to the artifact properties and claims

actually assessed.

Validated Artifact Integrity ≠ Validated Software Correctness.

Artifact Continuity

AVIM shall preserve material artifact identity and version relationships

across software lifecycle transitions.

Continuity may involve:

  • Artifact creation
  • Build output registration
  • Repository storage
  • Artifact copying
  • Artifact transformation
  • Version assignment
  • Promotion
  • Distribution
  • Retrieval
  • Replacement
  • Historical preservation

Artifact continuity shall distinguish identical content from derived,

transformed, or replaced content.

Artifact Continuity ≠ Artifact Content Immutability.

Artifact Historical Preservation

AVIM shall support preservation of material historical artifact identity

and version evidence.

Historical records may include:

  • Previous artifact identities
  • Previous content references
  • Previous version assignments
  • Superseded artifact references
  • Relevant integrity assessments
  • Transformation histories
  • Replacement relationships

Historical preservation shall not automatically establish that a
historical artifact remains currently suitable for use.

Historical Artifact Integrity ≠ Current Artifact Suitability.

Artifact Reassessment

AVIM shall support reassessment when material artifact identity,
version, provenance, or integrity conditions change.

Triggers may include:

  • New artifact content evidence
  • Conflicting repository records
  • Signature invalidation
  • Discovered version mismatch
  • Artifact modification
  • Artifact replacement
  • New provenance evidence
  • Material integrity gaps
  • Changed verification references

Reassessment shall preserve relevant historical determinations and their

supporting evidence.

Artifact Reassessment ≠ Historical Integrity Record Erasure.

Artifact Governance States

AVIM shall support identifiable governance states.

Possible states include:

Identified: An artifact governance object has been recognized.

Registered: An artifact has been associated with a material record.

Version-Declared: A version claim has been established as a
declaration.

Under Assessment: Material artifact integrity conditions are being
evaluated.

Content-Verified: Artifact content identity has been sufficiently

established within the assessed scope.

Version-Verified: Artifact-version correspondence has been sufficiently

established.

Provenance-Unresolved: Material artifact origin evidence remains

insufficient.

Version-Unresolved: Material version correspondence remains uncertain.

Integrity-Unresolved: Material integrity conditions remain insufficiently

established.

Evidence-Limited: Available evidence is insufficient for the required
determination.

Conflicted: Material artifact claims or evidence are contradictory.

Integrity-Failed: A material integrity requirement has been shown not to

be satisfied.

Validated: Material artifact-version integrity conditions are
sufficiently supported within the assessed scope.

Superseded: A later artifact or version relationship has replaced the

earlier reference.

Retired: The artifact is no longer an active applicable reference.

Unresolved: Available information does not support a sufficiently
determined state.

These states shall not independently establish software correctness,

security, release readiness, or deployment authorization.

Verified Artifact Integrity ≠ Verified Software Safety.

Minimum Implementation Framework

A conforming implementation of AVIM must provide the following six
functional capabilities.

  • Artifact Object, Identity, Purpose, Type, Scope, and
    Classification

Governance

Capability to establish identifiable artifact governance objects, determine

artifact purpose, type, scope, and classification, and distinguish
artifact identity from filenames, repository references, and informal
labels.

The implementation must preserve sufficiently stable artifact identity
across relevant lifecycle events.

  • Artifact Content, Version Attribution, and Correspondence
    Governance

Capability to establish artifact content identity, preserve version

attribution, assess artifact-version correspondence, and distinguish
declared version labels from verified content relationships.

The implementation must not treat matching version labels as proof of
identical artifact content.

  • Build, Baseline, Provenance, Transformation, and Derivation
    Governance

Capability to associate artifacts with relevant build and configuration

baseline references, preserve material provenance evidence, identify
transformations and derivations, and maintain predecessor–successor
relationships.

The implementation must distinguish recorded provenance from verified
provenance and original artifacts from transformed artifacts.

  • Artifact Integrity Evidence, Verification, Reference
    Authenticity, and

Authority Governance

Capability to associate artifact integrity claims with competent evidence,

apply suitable verification methods, assess reference authenticity,
preserve signing information where relevant, and identify competent
verification authority.

The implementation must distinguish successful technical checks from
complete artifact trustworthiness.

  • Artifact Conflict, Gap, Failure, Continuity, and Reassessment
    Governance

Capability to identify version conflicts, identity conflicts, integrity

uncertainty, evidence gaps, critical integrity gaps, established
integrity failures, modification events, replacement relationships,
historical records, and reassessment conditions.

The implementation must distinguish missing evidence from established
compromise or integrity failure.

  • Governed Artifact Version Integrity State and SCFS Handoff
    Governance

Capability to produce a Governed Artifact Version Integrity State with

sufficient artifact identity, version, content, provenance, build
correspondence, integrity evidence, validation, uncertainty, and
continuity information for competent downstream SCFS governance.

The implementation must not represent artifact integrity as proof of
software correctness, security, release readiness, or deployment
authorization.

Use Case 1 — Two Artifacts Share the Same Version Label but Contain

Different Software

An organization maintains a software application distributed through
two internal artifact repositories.

Both repositories contain an artifact labeled:

Application Version 4.2.1

The first artifact was generated through an approved build pipeline.

The second artifact was uploaded later by an automated maintenance
process.

Both artifacts have the same filename and version label.

However, their cryptographic digests differ.

The organization initially assumes that the artifacts are
interchangeable because the version labels match.

AVIM evaluates:

Artifact Identity → Version Attribution → Content Identity → Build

Correspondence → Repository Evidence → Integrity Verification

The assessment identifies:

  • Two distinct artifact content identities
  • One shared version label
  • Conflicting version correspondence claims
  • Different artifact creation or registration histories
  • Insufficient evidence that both artifacts represent the same

authorized version.

The relevant governance state may be:

Conflicted

until competent evidence resolves the version correspondence.

The critical distinctions are:

Matching Version Label ≠ Verified Version Correspondence.

Duplicate Version Labels ≠ Identical Artifact Content.

Repository Record ≠ Independent Artifact Verification.

Artifact Name ≠ Verified Artifact Identity.

The result: AVIM prevents version labels from concealing materially

different software artifacts and establishes the need for
content-based identity and evidence-supported version correspondence.

Use Case 2 — A Software Package Passes a Checksum Test Against an

Untrusted Reference

An organization downloads a software package from an external distribution

source.

The package is accompanied by a checksum published on the same
website.

The organization calculates the package checksum.

The values match.

The package is therefore initially considered verified.

However, the distribution website has been compromised.

Both the software package and the published checksum were replaced by the

The checksum match is technically correct.

But the reference itself is not trustworthy.

Retrieved Artifact → Content Identity → Integrity Reference → Reference

Authenticity → Provenance → Verification Evidence

The assessment identifies:

  • The downloaded package matches the supplied checksum
  • The checksum originates from the same compromised distribution
    source
  • The match supports content correspondence with the supplied
    reference
  • The match does not establish that the reference represents the
  • Independent provenance or trusted reference evidence is required
    for

intended authorized artifact. the broader integrity claim.

The relevant governance state may be:

Provenance-Unresolved

or:

Integrity-Unresolved

depending on the available evidence.

The critical distinctions are:

Digest Match ≠ Trusted Artifact Origin.

Integrity Evidence Presence ≠ Verified Artifact Integrity.

Verification Mechanism Execution ≠ Competent Integrity Verification.

Successful Integrity Check ≠ Complete Artifact Trustworthiness.

Canonical Closing Statement

Software artifacts are not reliably identified by their names.

They are not reliably verified by version labels alone.

And they do not become trustworthy merely because they exist in a

repository, carry a digital signature, or match a supplied checksum.

An artifact's identity must remain connected to its actual content.

Its version must remain connected to evidence supporting version
correspondence.

Its provenance must remain distinguishable from an unsupported origin
claim.

Its integrity verification must rely on competent methods and
sufficiently trustworthy references.

And its lifecycle history must preserve the material relationships
between original, transformed, copied, replaced, and retrieved
artifacts.

Declared Artifact Version ≠ Verified Artifact Version Integrity.

Matching Version Label ≠ Verified Version Correspondence.

Recorded Artifact Provenance ≠ Verified Artifact Provenance.

Digest Match ≠ Trusted Artifact Origin.

Validated Artifact Integrity ≠ Validated Software Correctness.

These distinctions become increasingly important as software artifacts
are generated, transformed, stored, and distributed through automated
systems and autonomous software development processes.

An AI agent may create a package.

A build pipeline may assign a version.

A repository may register the artifact.

A distribution system may deliver it.

None of these actions independently establishes that the artifact's
claimed identity, content, version, and provenance remain sufficiently
supported.

AVIM establishes the methodological requirement that artifact-version
integrity remain an identifiable, evidence-supported governance
condition rather than an assumption derived from filenames, labels, or
successful technical operations.

It does not promise that an integrity-verified artifact is secure,
functionally correct, or authorized for release.

It establishes the narrower but essential condition that the artifact
under assessment is sufficiently identifiable and that its material
version and integrity claims can be competently evaluated.

AVIM transforms software artifact versions from administrative labels into

governed identity and integrity relationships — ensuring that software
organizations can establish not merely which version an artifact
claims to represent, but which artifact actually exists, what content
it contains, how its version is supported, and whether its integrity
remains verifiable throughout the software lifecycle.

An artifact version is not governed because it has been named,
numbered, signed, or stored. It is governed when its identity,
content, version correspondence, provenance, integrity evidence, and
lifecycle continuity remain sufficiently established to support
competent software configuration governance.
