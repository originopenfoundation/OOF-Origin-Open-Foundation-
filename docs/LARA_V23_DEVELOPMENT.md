# LaRA v2.3 development boundary

The existing widget offers explicit Cross-Architecture Reasoning and automatic
selection for a multi-space operational problem. Single definitions keep the
ordinary retrieval route. Problem Discovery, navigation and cross reasoning are
three trusted capabilities, not autonomous agents. The cross route performs no
model call and takes no external action.

Versioned contracts live in `schemas/oof-cross-architecture.v1.schema.json` and
`schemas/oof-capability.v1.schema.json`. Existing read-only Knowledge is the
only methodology registry. Candidate operational cue mappings are hypotheses,
not a second source of architecture approval or relationship authority.

Canonical relationships require eligible endpoints and an exact, active,
authoritative relationship record with complete provenance. A hierarchy edge
within one architecture does not establish a dependency between architectures.
Tentative primary ordering is not normative priority; alternatives remain in
the output. Follow-up problem digests include all retained reported turns.

Registry limitations remain visible: RSGA currently has no eligible mapped
representation in the shared consumer. Its assignment remains unresolved rather
than creating a source association or approval automatically. Current SLGA
follows the explicit existing approval; in-progress behavior uses a labelled
synthetic fixture and does not rewrite that approval.

Groq narration now requests low reasoning effort for the pinned GPT-OSS model,
without increasing the output-token budget. The parameter is limited to Groq;
other compatible providers receive no new parameter. Reference:
https://console.groq.com/docs/reasoning . Incomplete responses still fail closed.
Private model captures are quality-reviewed separately from technical tests.
Model narration is not enabled on the deterministic cross-architecture route.

Public scopes stay empty, REPORT_ONLY stays active and global integration
readiness remains false. This work does not authorize merge, public deployment,
paid infrastructure, external tools, canonical edits or prototype acceptance.

The capability core validates input/output, enforces declared tools and caller
permissions, bounds byte sizes, elapsed time and eight steps per host authority
scope, and records digests. Its synchronous trusted code is not preempted; late
results are rejected after return. It is not a sandbox or an agent platform.
