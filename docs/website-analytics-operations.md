# Website analytics operations

## Release state

The website tracker is enabled in the published configuration. The static website is hosted on GitHub Pages; it cannot execute the LaRA Node server. The existing Render reference configuration uses a free service and does not establish persistent storage, and the owner has no access to that service. The separate Supabase Edge Functions and Cloudflare Worker proxy are deployed; a production HEAD request verified their authenticated database connection without recording an event. The backend is enabled, so disabling the website tracker alone does not prevent direct submissions to the public Worker. Because the domain currently resolves directly to GitHub Pages and is not a Cloudflare zone in the available account, the owner selected a separate workers.dev address instead of changing DNS. This address is cross-origin, not a first-party endpoint. Collection is separate from Cloudflare Web Analytics, although Cloudflare operates the proxy and may process request metadata. The administrator signed in and a website analytics notice was published. Legal review, MFA verification, monitoring, and a complete production event test remain necessary; the notice is not a legal compliance determination.

Umami was evaluated but its documented default session identifier combines IP address, User-Agent and a rotating salt. That default is incompatible with the task's strict no-fingerprinting requirement. This limited aggregate collector is not presented as feature-equivalent to Umami: it does not estimate visitors, reconstruct journeys, identify bots, or accept raw search queries.

## Configuration

The separate Supabase implementation uses `OOF_ANALYTICS_DATABASE_PASSWORD` for the restricted role, `OOF_ANALYTICS_ADMIN_USER_ID` for the approved administrator, and `OOF_ANALYTICS_PROXY_TOKEN` shared only between the proxy and collector. `OOF_ANALYTICS_ENABLED` is set on the deployed backend. Secrets must never be put into the repository or browser. The default Supabase Auth site URL was observed as `http://localhost:3000`; the analytics recovery flow explicitly requests its allowlisted production redirect. Free Cloudflare Zero Trust checkout requested payment details and authorization for possible overages, so it was not activated.

1. Provision an independently controlled, durable backend outside the public website tree. The chosen no-DNS-change option uses the specifically allowlisted `https://oof-analytics-ingress.samuel-malicky2.workers.dev/_oof/analytics/event` Worker endpoint. A free Render filesystem alone is not durable.
2. Provision the Supabase restricted role password in Edge Function secrets and test its TLS connection to the dedicated analytics schema. The functions check the role, row-level security, table permissions and public schema access before use. Do not use the project's privileged default database credential. A temporary authenticated connection probe returned success and was removed. The scheduled `oof-analytics-retention` job runs as the restricted writer, removes records older than 90 days and is scheduled daily at 03:17 UTC; a test execution succeeded with no rows to delete. A verified backup mechanism remains a release blocker.
3. Authenticate the standalone administrator through Supabase Auth and restrict server-side reports to the explicitly approved user ID. Verify invitation redirects, authentication, token handling, MFA policy and denied access before deployment. The existing LaRA administration is unrelated and must not be opened to the public or weakened.
4. Cloudflare Web Analytics is optional. Configure `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_WEB_ANALYTICS_SITE_TAG`, and `CLOUDFLARE_ANALYTICS_API_TOKEN` in the backend environment, not in Git or browser code. GitHub Actions secrets do not automatically become Render environment variables. Use a read-only token with the minimum required permissions.
5. After the prerequisites, privacy notice review, and access controls are verified, change `assets/data/oof-analytics-config.json` to enable collection. The client accepts only the same-origin endpoint or the explicitly pinned Worker endpoint and sends requests without cookies or a referrer header. The existing Cloudflare beacon is separate.

The Worker requires an `ANALYTICS_RATE_LIMIT` binding and fails closed if it or the Cloudflare client address is unavailable. It uses an HMAC of the address and the current minute as the rate-limit key; the address and derived key are not forwarded to the collector or stored in the analytics records. Cloudflare's rate limiting is approximate and location-specific, so this does not eliminate abuse. Platform providers may process network metadata under their own policies.

## Data and retention

The collector accepts event, content category, coarse referrer category, language, and an optional public canonical content ID from the generated allowlist. It stores daily aggregate counters only; it does not store URLs, IP addresses, user agents, cookies, browser IDs, search terms, LaRA conversations, or visitor-level records. Server infrastructure and network providers may still process request metadata under their own policies. This implementation cannot establish unique visitors, session paths, human identity, or bot classification. Regenerate the allowlist with `node tools/build_website_analytics_catalog.cjs` after changes to the canonical public knowledge registry.

The optional Cloudflare adapter queries only the existing Web Analytics visit grouping by date and country. It does not currently provide HTTP requests, bandwidth, verified bots, or security events; those metrics are shown as unavailable. Cloudflare visits and independent page views are different measures and must not be added together or interpreted as verified humans.

The database prunes old aggregate rows on startup and approximately daily. The private GitHub backup workflow exports aggregate CSV files and retains them for seven days. On 19 November 2026, an isolated PostgreSQL restore check imported the latest empty backup and successfully round-tripped a synthetic record; a restore of a non-empty real backup and recovery of schema and roles remain unverified. Supabase's free plan has limitations, including possible inactivity pauses and restrictions on downloadable automatic backups; verify the current service terms and arrange separate backups. For SQLite, use a consistent SQLite backup mechanism. To remove analytics data, disable collection first, then remove the analytics records and all retained backups using the host's authorized procedures; SQLite installations must also account for WAL/SHM companions. Deletion does not remove Cloudflare data.
