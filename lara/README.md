## Current implementation: 17 October 2026

See [the implementation and verification audit](../docs/lara-intelligent-foundation.md) for current evidence, deployment instructions and limitations. The notes below this section describe earlier snapshots and must not be treated as current test totals or readiness counts.

Run `node tools/check_lara.cjs`, `node --test tests/lara/*.test.js`, and `node tests/lara/memory-smoke.cjs`. Start with `node lara/server.js`. No npm dependencies are required. Render uses the repository root, Node 24, `HOST=0.0.0.0`, `NODE_ENV=production`, and the platform PORT; `/_lara/ready` is the health endpoint. `render.yaml` documents the existing service and does not need importing as a new Blueprint.

Keep `LLM_PROVIDER`, `LLM_MODEL`, `LLM_API_KEY` and (when needed) `LLM_BASE_URL` in Render Environment. Explicit environment settings override saved admin settings at startup. A configured key is not proof of model operation. Public generation remains blocked by report-only until actual governance readiness is established. Local review additionally requires explicit `NODE_ENV=development` and loopback; no new production override exists.

The same gateway now handles evidence-grounded explanation, preliminary assessment and ordinary conversation where permitted. All four existing modes and bounded redacted history share one pipeline. `generation.kind` separates model, retrieval and preview; failure reasons never expose provider responses or credentials. Alternative provider fallback requires its own explicit configuration. Request/response/context/concurrency limits protect the lightweight backend; inference weights stay on a separate host.

Current recorded engineering: 53 Node tests, 18 Python knowledge tests, schema/manifest/deterministic rebuild validation and full-server 256 MiB memory smoke pass. Current inventory: 2,294 accessible resources; readiness remains false with 7 duplicate groups and 220 candidate groups. Actual model quality and the 42/50 target remain unverified. These figures are a dated snapshot, not hardcoded acceptance conditions.

## Historical integration notes

Memory regression: `node tests/lara/memory-smoke.cjs private-results.json` starts the actual server with a 256 MiB V8 heap, loads the full read-only registry and performs 30 HTTP/SSE queries. It checks readiness, final heap and worker RSS against the free instance budget. Run from a disposable checkout with no saved provider override. Text chunks are joined once into flat strings and retrieval caches flat normalized bodies instead of per-resource word Sets. No heap-size increase or reduced source/authority coverage is required.

Communication fixes (14 October 2026): explanatory questions no longer become assessments merely because they mention governance/authority. Preview greetings, capability boundaries and uncertainty are explicit. Retrieval matches words, requires a subject anchor, prioritizes the OOF homepage for foundation questions, and preserves approved exact-identity ambiguity. Short follow-ups reuse a temporary topic; language/style controls stay within the session. Provider requests carry at most six redacted history messages as untrusted data.

Source presentation removes forwarded-email contact headers, emails/credential patterns and email confidentiality boilerplate, and creates chunks at word boundaries. Canonical files, their hashes and registry readiness are unchanged. This filters assistant output; it does not remove already-published contact metadata from the original website. The generated-output guard rejects user-supplied names/numbers as evidence and obvious unsupported authority/action claims, but remains a conservative rule filter rather than a complete semantic verifier.

Invalid inference configuration is diagnosed and the server keeps a source preview available. Public status includes the communication version and an optional Render commit revision. Real model generation stays blocked while public report-only governance review is unresolved. Friendly preview templates and quotations do not demonstrate generative intelligence, translated explanations or adaptive humor. Preserve the original baseline JSON and run `tests/lara/communication-audit.cjs` into a separate post-fix output. Regression suite now includes communication regressions; no audit transcript with contact data should be committed.

Run `node lara/server.js` from the repository root. Default URL: http://127.0.0.1:4173/. The active testing instance uses port 4180. Configure server environment using `.env.example`; never publish `.env`. No dependency installation is required (Node with built-in fetch).

The existing provider adapter, sessions, recognition, learning, assessment and authorization modules are reused. The widget mounts through the current shared header, even while Render is waking up. `assets/lara/config.json` sets its backend origin; localhost uses the local server. Existing language navigation and canonical pages remain intact. GitHub Pages does not execute Node; the assistant calls its Render backend using explicitly allowed frontend origins.

Knowledge is an in-memory read-only view of `data/knowledge`. There is no separate LaRA index/database or crawler. Public representations and their objects must explicitly allow LaRA and have CANONICAL_AUTHORITATIVE or SUPPORTING_CITABLE authority. Canonical evidence precedes supporting explanations; review/quarantine/private entries are excluded. Source paths stay within the repository and source hashes are verified using the shared registry's normalization. Changed sources are excluded until the existing governance build validates them. Only declared authoritative relationships expand retrieval. Source metadata retains object ID, representation ID, authority domain and provenance. `object_id` in chat supports exact ID, URL, name or approved alias lookup, returning FOUND, AMBIGUOUS or NOT_FOUND; candidate aliases never establish identity.

The shared readiness report currently has `LARA_INTEGRATION_READY=false`: 7 duplicate OriginID groups and 208 candidate groups remain under review. Responses expose `report_only=true`; public chat uses an explicitly labelled read-only registry preview while this report remains unresolved; production inference and public-chat learning writes are disabled. The integration does not alter the report or authorize production cutover. Admin reindex reloads the shared view and never regenerates canonical knowledge. The admin HTML is stored as a template to avoid including it in canonical public-page inventories.

Personality v1.0 supports natural/professional/exploration/sensitive communication and off/low/balanced humor. Set `LARA_PERSONALITY_ENABLED`, `LARA_PERSONALITY_MODE`, `LARA_PERSONALITY_HUMOR` and restart. The widget has a Communication style selector; sensitivity overrides style requests and disables humor. Personality introduces no persistent profiles or additional model calls. Existing learning remains separate from canonical knowledge and existing continuity requires explicit user confirmation.

With no configured LLM, responses remain source excerpts or deterministic assessments. LLM-generated style currently applies only to retrieval with evidence, not to casual greetings, unsupported questions or assessments. A live model's humor, truthfulness and resistance to injection have not been evaluated. Pattern cues and prompt instructions are not a complete safety classifier or semantic validator.
