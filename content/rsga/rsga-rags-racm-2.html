1. Canonical Definition

RACM — Resource Access Control Module governs how an established Resource Access authorization is translated into enforceable Resource Access controls that permit, constrain, activate, restrict, suspend, terminate, and verify actual access to a defined Resource or Resource capacity in accordance with the governed Access State, scope, limits, conditions, and authority.

RACM establishes the control layer between:

governed Resource Access authorization

and:

actual Resource Access.

Authorized Access ≠ Enforced Access Control.

2. Operational Role

RAEM establishes whether an actor is eligible to proceed within Resource Access Governance.

RACM governs how a valid Access authorization is operationally represented and enforced.

It determines:

which actor may exercise the authorized Access; which Resource may be accessed; which control mechanism implements that Access; what quantity, capacity, rate, purpose, temporal, spatial, or functional limits apply; when Access may become active; how restrictions are enforced; how Access is suspended or terminated; whether technical or operational Access matches the governed Access State; and how deviations are detected and corrected.

RACM does not create legitimate authority merely because a control system can technically enable Access.

3. Core Question

How must a governed Resource Access authorization be translated into operational controls so that the correct actor can access the correct Resource, within the authorized scope, limits, conditions, location, and time, while unauthorized or out-of-scope Resource Access is prevented or detected?

4. Position in RAGS Governance

Canonical functional progression:

Access Subject → Eligibility → Authority / Authorization → Access Control → Scope & Restrictions → Active Resource Access → Monitoring / Reassessment / Termination

RACM governs the control boundary between authorization and operational Resource Access.

It does not determine Resource Priority or Allocation.

5. Governed Space

RACM governs:

Resource Access Control Governance

This space concerns the controlled implementation and enforcement of legitimate Resource Access decisions.

6. Governed Object

The primary Governed Object is:

A Resource Access Control relationship implementing a governed Resource Access authorization.

Canonical relationship:

**Authorized Actor

Resource Governed Access State Authorized Scope Limits & Conditions → Access Control → Controlled Resource Access**

7. Scope

RACM governs:

Access Control definition; Access Control activation; actor-to-control binding; Resource-to-control binding; authorization-to-control traceability; quantity controls; capacity controls; rate controls; temporal controls; spatial controls; functional controls; purpose controls where enforceable; Resource Source controls; conditional controls; restriction controls; shared Access controls; temporary controls; emergency controls; control modification; control synchronization; Access suspension enforcement; Access revocation enforcement; Access expiration enforcement; Access Control verification; control-state evidence; Access Drift detection; control failure detection; control reassessment.

RACM does not independently:

determine Resource Access eligibility; create Access Authority; establish Resource Priority; allocate Resource capacity; determine Resource Demand; determine Resource Criticality; govern Resource Consumption efficiency; determine Scarcity response; establish long-term Resource Sustainability.

8. Access Control Principle

A governed Access authorization should be operationally enforceable where implementation conditions permit.

The control should reflect the authorization.

It should not redefine it.

Governance Defines Access. Control Enforces Access.

9. Authorization-to-Control Translation

RACM translates:

Who may access → What Resource → For what permitted scope → Within what limits → Under what conditions → During what period → At what location

into an enforceable Resource Access Control configuration.

10. Authorization Boundary

A control mechanism cannot legitimately expand the authority from which it derives.

Technical Permission ≠ Governance Authority.

If a technical system permits more than the governed authorization allows, the excess capability is not legitimate Access.

11. Control Subject

Every material Resource Access Control should be associated with the actor whose Access it implements.

The actor may be:

person; organization; facility; system; machine; AI system; autonomous system; operational function; infrastructure component.

12. Subject-Control Binding

The implementation must sufficiently establish that the control applies to the intended Access Subject.

Weak or ambiguous subject binding may permit unauthorized Resource Access.

13. Resource-Control Binding

The control must identify which Resource or Resource capacity it governs.

A permission affecting one Resource must not silently become authority over another Resource.

14. Resource Source Control

Where authorization is Source-specific, the Access Control should preserve that Source boundary where operationally enforceable.

Access to Resource Source A ≠ Access to Resource Source B.

15. Control Scope

The Access Control should reflect the authorized scope.

Scope may include:

Resource; Resource Source; quantity; capacity; rate; purpose; function; location; time; operating state.

16. Least-Scope Principle

Where controls permit granular enforcement, they should not provide materially broader Resource Access than the authorization requires.

Authorized Scope defines the maximum legitimate Control Scope.

17. Quantity Control

A Resource Access authorization may establish a maximum quantity.

RACM governs how that quantity boundary is enforced where technically or operationally possible.

18. Capacity Control

Capacity controls may govern:

electrical capacity; compute capacity;

storage capacity; network capacity; cooling capacity; processing capacity; other constrained Resource capacities.

19. Rate Control

Some Resources require rate-based Access Control.

Examples include:

water flow rate; power draw; network throughput; material delivery rate.

20. Temporal Control

Resource Access may be permitted only within defined time boundaries.

RACM may enforce:

start time; end time; scheduled windows; maximum duration; temporary activation; seasonal conditions; emergency duration.

21. Spatial Control

Where relevant, Access Control may restrict Resource Access to:

facility; region; network node; infrastructure segment; delivery point; other governed location.

22. Functional Control

Resource Access may be restricted to a particular function.

Where technically enforceable, RACM should preserve that functional boundary.

23. Purpose Control

Purpose restrictions may not always be directly enforceable by technical systems.

Where direct technical enforcement is unavailable, RACM may rely upon operational, procedural, contractual, monitoring, or audit controls.

24. Control Method Neutrality

RACM does not require one universal control technology.

Resource Access Control may be implemented through:

physical controls; digital permissions; identity-based controls; network controls; capacity schedulers; valves; meters; switches; quotas; rate limiters; operational procedures; contractual controls; human authorization; hybrid mechanisms.

The governance logic remains common.

25. Control Capability

The selected control mechanism should be capable of enforcing the material dimensions of the authorization relevant to that Resource context.

26. Control Capability Boundary

Control Capability ≠ Access Authority.

A control system may technically permit an action without legitimate governance authority to permit it.

27. Control Activation

A Resource Access Control becomes active when the authorized conditions for operational Access are satisfied.

Activation should remain traceable to the relevant authorization.

28. Authorization vs Activation

Access Authorization ≠ Access Activation.

An authorization may exist while the corresponding control remains inactive.

Examples include:

future Access; standby Access; emergency-only Access; Resource currently unavailable.

29. Activation Conditions

Activation conditions may include:

authorization validity; actor eligibility; time window;

location; Resource availability; operating state; emergency state; technical readiness.

30. Conditional Control

Where Access authorization is conditional, the control should reflect the relevant condition where implementation permits.

31. Condition Loss

Where a material activation condition ceases to hold, the control should transition according to the governed Access logic.

This may require:

restriction; deactivation; suspension; reassessment.

32. Active Control

An Active Control permits Resource Access within the governed scope.

Active does not mean unrestricted.

33. Restricted Control

A Restricted Control permits Resource Access within narrower limits than normal authorization or previous control state.

Examples:

reduced power limit; reduced water flow; reduced compute quota; restricted operating window.

34. Suspended Control

A Suspended Control prevents exercise of Resource Access while preserving the underlying governance distinction between suspension and revocation.

35. Revoked Control

Where Access authorization is revoked, corresponding controls should cease permitting the revoked Access within the required operational timeframe.

36. Expired Control

An expired authorization should not continue producing active Resource Access merely because the implementation system was not updated.

Expired Authorization + Active Technical Permission = Access Drift.

37. Temporary Control

Temporary Resource Access should include an explicit termination mechanism where feasible.

Temporary Access should not silently become persistent Access.

38. Emergency Control

Emergency Access Controls may permit exceptional Resource Access within a defined emergency authorization.

Emergency control should preserve:

authority; actor; Resource; scope; limits; activation condition; duration; termination condition.

39. Emergency Control Boundary

Emergency Control ≠ Unlimited Resource Control.

40. Standby Control

Standby Access may remain technically prepared but inactive until a governed trigger occurs.

41. Shared Access Control

Multiple authorized actors may share access to a Resource.

RACM should preserve actor-specific or class-specific limits where required.

42. Shared Access Boundary

Shared authorization does not mean every actor may consume unlimited Resource capacity.

43. Concurrent Access

Where multiple actors access the Resource simultaneously, Access Controls may need to preserve individual limits even where aggregate capacity remains a downstream Allocation concern.

44. Access Control and Allocation

RACM may enforce an Allocation decision received from RPAS.

It does not determine the Allocation.

Example:

RPAS Allocation = 8 MW

RACM may enforce:

Maximum Access Control = 8 MW

But:

Control Enforcement ≠ Allocation Authority.

45. Access Control and Reservation

Reserved Resource capacity may constrain what an Access Control can activate.

RACM may enforce that constraint without determining the legitimacy of the reservation.

46. Access Control and Availability

A valid Access Control cannot create Resource capacity that does not exist.

Access Control ≠ Resource Availability.

47. Access Control and Demand

A rise in Resource Demand does not automatically expand the Access Control.

Demand Increase ≠ Access Control Expansion.

48. Access Control and Criticality

High Resource Criticality does not automatically permit bypassing Access Controls.

Any exceptional pathway requires legitimate governance authority.

49. Access Control and Priority

Resource Priority may influence downstream Allocation and therefore the limits enforced by RACM.

Priority itself remains outside RACM.

50. Access Control and Consumption

RACM governs permission and control over Access.

RCUS governs actual Resource Consumption and Utilization.

Permitted Capacity ≠ Consumed Resource.

51. Access Control State

RACM should represent the current state of the Resource Access Control.

52. Minimum Access Control States

At minimum:

Control Defined

Control Active

Control Restricted

Control Standby

Control Suspended

Control Revoked

Control Expired

Control Failed

Control Conflicted

Control Unknown

Control Unresolved

53. Control Defined

A control configuration exists but is not necessarily active.

54. Control Active

The control currently permits Resource Access within its governed scope.

55. Control Restricted

The control currently permits narrower Resource Access than its normal or previous state.

56. Control Standby

The control is prepared for activation but is not currently permitting the governed Resource Access.

57. Control Suspended

The control prevents Resource Access due to a governed suspension.

58. Control Revoked

The control has been terminated following revocation of the relevant Access authorization.

59. Control Expired

The control's authorized validity period has ended.

60. Control Failed

The control is unable to enforce the governed Access State reliably.

61. Control Conflicted

Materially inconsistent control instructions or states exist.

62. Control Unknown

The actual control state cannot currently be established.

63. Control Unresolved

Relevant information exists but the valid control state cannot yet be determined.

64. Governed State vs Control State

RAGS Access State and RACM Control State are related but distinct.

Example:

Access State — Authorized

Control State — Standby

is valid.

So is:

Access State — Suspended

Control State — Failed

which represents a serious governance condition because the control may not enforce the suspension.

65. Control Synchronization

Material changes to the governed Resource Access State should propagate to the relevant Access Control within the operational timeframe required by the Resource context.

66. Synchronization Time

Not every Resource requires instantaneous control updates.

The required synchronization time should reflect:

Resource characteristics; Criticality; consequence; control capability; operational context.

67. Control Drift

Control Drift exists where the implemented Resource Access Control no longer correctly represents the governed Access State.

68. Access Drift

Access Drift exists where actual Resource Access no longer conforms to the governed Access State.

Control Drift may cause Access Drift.

The concepts should remain distinguishable.

69. Examples of Control Drift

Examples include:

authorization reduced but quota unchanged; Access revoked but technical permission remains active; temporary control never expires; Resource Source restriction not implemented; location boundary bypassed; old control configuration remains active after authorization update.

70. Drift Detection

RACM should support comparison between:

Governed Access State

and:

Implemented Control State

and, where evidence exists:

Actual Resource Access State.

71. Canonical Alignment

The desired alignment is:

Governed Access State → Control State → Actual Resource Access

Material divergence should remain detectable.

72. Control Verification

Access Controls should be verified where material to establish that they implement the intended authorization.

Verification may include:

configuration inspection; functional testing; telemetry; audit records; control-response testing; operational observation.

73. Control Effectiveness

A correctly configured control may still fail operationally.

RACM therefore distinguishes:

Control Configuration

from:

Control Effectiveness.

74. Control Configuration ≠ Control Effectiveness

A configuration record saying:

Maximum 5 MW

does not prove that the implementation actually prevents consumption above 5 MW.

75. Control Failure

Control Failure exists where the Access Control cannot reliably enforce the governed state.

Failure may be:

technical; physical; procedural; configuration-related; identity-related; communication-related; operational.

76. Fail-Open Condition

Some control failures may permit Resource Access despite loss of control.

This is a:

Fail-Open condition.

Its acceptability depends upon the Resource context and competent governance.

77. Fail-Closed Condition

Some control failures may prevent Resource Access.

This is a:

Fail-Closed condition.

Fail-closed behavior may protect authority boundaries but may create operational consequences for Critical Resource Dependencies.

78. Failure Behavior Governance

RACM should identify material expected control behavior during failure where relevant.

It does not impose one universal fail-open or fail-closed rule.

79. Manual Override

Some Resource Access Controls may support manual override.

Override capability should remain governed.

80. Override Boundary

Technical Override Capability ≠ Override Authority.

The existence of an override mechanism does not establish permission to use it.

81. Override Evidence

Where an override materially changes Resource Access, evidence should preserve where relevant:

actor; authority; reason; time; scope; duration; resulting control state.

82. Automated Control

Resource Access Controls may operate automatically.

Examples include:

compute quota enforcement; electricity load limiting; network rate limiting; water flow control; storage quota enforcement.

83. Automated Control Boundary

Automation executes the governed control logic.

It does not independently create Resource Access authority.

Automation ≠ Authority.

84. Autonomous Systems

An autonomous system may exercise Resource Access only within the Access Control boundaries legitimately established for it.

Its ability to discover alternative technical paths must not be treated as authority to bypass the governed Access boundary.

85. Alternative Technical Path

Where an actor can access the same Resource through multiple technical paths, RACM should consider whether the control boundary covers all materially relevant paths.

86. Control Path Completeness

A Resource Access Control is incomplete where a materially equivalent uncontrolled path permits the actor to bypass the governed restriction.

87. Control Bypass

Control Bypass exists where Resource Access occurs through a path that circumvents the intended Access Control.

88. Bypass Detection

Where material, RACM should support detection of:

alternate connection; credential misuse; control override; uncontrolled Resource Source; parallel infrastructure; configuration bypass; other Access path.

89. Identity-Control Integrity

Where controls rely on actor identity, identity binding must remain sufficiently reliable for the Resource context.

A valid authorization applied to the wrong actor is not valid control implementation.

90. Shared Credential Boundary

Where shared credentials prevent sufficient attribution of Resource Access, the control may be inadequate for contexts requiring actor-level governance.

91. Control Evidence

RACM should preserve evidence sufficient to establish the relevant Control State.

Evidence may include:

configuration records; permission records; control policies; activation logs; meter settings; quota records; control telemetry; restriction records; suspension records; revocation propagation records; verification results.

92. Evidence Provenance

Material control evidence should preserve where relevant:

source; control identifier; Resource; actor; time; version; configuration; authority reference.

93. Evidence Freshness

A historical control configuration does not prove the current control state.

Historical Configuration ≠ Current Control State.

94. Evidence Sufficiency

Control evidence is sufficient when it supports the determination required for the relevant Access Control governance purpose.

95. Control Uncertainty

Uncertainty may concern:

control configuration; control activation; actor binding; Resource binding; actual enforcement; synchronization; override status; control failure; actual Resource Access.

96. Uncertainty Propagation

Material uncertainty about Access Control effectiveness should remain visible to Resource Access Governance.

RACM should not represent control as effective merely because a configuration record exists.

97. Control Conflict

Control Conflict exists where materially incompatible instructions or control states affect the same Resource Access relationship.

Example:

Governed Authorization — Suspended

while:

Technical Control — Active

creates a material conflict requiring resolution.

98. Conflict Resolution Logic

Canonical logic:

Control Conflict → Governed Access State Check → Authority Check → Control Configuration Check → Current Operational State Check → Evidence Check → Correction / Escalation → Control Reverification

99. Control Traceability

A Resource Access Control should remain traceable through:

Actual Control State → Control Configuration → Resource Access Authorization → Access Scope → Access Subject → Resource → Authority Evidence.

100. Control Explainability

A governed control should be able to explain materially:

who is controlled; which Resource is controlled; which authorization it implements; what Access is permitted; what Access is restricted; which limits apply; when the control applies; what conditions activate or terminate it.

101. Control Auditability

Where required, changes should remain reconstructable across:

creation; activation; modification; restriction; suspension; override; revocation; expiration; failure; restoration.

102. Control Versioning

Material changes to an Access Control should create a new governed version where required for traceability.

103. Reassessment

RACM should reassess the relevant control whenever a material change could cause the control to diverge from the governed Access State.

104. Reassessment Triggers

Triggers may include:

Access authorization change; scope change; quantity limit change; capacity limit change; rate limit change; time-boundary change; location change; Resource Source change; restriction; suspension; revocation; expiration; technical-system change; control failure; override; detected bypass; new operational evidence.

105. Targeted Reassessment

Only the affected control dimensions need to be reassessed where the remainder of the control remains valid.

116. Failure Conditions

RACM should not be considered sufficiently completed where:

technical permission is treated as governance authority; Control Scope exceeds authorized scope; actor identity is materially mismatched; Resource identity is materially mismatched;

Resource Source restriction is ignored; quantity limits are not enforced where required; capacity limits are not enforced where required; rate limits are not enforced where required; expired authorization remains technically active; revoked authorization remains technically active; suspended Access remains usable without legitimate exception; temporary Access becomes persistent unintentionally; conditional Access is enforced as unconditional; override capability is treated as override authority; material bypass paths are ignored; control configuration is assumed to prove control effectiveness; control failure is hidden; material Control Drift is ignored; material Access Drift is ignored; historical configuration is represented as current control state; automation is treated as authority; Access Control is treated as Allocation authority.

117. Use Case 1 — AI Data Center GPU Access Control

An AI workload has been legitimately authorized to access:

256 GPUs

for:

model training

during:

a defined 12-hour operating window.

RACM translates the authorization into operational controls.

The Resource Access Control Profile may establish:

Access Subject — Defined AI workload

Resource — GPU Compute Capacity

Capacity Limit — 256 GPUs

Temporal Boundary — 12 hours

Control Mechanism — Compute Scheduler / Resource Quota

Control State — Active

The scheduler technically supports allocation of 512 GPUs.

That technical capability does not expand the governed authorization.

Technical Capacity = 512 GPUs

does not change:

Authorized Access = maximum 256 GPUs.

If the authorization expires after 12 hours but the scheduler continues permitting the workload to occupy the GPUs, RACM identifies:

Access Drift.

The control must then be corrected or legitimately reauthorized.

118. Use Case 2 — Regional Water Access Control

An industrial facility possesses legitimate authorization to access a regional water system within:

defined flow limits; defined daily quantity; defined delivery point; defined operating period.

RACM may translate those limits into:

metering controls; flow restrictions; valve controls; operational monitoring; automated or manual restriction mechanisms.

During a governed restriction period, the authorized flow limit is reduced.

RACM updates the corresponding control.

If the physical valve or digital control remains configured at the previous higher limit, the implementation no longer matches the governed Access State.

RACM identifies:

Control Drift

and requires correction or escalation.

The module enforces the Resource Access boundary.

It does not determine whether the industrial facility should receive higher or lower Resource Priority than households, agriculture, or essential services.

120. Cross-Architecture Boundary

RACM may consume:

RAEM — Resource Access Eligibility evidence.

RAGS — governed Resource Access authorization and Access State.

RACS — Resource Availability and practical accessibility context.

RDGS — Resource Demand context.

RDCS — Resource Dependency and Criticality context.

RPAS — Resource Allocation decisions where RACM is used to enforce allocated limits.

ORA™ — evidence of actual operational Resource Access.

GOA™ — authority and delegation evidence where relevant.

OBIDENITY® — identity, authority, permission, and provenance evidence where relevant.

AGI™ / ASGA™ — agent or autonomous-system permission and authority boundaries where relevant.

SIMULOS® — simulated Access Control failure or restriction evidence.

RACM does not absorb these governed mechanisms.

121. Cross-Architecture Mechanism Principle

An operational mechanism may produce inputs for multiple governance architectures, but it belongs only to the architecture whose governed domain includes that mechanism itself. Other architectures govern only its domain- specific relevance or consequences.

Identity mechanisms may establish who is exercising Access.

Allocation mechanisms may determine the Resource quantity to be provided.

Technical systems may enforce the resulting limit.

Operational Reality may reveal whether the control works.

RACM governs how those legitimate Access conditions are translated into and maintained as Resource Access Controls without taking ownership of the upstream or downstream mechanisms.

122. Canonical Boundary

RACM governs how a legitimate Resource Access authorization is translated into operational Resource Access Controls and how those controls are activated, bounded, restricted, suspended, revoked, expired, verified, synchronized, and reassessed so that actual Resource Access remains aligned with the governed Access State.

RACM does not determine Resource Access eligibility, create Access Authority, determine Resource Priority, allocate Resource capacity, govern Resource Consumption efficiency, determine Scarcity response, or establish long-term Resource Sustainability.

Its principal governed output is the Resource Access Control Profile .

123. Canonical Closing Statement

Permission that exists only on paper does not control a Resource, and technical access that exceeds permission does not become legitimate merely because the system allows it.

RACM connects governance to execution — translating authorized Resource Access into enforceable controls and continuously preserving the boundary between what an actor can technically access and what it is legitimately permitted to access.
