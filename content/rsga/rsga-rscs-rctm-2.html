1. Canonical Definition

RCTM — Resource Constraint Type Module governs how the specific type or combination of types of Resource Constraint affecting a defined Resource or Resource capacity is identified, distinguished, classified, evidenced, attributed to an operational constraint mechanism, related to other simultaneous constraints, monitored, and reassessed.

RCTM determines how a Resource is constrained .

It distinguishes constraints affecting:

quantity; capacity; rate; time; location; Source; accessibility; quality; delivery; infrastructure; regeneration; dependency; or multiple interacting Resource conditions.

Its foundational distinctions are:

Resource Constraint ≠ Resource Scarcity.

Constraint Type ≠ Constraint Severity.

Observed Resource Limitation ≠ Proven Constraint Mechanism.

One Scarcity State ≠ One Constraint Type by definition.

2. Operational Role

RSSM determines whether the governed Resource is in a Scarcity State relative to the applicable legitimate Resource requirement.

RCTM determines the form of Resource Constraint responsible for, contributing to, or otherwise materially affecting the Resource condition.

Its role is to transform:

**observed Resource limitation

Resource-state evidence operational context causal evidence**

into:

a governed Resource Constraint Type classification.

RCTM prevents different Resource problems from being collapsed into the generic statement:

“There is not enough Resource.”

The Resource may instead be constrained because:

not enough total quantity exists; capacity is saturated; the Resource cannot be delivered quickly enough; the Resource exists at the wrong time; the Resource exists at the wrong location; a required Source is unavailable; Access is restricted; Resource quality is inadequate; delivery infrastructure is constrained; regeneration is insufficient; another Resource dependency has failed; or several mechanisms operate simultaneously.

3. Operational Question

What type or combination of Resource Constraints is materially affecting the governed Resource, through which evidenced operational mechanisms, within which Source, location, time, capacity, quality, accessibility, delivery, infrastructure, regeneration, or dependency conditions, and with what confidence can those Constraint Types be established?

4. Position in RSCS Governance

Canonical progression:

Governed Resource State → Legitimate Resource Requirement → Applicable Resource Capacity → Resource Sufficiency Comparison → Resource Scarcity State → Constraint Type Identification → Constraint Mechanism Attribution → Constraint Interaction → Constraint Severity Evaluation → Scarcity Response / Monitoring → Resolution Assessment → Reassessment

RCTM governs:

Observed Resource Limitation → Resource Constraint Type

and:

Resource Constraint Evidence → Constraint Mechanism Classification

5. Governed Space

RCTM governs:

Resource Constraint Type Governance

This governed space concerns the identification, differentiation, classification, and evidence of the mechanisms through which Resource availability, usability, accessibility, capacity, quality, rate, location, timing, Source, delivery, regeneration, or dependent Resource conditions become constrained.

6. Governed Object

The primary Governed Object is:

A Resource Constraint Type classification associated with a defined Resource, Resource capacity, operational limitation, Source, location, time horizon, and evidenced Constraint mechanism.

Canonical relationship:

**Resource Limitation

Resource Context Constraint Evidence → Constraint Mechanism Identification → Constraint Type Classification → Constraint Interaction State**

7. Scope

RCTM governs:

Constraint Type identification; Constraint mechanism identification; quantity constraints; capacity constraints; rate constraints; temporal constraints; location constraints; Source constraints; accessibility constraints; quality constraints; delivery constraints; infrastructure constraints; regenerative constraints; dependency-induced constraints; cross-Resource constraints; single-mechanism constraints; multi-mechanism constraints; primary constraints; secondary constraints; direct constraints; indirect constraints; constraint interaction; constraint accumulation; constraint propagation relevance; constraint attribution; causal evidence; constraint-type evidence; constraint-type uncertainty;

constraint-type conflict; constraint-type transition; constraint-type monitoring; constraint-type reassessment; traceability; versioning.

RCTM does not independently:

determine Resource Demand; determine Resource Dependency or Criticality; grant Resource Access; determine Resource Priority; allocate Resources; measure actual Resource Consumption; determine the Scarcity State itself; determine complete Constraint Severity; authorize Resource intervention; govern Resource Recovery; authorize substitution; determine resilience; determine long-term Sustainability; determine Value; determine Harm; determine Liability.

8. Resource Constraint Type

A Resource Constraint Type represents the governed classification of the mechanism through which a Resource or Resource capacity is materially limited.

Constraint Type answers:

How is the Resource constrained?

It does not by itself answer:

How scarce is the Resource?

or:

How severe is the consequence?

9. Constraint-Type Principle

Constraint Type ≠ Scarcity State.

A Resource may experience an active constraint while remaining sufficient relative to legitimate Resource requirements.

10. Constraint-Type and Severity Principle

Constraint Type ≠ Constraint Severity.

The same Constraint Type may be minor in one context and critical in another.

11. Constraint Mechanism

A Constraint mechanism is the operational process or condition through which the Resource limitation arises.

Examples include:

reduced supply; capacity saturation; throughput limitation; Source interruption; transport failure; infrastructure failure; quality degradation; regenerative deficit; Access restriction; dependent Resource failure.

12. Mechanism Principle

Observed Resource Limitation ≠ Proven Constraint Mechanism.

Evidence must support the mechanism attribution.

14. Quantity Constraint

A Quantity Constraint exists where the amount of Resource relevant to the governed context is materially limited.

The limitation may concern:

physical quantity; energy quantity; material quantity;

data quantity; Resource stock; other Resource-specific quantity.

15. Quantity-Constraint Boundary

Low Resource Quantity ≠ Quantity Constraint by itself.

The quantity must be materially limited relative to the applicable Resource context or requirement.

16. Quantity Constraint and Scarcity

A Quantity Constraint may contribute to Scarcity.

However:

Quantity Constraint ≠ Scarcity automatically.

Remaining quantity may still be sufficient.

17. Capacity Constraint

A Capacity Constraint exists where the ability of a Resource system to provide, process, store, transmit, convert, or otherwise support Resource use is materially limited.

Examples include:

compute capacity; grid capacity; storage capacity; cooling capacity; processing capacity; transport capacity; treatment capacity.

18. Capacity Principle

Resource Existence ≠ Sufficient Resource Capacity.

19. Installed-Capacity Boundary

Installed or nominal capacity may exceed capacity actually usable under current conditions.

Installed Capacity ≠ Usable Capacity.

20. Capacity-Saturation Constraint

A Capacity-Saturation Constraint exists where applicable Resource-system capacity approaches or reaches its operational limit.

21. Saturation Principle

High Utilization ≠ Capacity Constraint by definition.

A Constraint exists only where the Resource condition becomes materially limiting.

22. Rate Constraint

A Rate Constraint exists where Resource quantity may be sufficient overall but cannot be supplied, processed, transmitted, withdrawn, consumed, or otherwise made available at the required rate.

23. Rate Principle

Sufficient Total Resource Quantity ≠ Sufficient Resource Rate.

24. Peak-Rate Constraint

A Resource may become constrained during peak intervals while remaining sufficient on average.

Average Resource Sufficiency ≠ Peak Resource Sufficiency.

25. Temporal Constraint

A Temporal Constraint exists where Resource availability or capacity is insufficient during the time interval in which it is required.

26. Temporal Principle

Resource Available Later ≠ Resource Available When Required.

27. Temporal-Mismatch Constraint

A Resource may exist in sufficient total quantity but be temporally misaligned with the relevant requirement.

28. Temporal Boundary

Long-Term Resource Sufficiency ≠ Short-Term Resource Sufficiency.

29. Location Constraint

A Location Constraint exists where Resource availability or capacity is insufficient at the location where it is required despite sufficient Resource conditions elsewhere.

30. Location Principle

Resource Availability Somewhere ≠ Resource Availability Where Required.

31. Spatial-Mismatch Constraint

A Spatial-Mismatch Constraint exists where the Resource and Resource requirement are geographically or operationally separated in a way that materially limits Resource use.

32. Source Constraint

A Source Constraint exists where a specific Resource Source becomes materially limited.

33. Source Principle

Constraint of Source A ≠ Constraint of Every Source of the Same Resource Type.

34. Source-Specific Scarcity Boundary

A Source may be constrained while alternative Sources remain available.

Whether those Sources can substitute for the constrained Source remains a separate governance question.

Alternative Source Availability ≠ Automatic Substitutability.

35. Accessibility Constraint

An Accessibility Constraint exists where Resource capacity exists but cannot be accessed by the relevant participant, system, function, or location.

36. Accessibility Principle

Available Resource ≠ Accessible Resource.

37. Access-Governance Boundary

An Accessibility Constraint may result from:

physical conditions; technical conditions; infrastructure conditions; governed Access conditions; other operational conditions.

RCTM identifies the Constraint Type.

RAGS governs Resource Access authority and rights.

38. Quality Constraint

A Quality Constraint exists where Resource quantity is available but fails the quality required for the relevant Resource use.

39. Quality Principle

Sufficient Resource Quantity ≠ Sufficient Resource Quality.

40. Quality-Degradation Constraint

A Resource may transition into a constrained state because its usable quality deteriorates even when physical quantity remains unchanged.

41. Quality Boundary

Resource Presence ≠ Functional Resource Suitability.

42. Delivery Constraint

A Delivery Constraint exists where Resource supply exists but cannot be delivered to the relevant requirement with sufficient quantity, rate, timing, reliability, or other required delivery condition.

43. Delivery Principle

Resource Availability ≠ Resource Deliverability.

44. Delivery and Location

Delivery Constraints may create Localized Scarcity even where upstream Resource supply remains sufficient.

45. Infrastructure Constraint

An Infrastructure Constraint exists where infrastructure required for Resource access, transport, transmission, processing, storage, conversion, cooling, treatment, or delivery becomes materially limiting.

46. Infrastructure Examples

Infrastructure Constraints may include:

electricity transmission congestion; pipeline capacity limitation; port congestion; water-treatment limitation; cooling-system capacity; data-network saturation; storage limitation; transport-system failure.

47. Infrastructure Principle

Resource Supply ≠ Infrastructure Capacity.

48. Infrastructure-Failure Constraint

Infrastructure failure may create a Resource Constraint even when the underlying Resource remains abundant.

49. Regenerative Constraint

A Regenerative Constraint exists where a Resource's effective regeneration cannot sustain the relevant withdrawal, Consumption, or depletion pattern over the applicable time horizon.

50. Regenerative Principle

Renewable Resource ≠ Unconstrained Resource.

51. Regeneration-Rate Constraint

A Resource may regenerate while remaining constrained because:

Consumption Rate > Effective Regeneration Rate

over a materially relevant period.

52. Regeneration Boundary

Resource Regeneration ≠ Immediate Resource Availability.

53. Dependency-Induced Constraint

A Dependency-Induced Constraint exists where a Resource becomes constrained because another Resource, system, infrastructure, or capability upon which its availability or use depends becomes constrained.

54. Dependency Principle

Constraint in a Dependency ≠ Automatic Constraint in the Dependent Resource.

The operational dependency and resulting limitation must be evidenced.

55. Cross-Resource Constraint

A Cross-Resource Constraint exists where the constrained state of one Resource materially limits the availability, usability, accessibility, capacity, or delivery of another Resource.

Example:

Water Constraint → Cooling Constraint → Compute Capacity Constraint

56. Cross-Resource Principle

Resource Correlation ≠ Cross-Resource Constraint.

A material dependency mechanism must exist.

57. Direct Constraint

A Direct Constraint acts directly upon the governed Resource or its immediate capacity.

Examples:

reduced water quantity; GPU failure;

pipeline capacity reduction.

58. Indirect Constraint

An Indirect Constraint affects the governed Resource through another dependency or enabling condition.

Examples:

electricity constraint reducing water-treatment capacity; water constraint reducing data-center cooling capacity.

59. Directness Principle

Indirect Constraint ≠ Secondary Importance.

An indirect constraint may become the dominant limitation.

60. Primary Constraint

A Primary Constraint is the Constraint mechanism that currently exerts the dominant limiting effect within the defined Resource context.

61. Primary-Constraint Boundary

Primary Constraint ≠ Root Cause by definition.

The dominant current limitation may itself result from another upstream mechanism.

62. Secondary Constraint

A Secondary Constraint materially contributes to the Resource limitation without being the dominant current constraint.

63. Secondary-Constraint Principle

Secondary Constraint ≠ Immaterial Constraint.

64. Combined Constraint

A Combined Constraint exists where multiple Constraint Types jointly produce or materially intensify the constrained Resource condition.

65. Combined-Constraint Principle

One Resource Constraint State ≠ One Constraint Type by default.

66. Constraint Interaction

RCTM should identify material interactions among simultaneous Constraint Types.

Possible interaction forms include:

independent; additive; amplifying; cascading; conditional; sequential; mutually reinforcing.

67. Independent Constraints

Two constraints may affect the same Resource without materially influencing one another.

68. Additive Constraints

Multiple constraints may independently reduce Resource sufficiency and collectively create a larger Resource limitation.

69. Amplifying Constraints

One Constraint Type may increase the effect of another.

For example:

high temperature → reduced cooling efficiency → increased water requirement → stronger water Constraint.

70. Cascading Constraints

One Constraint may trigger another Constraint through a dependency chain.

71. Conditional Constraint

A Constraint may become active only when another condition is present.

72. Interaction Principle

Coexisting Constraints ≠ Interacting Constraints by default.

Interaction must be evidenced.

73. Constraint Accumulation

Multiple individually manageable constraints may collectively become materially limiting.

Individually Non-Critical Constraints ≠ Collectively Non-Critical Constraint State.

74. Constraint Attribution

RCTM should preserve the evidentiary basis connecting the observed Resource limitation with the classified Constraint Type.

75. Attribution Evidence

Constraint attribution may use:

Resource measurements; capacity measurements; Source records; infrastructure telemetry; quality measurements; Access records; delivery records; regeneration evidence; dependency evidence; operational event records; other governed evidence.

76. Attribution Principle

Temporal Correlation ≠ Constraint Causation.

77. Multi-Causal Attribution

Where several mechanisms contribute to the Resource limitation, RCTM should preserve each material mechanism rather than forcing a single-cause classification.

78. Causal Confidence

Constraint mechanism attribution should preserve uncertainty or confidence where appropriate.

79. Confidence Principle

High Classification Confidence ≠ High Constraint Severity.

Confidence concerns evidence.

Severity concerns governance significance.

80. Constraint-Type Evidence

Every material Constraint Type should preserve evidence sufficient to support the classification.

81. Evidence Provenance

Material Constraint evidence should remain traceable to its origin, applicable period, Resource context, and relevant measurement or observation.

82. Evidence Sufficiency

RCTM should determine whether evidence is sufficient for the asserted Constraint Type.

Observed Resource Limitation Without Sufficient Causal Evidence ≠ Confirmed Constraint Type.

83. Constraint Type Unknown

Constraint Type Unknown applies where a Resource limitation is observed but the mechanism cannot yet be sufficiently identified.

84. Unknown-Type Principle

Unknown Constraint Type ≠ No Constraint.

85. Constraint Type Conflicted

Constraint Type Conflicted applies where material evidence supports incompatible Constraint-mechanism classifications.

86. Conflict Principle

Conflicting Constraint Evidence ≠ Permission to Select the Most Convenient Mechanism.

87. Multiple Constraint Types

Where evidence supports multiple simultaneous Constraint Types, each should remain independently identifiable.

88. Multi-Type Principle

Multiple Constraint Types ≠ Duplicate Classification.

Distinct mechanisms should remain distinct even when they contribute to the same Scarcity State.

89. Constraint-Type Transition

The mechanism constraining a Resource may change over time.

For example:

Source Constraint → Delivery Constraint → Infrastructure Constraint

or:

Rate Constraint → Quantity Constraint

as conditions evolve.

90. Transition Principle

Same Scarcity State ≠ Same Constraint Type Over Time.

91. Constraint-Type Persistence

A Constraint Type may persist even when its magnitude or severity changes.

92. Constraint-Type Resolution

A specific Constraint Type may resolve while other Constraint Types remain active.

93. Resolution Principle

Resolution of One Constraint Type ≠ Resolution of Resource Scarcity.

94. Constraint Substitution

Removing one Constraint may expose another previously non-binding Constraint.

For example:

grid capacity increased → cooling capacity becomes the new limiting constraint.

95. Binding Constraint

A Binding Constraint is the Constraint currently limiting Resource sufficiency or capacity within the applicable context.

96. Binding-Constraint Principle

Most Visible Constraint ≠ Binding Constraint by default.

97. Constraint Hierarchy

Where multiple constraints exist, RCTM may preserve relationships such as:

upstream; downstream; primary; secondary; binding; non-binding; enabling; dependent.

98. Hierarchy Boundary

Constraint Hierarchy ≠ Governance Priority Hierarchy.

RPAS governs Resource Priority.

99. Constraint Monitoring

Material Constraint Types should support monitoring appropriate to their operational characteristics.

100. Type-Specific Monitoring

Monitoring variables should reflect the Constraint Type.

Examples:

Quantity Constraint → Resource stock / flow

Capacity Constraint → usable capacity / occupancy

Rate Constraint → throughput / withdrawal / delivery rate

Temporal Constraint → availability window

Location Constraint → spatial availability

Source Constraint → Source condition

Quality Constraint → Resource quality indicators

Infrastructure Constraint → infrastructure capacity / state

Regenerative Constraint → withdrawal / regeneration relationship

101. Monitoring Principle

One Monitoring Variable ≠ Sufficient Evidence for Every Constraint Type.

102. Constraint-Type Reassessment

Constraint Type should be reassessed when materially relevant evidence changes.

Triggers may include:

Resource-state change; capacity change; Source change; infrastructure change; quality change; Access change; location change; regeneration change; dependency change; new operational evidence.

103. Historical Constraint Type

Historical Constraint Types may support recurrence and causal analysis.

However:

Historical Constraint Type ≠ Current Constraint Type.

104. Predicted Constraint Type

Prediction may identify a likely future Constraint Type.

However:

Predicted Constraint Type ≠ Observed Constraint Type.

PGA™ governs Prediction methodology where applicable.

105. Simulated Constraint Type

Simulation may test how Constraint Types could emerge under hypothetical conditions.

Simulated Constraint Type ≠ Operational Constraint Type.

SIMULOS® governs simulation.

106. Scarcity Boundary

RSSM determines the Resource Scarcity State.

RCTM determines the Constraint Type.

Constraint Type ≠ Scarcity State.

107. Severity Boundary

Constraint Type may provide an input to severity evaluation.

However:

Constraint Type ≠ Constraint Severity.

108. Demand Boundary

Demand may contribute to Resource constraint.

RCTM may identify Demand-related mechanisms where supported by evidence.

It does not govern Demand itself.

RDGS retains Resource Demand governance.

109. Dependency Boundary

Dependency evidence may explain a Dependency-Induced or Cross-Resource Constraint.

RDCS governs Resource Dependency and Criticality.

RCTM governs the Constraint mechanism affecting the Resource.

110. Access Boundary

Access conditions may create an Accessibility Constraint.

RAGS governs Access authority.

RCTM governs the resulting Constraint Type.

111. Allocation Boundary

Allocation may create or expose a localized Resource Constraint.

RCTM may classify the resulting mechanism.

It does not determine whether the Allocation should change.

112. Consumption Boundary

Consumption patterns may contribute to Quantity, Rate, Capacity, Regenerative, or other Constraint Types.

RCUS governs Consumption & Utilization.

RCTM governs the resulting Constraint classification.

113. Recovery Boundary

Recovery may reduce a Resource Constraint.

RCTM may observe the resulting Constraint-Type change.

It does not govern Recovery.

114. Substitution Boundary

An alternative Resource may bypass or reduce a Constraint.

RCTM does not determine whether substitution is acceptable.

RSFS governs substitution.

115. Resilience Boundary

Constraint Types may reveal vulnerabilities relevant to resilience.

RIRS governs Resource Interdependency & Resilience.

116. Sustainability Boundary

Persistent or regenerative Constraint Types may provide Sustainability evidence.

RCTM does not determine long-term Sustainability.

117. Value Boundary

The Value produced by Resource use does not determine Constraint Type.

High Value ≠ Different Constraint Mechanism.

118. Harm Boundary

A Constraint may contribute to Harm.

Resource Constraint ≠ Harm.

HAGA™ governs Harm.

119. Liability Boundary

A Constraint may become evidence relevant to Liability.

Resource Constraint ≠ Liability.

LIGA™ governs Liability.

120. Automation Boundary

Software may classify Resource Constraint Types.

However:

Automated Constraint Classification ≠ Governance Authority.

121. Intervention Boundary

Identification of a Constraint Type may support intervention analysis.

It does not authorize intervention.

Constraint Diagnosis ≠ Intervention Authority.

124. Minimum Implementation Framework

A minimum operational RCTM implementation should contain eight governed layers.

Layer 1 — Resource Limitation

Establish:

Resource; observed limitation; Source; location; time horizon; operational context.

Layer 2 — Constraint Evidence

Collect:

quantity; capacity; rate; time; location; Source; Access; quality; delivery; infrastructure; regeneration; dependency evidence.

Layer 3 — Mechanism Identification

Determine the operational mechanism producing or contributing to the Resource limitation.

Layer 4 — Constraint Type Classification

Classify applicable Constraint Types.

Layer 5 — Constraint Relationship

Determine where applicable:

direct / indirect; primary / secondary; binding / non-binding; single / combined.

Layer 6 — Interaction & Causality

Determine:

interaction; accumulation; causal evidence; uncertainty; conflict.

Layer 7 — Monitoring & Reassessment

Establish:

type-specific monitoring; transition triggers; reassessment triggers.

Layer 8 — Governed Output

Produce:

Resource Constraint Type Profile

132. Use Case 1 — AI Data Center Multi-Constraint Classification

An AI data center has sufficient installed GPU inventory for a planned workload.

Operational evidence shows:

GPU inventory — sufficient; electrical connection capacity — near maximum; cooling capacity — limited during peak temperature; water delivery rate — temporarily reduced; available annual water quantity — sufficient.

A generic shortage classification could incorrectly label the situation as a compute shortage or water shortage.

RCTM separates the mechanisms.

It identifies:

Compute Quantity Constraint — not established

Electrical Capacity Constraint — active

Cooling Infrastructure Constraint — active

Water Quantity Constraint — not established

Water Delivery / Rate Constraint — active

The cooling limitation is partly amplified by the reduced water-delivery rate.

RCTM therefore records a Combined Constraint with interacting Capacity, Infrastructure, and Rate Constraint Types.

It does not determine whether workloads should be stopped or reallocated.

Its output establishes how the Resource system is constrained , allowing the competent downstream governance mechanisms to act on the correct problem.

133. Use Case 2 — Regional Water Constraint Classification

A region reports declining water availability during a prolonged dry period.

Evidence shows:

reservoir quantity — reduced but still above minimum operational requirement; groundwater regeneration — materially below withdrawal rate; treatment capacity — sufficient; one municipality's pipeline — operating at maximum delivery capacity; another municipality retains sufficient supply.

RCTM does not classify the entire condition as a generic “water shortage.”

It identifies:

Regenerative Constraint — active

Delivery / Infrastructure Constraint — active in the affected municipality

Regional Quantity Constraint — not yet established

Location Constraint — active for the affected municipality

The Resource system therefore contains several distinct Constraint Types with different geographic and operational boundaries.

RCTM preserves those distinctions so that a regenerative Resource problem is not mistaken for a simple quantity shortage and a local delivery problem is not misrepresented as region-wide Resource absence.

135. Cross-Architecture Mechanism Principle

An operational mechanism may produce inputs for multiple governance architectures, but it belongs only to the architecture whose governed domain includes that mechanism itself. Other architectures govern only its domain- specific relevance or consequences.

RCTM governs the classification of how a Resource is constrained .

It does not govern the downstream decisions that the Constraint diagnosis may trigger.

136. Canonical Boundary

RCTM governs how the specific type or combination of types of Resource Constraint affecting a defined Resource or Resource capacity is identified, distinguished, classified, evidenced, attributed to an operational Constraint mechanism, related to simultaneous constraints, monitored, and reassessed across quantity, capacity, rate, time, location, Source, accessibility, quality, delivery, infrastructure, regeneration, dependency, and cross-Resource conditions.

It does not independently determine the Resource Scarcity State, complete Constraint Severity, Resource Demand, Resource Dependency or Criticality, Access authority, Priority or Allocation, Resource Consumption measurement, Recovery action, substitution authorization, resilience, long-term Sustainability, Value, Harm, Liability, or intervention authority.

Its principal governed output is the Resource Constraint Type Profile .

137. Canonical Closing Statement

A Resource shortage cannot be governed correctly until governance knows what is actually constrained. Insufficient quantity, saturated capacity, inadequate rate, wrong timing, wrong location, Source interruption, poor quality, inaccessible supply, infrastructure limitation, and regenerative deficit are not interchangeable problems.

RCTM turns the generic idea of Resource constraint into an evidenced operational diagnosis — identifying how the Resource is constrained, which mechanisms interact, which limitation is binding, and where uncertainty remains without converting diagnosis into Scarcity severity, Allocation authority, or intervention authority.
