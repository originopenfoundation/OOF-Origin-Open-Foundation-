1. Canonical Definition

The Capability Value Module (CVM) governs how intelligence-related capability created, improved, enabled, or preserved through an intelligence investment is identified, evidenced, bounded, evaluated, and represented as a potential source of Strategic Value.

CVM determines whether a Strategic Value Candidate has produced a real capability capable of supporting the future Value pathway identified through Strategic Value Identification Governance.

It distinguishes demonstrated capability from planned, claimed, theoretical, inaccessible, obsolete, or strategically irrelevant capability.

CVM evaluates whether the capability exists, what it enables, how mature and usable it is, what conditions constrain it, whether it can be reused or transferred, how dependent it is on specific resources or systems, and whether it has a defensible relationship to future Value.

It does not assume that greater technical capability automatically creates greater Strategic Value.

Its principal output is:

Governed Capability Value State

Its foundational distinction is:

Capability ≠ Strategic Value by default.

2. Operational Role

The operational role of CVM is:

to determine whether an intelligence investment has created or materially improved a real capability and whether that capability has a defensible relationship to future governed Value.

SVIM asks:

“Is there a legitimate Strategic Value candidate?”

CVM asks:

“What capability actually exists, and why does that capability matter?”

3. Position in the SVGS Internal Flow

The SVGS internal governance flow is:

Strategic Value Identification → Capability Value → Deferred Value → Strategic Milestone → Capital-at-Risk

CVM governs:

Capability Value

Its principal upstream input is:

Governed Strategic Value Identification State

Its principal output is:

Governed Capability Value State

That state proceeds to:

Deferred Value Governance

4. Central Operational Question

What intelligence-related capability actually exists or has materially improved, what can it reliably enable, and does that capability have a sufficiently evidenced relationship to future governed Value?

5. Capability Object

Every CVM assessment must identify the capability being evaluated.

The Capability Object may be:

a technical capability,

reasoning capability,

automation capability,

agentic capability,

research capability,

deployment capability,

integration capability,

data capability,

infrastructure capability,

governance capability,

organizational capability,

human-AI capability,

or another sufficiently defined intelligence-enabled capability.

6. Capability Boundary

The Capability Boundary defines:

what the capability can do,

what it cannot do,

under what conditions it operates,

what resources it requires,

and what dependencies constrain it.

7. Capability Existence

A capability exists for CVM purposes only where sufficient evidence demonstrates that the relevant function can actually be performed under defined conditions.

Therefore:

Planned Capability ≠ Existing Capability.

8. Claimed Capability

A Claimed Capability is a statement that an intelligence system or investment can perform a defined function.

A claim is not evidence.

9. Demonstrated Capability

A Demonstrated Capability has been evidenced through:

testing,

experimentation,

validated execution,

operational performance,

or another appropriate mechanism.

10. Theoretical Capability

A Theoretical Capability may be technically plausible without having been demonstrated.

It should remain distinguishable from demonstrated capability.

11. Available Capability

A capability may technically exist but remain unavailable because required:

models,

hardware,

data,

infrastructure,

permissions,

or expertise

cannot be accessed.

12. Accessible Capability

Accessible Capability can be practically invoked or deployed within the relevant environment.

13. Usable Capability

Usable Capability can perform its intended function with sufficient:

reliability,

quality,

availability,

and operational compatibility.

14. Operational Capability

Operational Capability is sufficiently integrated and reliable for the applicable operational environment.

15. Capability State Progression

A capability may progress through states such as:

Conceptual → Experimental → Demonstrated → Accessible → Usable → Operational → Scalable

These states are not automatic.

Each transition should be supported by appropriate evidence.

16. Capability Maturity

Capability Maturity represents how far the capability has progressed from theoretical possibility toward dependable operational use.

17. Experimental Capability

Experimental Capability has been demonstrated under limited or controlled conditions.

18. Prototype Capability

Prototype Capability exists in an implementation capable of demonstrating meaningful functionality but may not yet satisfy operational requirements.

19. Production Capability

Production Capability can operate within the applicable production environment under defined conditions.

20. Scalable Capability

Scalable Capability can expand across relevant volume, users, tasks, or environments without unacceptable degradation of the governed capability.

21. Capability Maturity ≠ Capability Value

A mature capability may have little strategic relevance.

An immature capability may have substantial future significance.

Therefore:

Capability Maturity ≠ Capability Value.

22. Capability Function

The Capability Function identifies what the capability actually enables.

It should be expressed in operationally meaningful terms.

23. Capability Output

The capability should identify the type of output or state it can produce.

24. Capability Requirement

The requirements necessary for the capability to function should be explicit where material.

25. Capability Conditions

Capability may depend on:

input quality,

context,

model configuration,

tools,

hardware,

human supervision,

environment,

or other execution conditions.

26. Capability Reliability

Capability Reliability concerns whether the capability can perform the relevant function consistently enough for its intended strategic use.

27. Capability Quality

Capability Quality concerns whether the produced output satisfies the relevant qualitative requirements.

28. Capability Consistency

A capability that appears only intermittently may have different Strategic Value from one that can be reproduced reliably.

29. Capability Reproducibility

A demonstrated capability should be reproducible where reproducibility is material to the future Value pathway.

30. Capability Robustness

Capability Robustness concerns whether the capability remains functional under relevant variation in:

inputs,

conditions,

scale,

or environment.

31. Capability Availability

Strategic Value may depend on whether the capability is available when required.

32. Capability Latency

A capability may exist technically but be too slow for its intended future use.

Latency may therefore constrain Capability Value.

33. Capability Precision

Some capabilities require defined levels of precision.

Greater precision does not automatically create greater Strategic Value.

34. Minimum Sufficient Capability

Minimum Sufficient Capability is the least capability level capable of supporting the relevant future Value pathway within applicable constraints.

35. Excess Capability

Capability beyond what the strategic pathway can meaningfully use does not automatically create additional Strategic Value.

Therefore:

More Capability ≠ More Strategic Value.

36. Capability Relevance

Capability Value requires a defensible relationship between:

Capability → Future Value Pathway

Technical capability without strategic relevance does not establish Capability Value.

37. Strategic Need Relationship

The capability should address the strategic need identified upstream.

38. Capability-to-Need Fit

Capability-to-Need Fit represents how directly the demonstrated capability addresses the identified strategic requirement.

39. Capability Misalignment

A technically strong capability may have weak Strategic Value where it does not materially address the relevant strategic need.

40. Capability Additionality

CVM should determine what capability exists because of the intelligence investment that did not exist, or did not exist at the same level, before it.

41. Capability Baseline

The Capability Baseline represents the relevant capability state before the intelligence investment or improvement.

42. Capability Increment

Capability Increment is the measurable or evidenced improvement relative to the Capability Baseline.

43. Existing Capability

Existing organizational capability should not be counted again as newly created Strategic Value.

44. Capability Duplication

Creating a second implementation of an already available capability may still have Strategic Value where it improves:

independence,

resilience,

availability,

cost,

or another relevant strategic property.

The additional Value must be identified.

45. Capability Substitution

A new capability may replace an existing capability.

Replacement alone does not establish Strategic Value unless the substitution creates a relevant improvement or strategic option.

46. Capability Expansion

Capability Expansion occurs where the intelligence investment enables materially broader:

tasks,

contexts,

users,

volumes,

or operational functions.

47. Capability Depth

Capability Depth represents improvement in the sophistication or difficulty of functions the capability can perform.

48. Capability Breadth

Capability Breadth represents the range of functions or contexts in which the capability can operate.

49. Breadth vs Value

Broad capability does not automatically create greater Strategic Value.

Strategic relevance remains required.

50. Capability Specialization

A narrow specialized capability may create substantial Strategic Value where it addresses a critical future need.

51. General Capability

A general capability may create Strategic Value through broad applicability.

Its Value should not be assumed merely from generality.

52. Capability Reusability

Capability Reusability concerns whether the capability can support multiple future uses without being rebuilt from the beginning.

53. Reuse Evidence

Potential reuse should be supported by evidence concerning:

technical compatibility,

operational applicability,

and required adaptation.

54. Reusable Capability Value

Reusable capability may increase Strategic Value because one investment can support multiple future Value pathways.

55. Reuse ≠ Double Counting

The same underlying capability should not be counted as independently created Value each time it is reused.

56. Capability Transferability

Capability Transferability concerns whether the capability can be applied to a materially different:

task,

system,

business function,

operational environment,

or technical configuration.

57. Transfer Requirement

Transfer may require:

adaptation,

retraining,

integration,

validation,

or additional infrastructure.

These requirements should remain visible.

58. Transferability Evidence

Claims of transferability should be supported through:

demonstration,

comparative testing,

validated reuse,

or another appropriate evidence mechanism.

59. Theoretical Transferability

A capability believed to be transferable but not yet tested should remain identified as such.

60. Portability

Portability concerns whether the capability can move between technical environments without losing essential function.

61. Model Portability

A capability may depend on one model or remain available across multiple models.

This may affect its Strategic Value.

62. Provider Portability

Capability tied to one provider may have different strategic characteristics from capability that can operate across providers.

63. Infrastructure Portability

A capability may depend on specific hardware, cloud infrastructure, edge systems, or other execution environments.

64. Data Portability Boundary

A capability may depend on data that cannot be transferred or reused across environments.

CVM identifies the capability implication without replacing data governance.

65. Capability Modularity

A modular capability may be easier to reuse, replace, integrate, or extend.

Modularity may contribute to Strategic Value where operationally relevant.

66. Capability Composability

Composability concerns whether the capability can combine with other capabilities to create broader future functionality.

67. Capability Interoperability

Interoperability may increase future strategic applicability.

Interoperability should be evidenced rather than assumed.

68. Capability Integration

A technically valid capability may require significant integration before future Value can be realized.

69. Integration Readiness

Integration Readiness represents whether the capability can be connected to the relevant operational environment.

70. Integration Burden

High integration burden may reduce the practical Strategic Value of an otherwise strong capability.

71. Deployment Readiness

Deployment Readiness concerns whether the capability is sufficiently prepared for the intended future deployment environment.

72. Deployment Gap

A Deployment Gap exists where a demonstrated capability cannot yet be used under the intended operational conditions.

73. Operational Readiness

Operational Readiness requires more than technical existence.

It may include:

reliability,

integration,

support,

governance,

monitoring,

and other necessary operating conditions.

74. Capability Accessibility

Strategic capability has limited practical Value where it cannot be accessed by the intended operational users or systems.

75. Human Accessibility

A capability may require specialized expertise to use effectively.

The required human capability should remain visible.

76. Capability Complexity

High operating complexity may reduce practical usability and increase dependency.

77. Capability Maintainability

Capability Value may depend on whether the capability can be maintained over the relevant strategic horizon.

ISS governs long-term sustainability.

CVM identifies the capability dependency.

78. Capability Evolvability

A capability capable of adapting to changing requirements may possess greater future applicability.

This should be evidenced where claimed.

79. Capability Extensibility

Extensibility concerns whether new functions can be added without replacing the underlying capability.

80. Capability Upgradeability

Upgradeability concerns whether the capability can improve as underlying intelligence technology evolves.

81. Capability Dependency

Capability Value may depend on specific:

models,

vendors,

hardware,

software,

tools,

data,

infrastructure,

people,

or external services.

82. Critical Capability Dependency

A Critical Capability Dependency is one whose loss would materially eliminate or degrade the capability.

83. Model Dependency

A capability tied exclusively to one model should preserve that dependency in its governed state.

84. Vendor Dependency

Provider-specific capability may create strategic dependency.

CVM identifies the dependency without governing long-term sustainability.

85. Hardware Dependency

Some capabilities require specialized hardware.

The requirement should remain visible where material.

86. Infrastructure Dependency

Capability may depend on:

cloud,

network,

storage,

compute,

edge infrastructure,

or another execution environment.

87. Tool Dependency

Agentic or workflow capability may depend on external tools or services.

88. Data Dependency

Capability may depend on specific data availability, quality, or access.

89. Human Dependency

Some intelligence capabilities remain dependent on:

specialist operation,

human review,

engineering,

domain expertise,

or governance.

90. Dependency Concentration

Capability dependent on a single critical component may have different strategic characteristics from a capability supported by multiple alternatives.

91. Capability Independence

Greater independence may create Strategic Value where it reduces a material strategic dependency.

Independence itself is not automatically Value.

92. Capability Resilience Boundary

A capability may remain available despite failure of a component.

CVM may identify this property where relevant.

Broader long-term resilience belongs to ISS and other competent governance spaces.

93. Capability Obsolescence

Capability may lose Strategic Value because:

better alternatives emerge,

technical requirements change,

the strategic need disappears,

or dependencies become unavailable.

94. Obsolescence Exposure

Capabilities in rapidly changing technical environments may require more frequent reassessment.

95. Capability Half-Life

Where useful, an implementation may estimate the period over which the capability is expected to remain strategically relevant.

This is not a universal VEGA™ metric.

96. Capability Preservation

Some capabilities require continued investment to remain usable.

Maintenance expenditure should remain visible for subsequent governance.

97. Knowledge Preservation

A capability may depend on retained:

technical knowledge,

documentation,

models,

configuration,

or human expertise.

98. Capability Loss

Capability may be lost through:

technology removal,

staff departure,

vendor withdrawal,

data loss,

infrastructure change,

or obsolescence.

99. Capability Recovery

Where capability can be restored after loss, the recovery requirement may affect its strategic significance.

100. Capability Evidence

CVM requires evidence appropriate to the capability claim.

Evidence may include:

tests,

benchmarks,

validated demonstrations,

operational records,

experimental results,

deployment records,

integration evidence,

or other relevant artifacts.

101. Capability Evidence Quality

Evidence quality should reflect:

relevance,

reproducibility,

environmental similarity,

independence,

recency,

and methodological quality.

102. Demonstration Evidence

A demonstration may establish that a capability can exist.

It may not establish that the capability is operationally reliable.

103. Benchmark Evidence

Benchmark performance may support capability evidence where the benchmark is relevant to the intended function.

Therefore:

Benchmark Performance ≠ Operational Capability by default.

104. Laboratory Evidence

Laboratory evidence may demonstrate capability under controlled conditions.

Its transfer to operational environments should not be assumed.

105. Operational Evidence

Operational evidence demonstrates capability under real or sufficiently representative operating conditions.

106. Reproduction Evidence

Independent or repeated reproduction strengthens evidence that the capability is stable rather than accidental.

107. Capability Evidence Gap

An Evidence Gap exists where a material capability claim lacks sufficient support.

108. Critical Capability Evidence Gap

A critical gap may prevent a capability from being represented as established.

109. Capability Uncertainty

Capability uncertainty should remain explicit where:

performance,

reliability,

transferability,

availability,

or future relevance

remains uncertain.

110. Capability Confidence

Capability confidence should correspond to the strength of the evidence.

111. Capability Value Pathway

Capability Value requires a pathway:

Demonstrated Capability → Relevant Future Use → Validated Future Value

Each connection should remain governable.

112. Capability-to-Use Relationship

A capability may exist without a credible future use.

Such capability should not automatically be assigned Strategic Value.

113. Use-to-Value Relationship

A future use may exist without producing material Value.

The Value pathway should therefore remain explicit.

114. Capability Value Additionality

CVM should identify the future Value potential created specifically by the capability increment.

115. Capability Value Evidence

Capability Value evidence should support both:

the existence of the capability

and

its relationship to future Value.

116. Capability Value Strength

Capability Value may strengthen where:

capability is demonstrated,

relevant,

mature,

reusable,

transferable,

accessible,

and connected to a credible future Value pathway.

117. Capability Value Weakness

Capability Value may weaken where the capability is:

theoretical,

fragile,

irrelevant,

inaccessible,

highly dependent,

non-transferable,

or rapidly becoming obsolete.

118. Capability Value Candidate

A demonstrated capability may still remain only a Capability Value Candidate where the future Value relationship is insufficiently evidenced.

119. Established Capability Value

Capability Value becomes established where sufficient evidence supports both capability existence and strategic relevance.

120. Conditional Capability Value

Capability Value may be conditional on:

integration,

deployment,

access,

additional development,

or another material dependency.

121. Capability Value Ceiling

The Strategic Value of a capability may be limited by the maximum future Value it can realistically enable.

122. Capability Value Saturation

Additional technical improvement may stop producing material additional Strategic Value once the relevant future need is already sufficiently supported.

123. Capability Overdevelopment

Investment may continue increasing capability beyond what the strategic pathway requires.

Therefore:

Capability Improvement ≠ Strategic Improvement by default.

124. Capability Underdevelopment

A strategically relevant capability may remain below the level required to support the future Value pathway.

125. Capability Gap

A Capability Gap is the difference between the demonstrated capability and the capability required for the future Value pathway.

126. Critical Capability Gap

A Critical Capability Gap prevents the capability from supporting the required future Value pathway.

127. Capability Development Path

Where a gap exists, CVM may identify the capability states required to close it.

It does not authorize the investment needed to do so.

128. Capability Optimization Opportunity

A Capability Optimization Opportunity exists where Strategic Value may be improved by:

increasing relevant capability,

reducing unnecessary capability,

improving reliability,

increasing transferability,

reducing critical dependency,

or improving operational usability.

129. Capability Optimization Hypothesis

An optimization hypothesis should identify:

the capability property being changed,

the expected strategic effect,

the evidence required,

and the Value pathway that should improve.

130. Capability Cost Boundary

The cost required to create or maintain capability remains economically relevant.

IES governs Intelligence Economy.

CVM does not rewrite that economic state.

131. Expensive Capability

High development cost does not eliminate Capability Value.

It may affect subsequent strategic and sustainability governance.

132. Cheap Capability

Low development cost does not establish Capability Value.

133. Capability ROI Boundary

Positive ROI does not establish Capability Value.

Negative immediate ROI does not eliminate Capability Value.

134. Productivity Boundary

High productivity does not automatically create Strategic Capability Value.

IPS governs productivity.

135. Computational Optimization Boundary

A computationally efficient capability may still lack strategic relevance.

COS governs Computational Optimization.

136. Resource Boundary

Resource-efficient capability may still have little Strategic Value.

RGS governs resource allocation and consumption.

137. Value Boundary

VGS governs Value.

CVM governs the strategic significance of capability as a potential future Value mechanism.

138. Deferred Value Boundary

CVM establishes whether capability exists and matters.

The next SVGS mechanism governs the Value expected to materialize later.

Therefore:

Capability Value ≠ Deferred Value.

139. Milestone Boundary

Capability evidence may later support Strategic Milestones.

CVM does not govern the complete milestone lifecycle.

140. Capital-at-Risk Boundary

Capability development may require significant capital.

CVM does not determine whether continued Capital-at-Risk is justified.

141. Sustainability Boundary

ISS governs whether the capability and its operating model can remain viable over the intended lifecycle.

142. Attribution Boundary

VAS governs detailed Value Attribution.

CVM should preserve uncertainty where capability results from multiple contributors.

143. Harm Boundary

HAGA™ governs Harm.

A strategically valuable capability does not make Harm acceptable.

144. Liability Boundary

LIGA™ governs Liability.

Capability Value does not determine Liability.

145. Authority Boundary

Capability does not create authority.

Therefore:

Capability ≠ Execution Authority.

146. Decision Boundary

CVM provides Strategic Value evidence.

It does not decide:

continuation,

scaling,

migration,

retirement,

or investment approval.

147. Capability Drift

Capability may change over time because of:

model changes,

system updates,

data changes,

infrastructure changes,

environmental change,

or operational degradation.

148. Capability Value Drift

Strategic Value may change even where the technical capability remains stable.

The future need or Value pathway may change.

149. Relevance Drift

A previously important capability may become strategically irrelevant.

150. Dependency Drift

Dependencies may become:

stronger,

weaker,

unavailable,

or replaceable.

151. Maturity Drift

Capability may advance or regress in maturity.

152. Evidence Drift

Evidence may become outdated where the capability or environment changes materially.

153. Capability Reassessment

Reassessment should occur where material changes affect:

capability function,

performance,

reliability,

maturity,

accessibility,

transferability,

dependencies,

future need,

or Value pathway.

154. Capability Value Integrity

CVM should resist:

capability hype,

benchmark substitution,

demo-to-production assumptions,

planned-capability inflation,

unused capability inflation,

technical novelty bias,

unsupported transferability,

unsupported scalability,

dependency concealment,

obsolescence neglect,

and treating greater capability as automatic greater Value.

The governing principle is:

A capability has Strategic Value only when what it can reliably enable has a defensible relationship to future Value.

The Governed Capability Value State determines whether the intelligence investment has created a real capability with a sufficiently evidenced relationship to future Value.

160. Minimum Implementation Framework

A conforming implementation of CVM must provide exactly the following six capabilities:

1. Capability Object & Boundary Governance

Capability to define the Capability Object, function, requirements, operating conditions, and relevant capability boundaries.

2. Capability Existence & Maturity Governance

Capability to distinguish claimed, theoretical, experimental, demonstrated, accessible, usable, operational, and scalable capability and establish the applicable maturity state.

3. Capability Relevance & Future Value Governance

Capability to connect demonstrated capability to the identified strategic need and future Value pathway, establish capability additionality, and identify relevant capability gaps.

4. Reusability, Transferability & Dependency Governance

Capability to evaluate reuse, transferability, portability, integration, critical dependencies, accessibility, and obsolescence exposure.

5. Capability Evidence & Integrity Governance

Capability to evaluate capability evidence, uncertainty, reproducibility, reliability, detect capability inflation, benchmark substitution, demo-to-production assumptions, unsupported scalability, and other integrity failures.

6. SVGS Deferred Value Handoff Governance

Capability to produce a Governed Capability Value State sufficiently explicit for subsequent Deferred Value governance.

164. Cross-Architecture Boundary

CVM governs Strategic Capability Value within SVGS.

SVIM governs Strategic Value Identification.

The subsequent SVGS mechanisms govern:

Deferred Value,

Strategic Milestones,

and Capital-at-Risk.

VGS governs Value.

IPS governs Intelligence Productivity.

RGS governs Resource Governance.

COS governs Computational Optimization.

IES governs Intelligence Economy.

ISS governs long-term Intelligence Sustainability.

VAS governs detailed Value Attribution.

DGS governs lifecycle Decision Governance.

VALIDOS™ may govern validation methodology.

ADIT® may govern evidence and auditability.

HAGA™ governs Harm.

LIGA™ governs Liability.

CVM may consume governed evidence from these spaces without replacing their methodologies.

166. Use Case 1 — Impressive AI Demo, No Operational Capability

An organization demonstrates an advanced AI system capable of completing a complex task under controlled conditions.

The demonstration receives strong internal attention and is described as a major strategic capability.

CVM evaluates whether the capability is:

reproducible,

reliable,

accessible,

integrable,

operationally usable,

and relevant to the identified future Value pathway.

The assessment finds that the demonstration depends on extensive manual preparation, specialized engineers, unstable tooling, and conditions unavailable in the intended production environment.

The technical capability may be real.

Its operational maturity and current Capability Value are more limited.

Demonstrated Capability ≠ Production Capability.

Capability Maturity ≠ Capability Value.

167. Use Case 2 — Research Creates a Reusable Capability

An intelligence research program develops a new capability that initially has no direct commercial return.

The capability has been independently reproduced, can operate across several relevant task classes, integrates with existing infrastructure, and can support multiple future operational applications.

CVM establishes:

the Capability Object,

Capability Increment,

maturity,

reliability,

reusability,

transferability,

dependencies,

and its relationship to the identified future Value pathways.

The capability can therefore possess legitimate Strategic Value even before the future applications generate realized Value.

A capability becomes strategically meaningful when what it enables can be connected to future Value.

168. Canonical Closing Statement

A capability is not strategically valuable merely because it exists.

It must do something that matters.

It must exist beyond a claim.

It must operate under identifiable conditions.

Its dependencies must be visible.

Its limits must be understood.

And what it enables must connect to a credible future Value pathway.

Planned Capability ≠ Existing Capability.

Demonstrated Capability ≠ Production Capability.

More Capability ≠ More Strategic Value.

Capability ≠ Strategic Value by default.

A capability has Strategic Value only when what it can reliably enable has a defensible relationship to future Value.

The strategic value of capability is not measured by how impressive the technology appears, but by what future Value that capability can credibly make possible.
