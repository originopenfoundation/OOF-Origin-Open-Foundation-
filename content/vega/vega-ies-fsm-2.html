1. Canonical Definition

The Failure Spend Module (FSM) governs how economic consumption attributable to unsuccessful intelligence execution is identified, bounded, measured, attributed, classified, aggregated, and represented before subsequent correction and Value relationships are evaluated.

FSM treats failed execution as economically real consumption even where it produces no validated operational outcome.

It establishes the methodological relationship between execution failure and the resources economically consumed before, during, and as a direct consequence of that failed attempt.

FSM prevents unsuccessful model calls, agent paths, tool operations, workflow stages, validations, retries, and other failed execution from disappearing from intelligence economics merely because they produced no usable result.

Its principal output is:

Governed Failure Spend State

Its foundational distinction is:

Failed Execution ≠ Zero Economic Cost.

2. Operational Role

The operational role of FSM is:

to determine how much governed economic consumption is attributable to execution that fails to produce the required task outcome.

ETCM establishes what ordinary task execution costs.

FSM identifies what intelligence economics spends on unsuccessful execution.

3. Position in the IES Internal Flow

The IES internal governance flow is:

Effective Task Cost → Failure Spend → Correction Cost → Intelligence ROI → Value-to-Cost

FSM governs:

Failure Spend

Its principal upstream input is:

Governed Effective Task Cost State

Its principal output is:

Governed Failure Spend State

That state proceeds to:

Correction Cost Governance

4. Central Operational Question

What economically relevant resources were consumed by intelligence execution that failed to produce the required governed outcome, and how much of that consumption constitutes Failure Spend?

5. Failure Spend Object

Every FSM assessment should identify the execution failure whose economic consequence is being evaluated.

The Failure Spend Object may be:

a model invocation,

task attempt,

agent action,

agent path,

workflow stage,

tool operation,

retrieval operation,

validation attempt,

transaction,

or another defined execution object.

6. Failure Definition

Failure exists where an execution does not satisfy the applicable required execution outcome or completion condition.

Failure should be determined through the relevant upstream governance or validation mechanism.

FSM does not independently redefine successful completion.

7. Failure Boundary

The Failure Boundary determines which execution activity belongs to the failed attempt.

The boundary should distinguish:

ordinary successful execution,

failed execution,

subsequent retry,

and subsequent correction.

8. Failure Start

Failure Spend may begin when economically relevant execution begins on an attempt that ultimately fails.

The failure need not be recognized at the moment the cost begins accumulating.

9. Failure Recognition

Failure Recognition is the point at which the execution is identified as unable or unlikely to satisfy the required outcome under the applicable criteria.

Earlier detection may reduce Failure Spend.

10. Failure Termination

Failure Termination is the point at which economically relevant execution associated with the failed attempt stops.

Delayed termination may increase Failure Spend.

11. Failed Attempt

A Failed Attempt is an execution attempt that consumes economically relevant resources without producing the required task outcome.

12. Failure Spend

Failure Spend is:

the economically relevant consumption attributable to execution that fails to produce the required governed outcome.

Failure Spend may include material cost associated with:

models,

compute,

orchestration,

agents,

tools,

retrieval,

infrastructure,

validation,

and other execution mechanisms participating in the failed path.

13. Failure Spend vs Effective Task Cost

ETCM establishes the ordinary task-cost baseline.

FSM isolates the economic burden attributable to unsuccessful execution.

Therefore:

Effective Task Cost ≠ Failure Spend.

14. Failure Spend vs Correction Cost

Failure Spend concerns resources consumed by unsuccessful execution.

Correction Cost concerns resources required to repair or complete an insufficient result.

Therefore:

Failure Spend ≠ Correction Cost.

15. Failure Spend vs Retry Cost

A failed attempt may trigger a retry.

The failed attempt and the subsequent retry should remain economically distinguishable.

16. Model Failure Spend

A model invocation that fails to satisfy its required execution role may generate Failure Spend.

Its economic consequence should not disappear because another model later succeeds.

17. Agent Failure Spend

An agent may consume:

model calls,

context,

tools,

compute,

and time

before failing to complete its assigned execution role.

That consumption may constitute Failure Spend.

18. Multi-Agent Failure Spend

A failed multi-agent path may involve economic consumption across several agents before failure becomes visible.

FSM should preserve the complete relevant failed path.

19. Tool Failure Spend

Tool execution may fail after consuming economically relevant resources.

Repeated failed tool calls may materially increase Failure Spend.

20. Retrieval Failure Spend

Retrieval may consume resources without obtaining the information required by the task.

Where economically material, unsuccessful retrieval belongs to Failure Spend.

21. Routing Failure Spend

Incorrect routing may send a task through an execution path incapable of satisfying the requirement.

Resources consumed before rerouting may constitute Failure Spend.

22. Validation Failure Spend

Validation may establish that an execution output is not acceptable.

The economic consumption of the failed underlying execution remains Failure Spend.

The validation mechanism itself should be treated according to its relevant economic role without double counting.

23. Timeout Failure

An execution may consume resources until a timeout condition terminates it.

The consumed economic resources remain Failure Spend.

24. Aborted Execution

An execution may be terminated before completion because it becomes:

invalid,

unnecessary,

infeasible,

or incapable of satisfying the requirement.

Consumed resources remain economically real.

25. Partial Failure

An execution may produce some useful intermediate work while failing to satisfy the complete required outcome.

FSM should distinguish complete economic waste from partially reusable output.

26. Complete Failure

Complete Failure exists where the failed execution produces no materially reusable output for the required task path.

27. Reusable Failure Output

A failed attempt may produce information or intermediate state that reduces subsequent execution cost.

FSM should preserve this distinction where material.

28. Non-Reusable Failure Output

Where the failed execution contributes nothing materially reusable, its economic consumption may be treated as fully attributable to the failed path.

29. Failure Classification

Failures may be classified according to the mechanism relevant to economic interpretation.

Possible classes include:

model failure,

routing failure,

tool failure,

retrieval failure,

orchestration failure,

resource failure,

timeout,

validation failure,

or another defined class.

30. Failure Cause vs Failure Cost

FSM may use an established failure cause as evidence.

Its primary governed object remains economic consumption.

Therefore:

Failure Cause ≠ Failure Spend.

31. Failure Attribution

Failure Spend should be attributed to the relevant failed execution object where evidence permits.

Attribution should not be assigned merely because a component participated in the workflow.

32. Shared Failure Cost

A failed execution may use shared infrastructure or services.

Their economic contribution should use a defensible allocation Basis.

33. Failure Cost Allocation Basis

Where shared costs are attributed to failure, the allocation methodology should remain explicit.

34. Measured Failure Spend

Measured Failure Spend is directly supported by sufficiently reliable economic evidence.

35. Estimated Failure Spend

Where direct measurement is unavailable, Failure Spend may be estimated using a documented Basis.

Estimated values should remain distinguishable from measured values.

36. Failure Spend Evidence

Evidence may include:

execution logs,

billing records,

resource traces,

model usage,

agent traces,

tool calls,

runtime,

compute consumption,

infrastructure usage,

and validation records.

37. Failure Spend Completeness

FSM should identify whether material economic components of the failed path are represented.

38. Failure Spend Materiality

Individually small failures may appear economically negligible.

At sufficient volume, they may become material.

Therefore:

Small Failure Cost × Large Failure Volume = Potentially Material Failure Spend.

39. Failure Frequency

Failure Frequency represents how often a defined failure occurs within a relevant task population.

40. Failure Rate

Failure Rate may relate failed attempts to total comparable attempts.

Failure Rate alone does not establish economic significance.

41. Cost per Failure

Cost per Failure represents the economic burden associated with a defined failed execution.

42. Failure Volume

High-volume systems may accumulate substantial Failure Spend even when individual failures are inexpensive.

43. Aggregate Failure Spend

Aggregate Failure Spend represents the total governed economic burden of relevant failed execution across a defined population or period.

44. Failure Spend Distribution

Failure Spend may be concentrated in:

specific task classes,

models,

agents,

tools,

workflows,

or operating conditions.

Distribution analysis may identify economically important failure patterns.

45. Failure Spend Concentration

A small number of failure classes may account for a large share of total Failure Spend.

This can identify high-value optimization targets.

46. Routine Failure

Repeated failure under ordinary operating conditions may indicate persistent economic inefficiency.

47. Exceptional Failure

Rare failures may carry high individual cost while remaining economically limited at population level.

Frequency and cost should both remain visible.

48. High-Cost Failure

Some failures may consume substantial resources before termination.

These should remain distinguishable from low-cost early failures.

49. Early Failure

A failure detected early may consume fewer resources than the same failure detected later.

50. Late Failure

Late Failure occurs after substantial execution has already occurred.

Late detection may create greater Failure Spend.

51. Failure Detection Economics

Earlier reliable detection of an inevitable failure may reduce economic consumption.

FSM may identify this as an optimization opportunity.

52. Failure Termination Economics

Continuing execution after a failure state is sufficiently established may create avoidable Failure Spend.

53. Failure Continuation

Failure Continuation exists where execution continues despite sufficient evidence that the current path cannot satisfy the requirement.

54. Failure Stopping Condition

A governed execution may define conditions under which an unsuccessful path should terminate.

FSM evaluates the economic consequence of those conditions without replacing XGS execution governance.

55. Retry Trigger

Failure may trigger another execution attempt.

The trigger should remain identifiable where it materially affects economics.

56. Retry Necessity

A retry may be justified where the failure is:

transient,

recoverable,

or otherwise likely to succeed under a new attempt.

57. Unnecessary Retry

A retry may create additional Failure Spend where the underlying failure condition has not changed.

58. Repeated Retry

Repeated retries can transform a low-cost individual failure into substantial cumulative Failure Spend.

59. Retry Ceiling

A governed execution may establish a limit on repeated attempts.

FSM may evaluate the economic consequences of retry behavior.

It does not independently establish execution authority.

60. Retry Cascade

A failed execution may trigger multiple downstream attempts.

The complete cascade should remain economically visible.

61. Escalation After Failure

Failure may justify escalation to:

another model,

another tool,

another workflow,

or human intervention.

The failed path remains Failure Spend even where escalation later succeeds.

62. Model Escalation Economics

A lower-capability model may be inexpensive per call while generating repeated failures before escalation.

FSM keeps the cost of those failures visible.

63. Failure and Model Allocation

MAEM governs Model Allocation Efficiency.

FSM may identify economic consequences of model insufficiency.

Therefore:

Cheaper Model ≠ Lower Failure Spend by default.

64. Failure and Compute Allocation

CAEM governs Compute Allocation Efficiency.

Insufficient compute may create failed execution.

FSM evaluates the economic consequence of the failure rather than determining compute sufficiency.

65. Failure and Hardware Execution

HEEM governs Hardware Execution Efficiency.

Hardware-related execution failure may generate Failure Spend.

66. Failure and Orchestration

OEM governs Orchestration Efficiency.

Poor routing, loops, coordination, or handoffs may create economically relevant failed execution.

FSM measures the resulting Failure Spend.

67. Failure and Cognitive Efficiency

CGEM governs Cognitive Efficiency.

Insufficient or excessive cognition may contribute to failure.

FSM governs the economic consequence of the failed execution.

68. Failure and Problem-Space Efficiency

PSEM governs Problem-Space Efficiency.

Poor problem formulation may create repeated execution failure.

FSM does not redefine the problem; it exposes its economic consequence.

69. Failure and Resource Governance

RGS may provide Consumption Traceability for failed execution.

FSM may translate relevant resource consumption into Failure Spend.

70. Failure and Productivity

Failed execution may consume resources without producing Validated Productive Output.

IPS governs productivity.

FSM governs the economic consumption associated with failure.

71. Failure and Value

A failed execution may produce no validated Value while still generating cost.

Therefore:

No Validated Value ≠ No Economic Consumption.

72. Failure Spend Ratio

Where appropriate, Failure Spend may be related to:

Total Governed Cost,

task volume,

execution volume,

or another defined economic denominator.

Formal cross-system metrics belong to the VEGA™ Reference Metrics Framework.

73. Failure Spend per Task

Aggregate Failure Spend may be normalized across task volume where appropriate.

74. Failure Spend per Validated Completion

Failure Spend may also be related to Validated Completions to reveal the failed execution economically required around successful outcomes.

75. Failure Spend Baseline

FSM should establish the current Failure Spend state before claiming improvement.

The baseline may identify:

failure classes,

frequency,

cost,

task classes,

models,

execution paths,

and time period.

76. Failure Baseline Integrity

The baseline should use sufficiently stable failure definitions and economic boundaries.

77. Alternative Failure Configuration

Alternative execution configurations may be compared to determine whether Failure Spend changes.

The required outcome and relevant operating conditions should remain sufficiently comparable.

78. Failure Spend Optimization Opportunity

An optimization opportunity exists where Failure Spend may be reduced without compromising the required validated outcome or applicable constraints.

79. Failure Spend Optimization Hypothesis

A proposed optimization should identify:

the failure class,

the expected reduction mechanism,

the expected economic effect,

and the outcome that must remain preserved.

80. Failure Prevention

Preventing an avoidable failure may eliminate the associated Failure Spend.

FSM evaluates the economic effect.

The mechanism preventing failure may belong to another governance domain.

81. Failure Avoidance vs Failure Hiding

A lower recorded failure rate is not an improvement if failures are merely:

reclassified,

excluded,

or shifted outside the measured boundary.

82. Failure Spend Displacement

Failure cost may move between:

models,

agents,

tools,

humans,

providers,

or workflow stages.

Displacement should not be represented as elimination.

83. Failure Spend Externalization

Failure-related economic burden may occur outside the observed system boundary.

Where materially related to the governed execution, it should remain visible.

84. Failure Spend Rebound

Reducing one failure class may create another economically significant failure mechanism.

Total Failure Spend should therefore be assessed where appropriate.

85. Failure Spend Regression

An optimization may reduce ordinary task cost while increasing Failure Spend.

This should remain visible to subsequent IES governance.

86. False Efficiency Through Failure Exclusion

A system may appear inexpensive if only successful executions are measured.

Therefore:

Successful Execution Cost Alone ≠ Complete Intelligence Economics.

87. Failure Spend and Cheap Attempts

Low attempt cost may encourage repeated execution.

If failure frequency rises, aggregate Failure Spend may offset the apparent savings.

88. Failure Spend and Premium Execution

A more expensive execution mechanism may reduce Failure Spend sufficiently to improve total economics.

FSM does not assume either cheaper or more expensive mechanisms are inherently superior.

89. Failure Spend Threshold

A governed implementation may establish a threshold at which Failure Spend requires investigation or intervention.

Threshold authority should remain explicit.

90. Failure Spend Alert State

Where Failure Spend materially exceeds an established threshold, FSM may produce an alert or optimization state.

91. Failure Spend Trend

Failure Spend may increase or decrease over time.

Trend analysis should distinguish:

volume change,

cost change,

and failure-rate change.

92. Failure Cost Drift

The economic cost of an equivalent failure may change due to:

pricing,

resource cost,

model configuration,

or execution architecture.

93. Failure Rate Drift

Failure frequency may change even where individual failure cost remains stable.

94. Failure Pattern Drift

The dominant failure mechanisms may change over time.

Historical optimization assumptions should therefore remain reassessable.

95. Failure Spend Reassessment

Reassessment should occur where material changes affect:

failure rate,

failure class,

model allocation,

orchestration,

compute,

hardware,

pricing,

task mix,

or execution conditions.

96. Failure Spend Versioning

Material changes to failure definitions, boundaries, or economic methodology should remain versioned where necessary.

97. Failure Spend Provenance

A Governed Failure Spend State should preserve sufficient provenance to identify:

Failure Spend Object,

failure definition,

failure class,

execution path,

cost components,

Cost Allocation Basis,

time period,

evidence,

uncertainty,

and version.

98. Failure Spend Uncertainty

Where Failure Spend cannot be established precisely, uncertainty should remain explicit.

A range or confidence state may be preferable to unsupported precision.

99. Failure Evidence Integrity

FSM should resist:

excluding failed model calls,

excluding failed agent paths,

excluding failed tool operations,

ignoring repeated retries,

measuring only successful executions,

changing failure definitions to reduce reported spend,

hiding failure cost in general overhead,

and shifting failed execution outside the measured boundary.

100. Failure Spend Integrity Principle

The governing principle is:

If execution consumes economic resources and fails, the cost does not disappear with the outcome.

101. Failure Spend and Correction Boundary

A failed attempt may be followed by correction.

FSM ends where the economic question changes from:

What was spent on the unsuccessful execution?

to:

What must now be spent to repair or complete the deficient outcome?

That subsequent economic state belongs to Correction Cost governance.

102. Failure Spend and Abandonment

Some failed tasks may be abandoned rather than retried or corrected.

The Failure Spend already incurred remains economically real.

103. Failure Spend and Successful Recovery

A later successful execution does not erase the cost of previous failed attempts.

Therefore:

Final Success ≠ Absence of Failure Spend.

104. Failure Spend and Partial Reuse

Where output from a failed attempt is reused in later successful execution, the economic state should distinguish:

consumed cost,

reusable contribution,

and non-recoverable Failure Spend

where the methodology supports that distinction.

105. Failure Spend Recovery

FSM does not assume that reusable intermediate output economically cancels the failed execution.

Any credited contribution should be supported by evidence.

106. Failure Spend State

108. Meaning of the Output

The Governed Failure Spend State establishes the economic burden attributable to failed intelligence execution.

It makes unsuccessful execution visible as a distinct economic state rather than allowing it to disappear inside successful- task averages or general operating cost.

It provides the failure-economics state required for subsequent Correction Cost governance.

109. Minimum Implementation Framework

A conforming implementation of FSM must provide exactly the following six capabilities:

1. Failure Object & Boundary Governance

Capability to identify the Failure Spend Object, failure definition, Failure Boundary, failure recognition, failure termination, and relevant failed execution path.

2. Failure Cost Identification Governance

Capability to identify economically relevant model, agent, tool, retrieval, orchestration, compute, infrastructure, validation, and other costs consumed by failed execution.

3. Failure Classification & Attribution Governance

Capability to classify failures, distinguish complete and partial failure, identify reusable output, attribute failure costs, and apply defensible allocation methods.

4. Failure Frequency & Aggregate Spend Governance

Capability to measure failure frequency, failure rate, Cost per Failure, Failure Volume, Aggregate Failure Spend, distribution, concentration, and trends.

5. Failure Spend Evidence & Integrity Governance

Capability to preserve evidence, uncertainty, baselines, drift, displacement, externalization, rebound, versioning, and provenance.

6. IES Correction Cost Handoff Governance

Capability to produce a Governed Failure Spend State sufficiently explicit for subsequent Correction Cost governance.

115. Use Case 1 — Cheap Model Fails Before Escalation

A company routes routine and moderately complex tasks to a low-cost model.

When the model fails, the task is escalated to a more capable model that usually succeeds.

The organization measures only the cost of the successful final model.

FSM identifies the unsuccessful first-stage executions and calculates their aggregate economic consumption.

At high task volume, the repeated low-cost failures create substantial Failure Spend.

The organization can now determine whether the routing strategy is actually reducing economic consumption.

Final Success ≠ Absence of Failure Spend.

116. Use Case 2 — Agent Repeats a Failed Tool Path

An autonomous workflow calls an external tool.

The tool fails because a required condition is unavailable.

The agent retries the same operation several times before terminating the path.

Each attempt consumes model execution, tool usage, compute, and runtime resources.

FSM identifies the failed path, separates the attempts, and establishes the resulting Failure Spend.

The final workflow failure is therefore not represented as a zero-output event with no economic consequence.

If execution consumes economic resources and fails, the cost does not disappear with the outcome.

117. Canonical Closing Statement

Failure has an economic footprint.

A failed model call consumes resources.

A failed agent path consumes resources.

A failed tool operation consumes resources.

And repeating an execution that cannot succeed consumes still more.

Those costs do not disappear because the final output was never produced.

Nor do they disappear when a later attempt eventually succeeds.

Failed Execution ≠ Zero Economic Cost.

Final Success ≠ Absence of Failure Spend.

Intelligence economics must account not only for what it costs to succeed, but also for what is spent on the paths that never should have reached the finish line.
