1. Canonical Definition

The Model Allocation Efficiency Module (MAEM) governs whether the model or model class assigned to an intelligence execution provides the minimum sufficient capability required to reliably produce the required validated outcome within the Governed Problem-Space, Cognitive, and Orchestration states and applicable governed constraints.

MAEM establishes the methodological relationship between task requirement and model capability.

It determines whether a model is insufficient, proportionate, excessive, conditionally appropriate, or unresolved relative to the execution it has been assigned to perform.

MAEM prevents model selection from being driven primarily by maximum available capability, benchmark prestige, parameter scale, provider preference, historical configuration, or the assumption that a more capable model necessarily produces a better operational result.

Its principal output is:

Governed Model Allocation Efficiency State

Its foundational distinction is:

Model Capability ≠ Model Requirement.

2. Operational Role

The operational role of MAEM is:

to allocate the minimum sufficient model capability capable of reliably satisfying the governed execution requirement.

PSEM establishes the problem.

CGEM establishes the required cognitive work.

OEM establishes the orchestration structure.

MAEM determines what model capability that execution actually requires.

3. Position in the COS Internal Flow

The COS internal governance flow is:

MAEM governs:

Its principal input is:

Its principal output is:

Governed Model Allocation Efficiency State

That state proceeds to:

CAEM — Compute Allocation Efficiency Module

4. Central Operational Question

What is the minimum sufficient model capability required to reliably perform the governed execution and produce the required validated outcome within applicable governed constraints?

5. Model Allocation Object

Every MAEM assessment should identify the execution object for which a model is being allocated.

The object may be:

a task,

task class,

workflow stage,

agent role,

tool-support operation,

validation operation,

or another governed execution component.

6. Model Requirement

The Model Requirement represents the capabilities a model must possess to perform the assigned execution reliably.

The requirement should derive from the execution.

The execution should not be expanded merely to exploit available model capability.

7. Model Capability

Model Capability represents the relevant operational abilities available from a model.

Capability may include, where applicable:

language understanding,

reasoning,

classification,

generation,

multimodal processing,

tool use,

planning,

code generation,

or another function.

Capability existence does not establish allocation necessity.

8. Capability-to-Requirement Relationship

MAEM compares required capability against available capability.

The objective is not maximum capability.

It is sufficient capability.

Therefore:

Available Capability ≠ Required Capability.

9. Model Sufficiency

A model is sufficient where it can reliably satisfy the assigned execution requirement within applicable constraints.

10. Model Insufficiency

A model is insufficient where it cannot reliably satisfy the required execution.

Insufficiency may appear through:

failure,

incorrect outputs,

unresolved tasks,

excessive retries,

correction,

or another material performance limitation.

11. Model Excess

Model Excess exists where materially greater model capability is allocated than the execution requires without sufficient additional governed benefit.

12. Minimum Sufficient Model

The Minimum Sufficient Model is:

the least capability-intensive model capable of reliably performing the assigned governed execution within applicable constraints.

It is not necessarily:

the smallest model,

the cheapest model,

the fastest model,

or the model with the fewest parameters.

13. Model Proportionality

Model capability should remain proportionate to:

task complexity,

cognitive requirement,

output requirement,

uncertainty,

tool requirement,

validation requirement,

and applicable constraints.

14. Model Oversizing

Model Oversizing occurs where the allocated model materially exceeds the capability required for the execution.

Therefore:

Larger Model ≠ Better Operational Outcome.

15. Model Undersizing

Model Undersizing occurs where the allocated model lacks sufficient capability to satisfy the execution reliably.

A smaller model is not efficient if it systematically creates:

failure,

retry,

correction,

or escalation.

16. Model Scale

Model scale may influence capability and resource consumption.

Scale alone does not establish suitability.

Therefore:

Model Scale ≠ Operational Fit.

17. Parameter Count

Parameter count may describe one technical property of a model.

It does not independently establish:

capability,

quality,

efficiency,

or suitability for the governed task.

18. Benchmark Performance

External benchmarks may provide useful capability evidence.

Benchmark performance does not automatically establish operational fit for a specific execution.

Therefore:

Benchmark Performance ≠ Task-Specific Sufficiency.

19. Model Reputation

Provider reputation, market position, or model prestige should not substitute for task-specific evidence.

20. Frontier Capability

Frontier capability may be justified where the Operational Requirement genuinely requires it.

It should not be the default allocation merely because it is available.

21. Specialized Model

A specialized model may provide sufficient capability for a narrow execution with lower resource demand than a general- purpose model.

MAEM remains neutral between specialized and general models.

22. General-Purpose Model

A general-purpose model may be appropriate where execution requires broad or variable capability.

Generality should correspond to operational need.

23. Small Model

A small model may be sufficient for:

routine,

bounded,

structured,

or specialized execution.

Its smaller size does not independently establish efficiency.

24. Advanced Model

An advanced model may be required where lower-capability models cannot reliably satisfy the execution.

Its use should follow evidence of unresolved need.

25. Reasoning Model

A reasoning-capable model may be appropriate where CGEM establishes a legitimate reasoning requirement.

Reasoning capability should not be allocated to tasks that do not require it merely because it exists.

26. Multimodal Model

A multimodal model may be required where the governed execution genuinely depends upon multiple input modalities.

Where the task uses only one modality, unused multimodal capability does not automatically provide operational benefit.

27. Model Modality Fit

Model modality should correspond to actual input and output requirements.

28. Tool-Capable Model

Tool-use capability may be necessary where OEM establishes tool interaction as part of the governed orchestration.

It should not independently justify selection of a more resource-intensive model.

29. Context Capability

A model may support large context capacity.

The existence of that capacity does not establish that the execution requires it.

Therefore:

Available Context Capacity ≠ Required Context Capacity.

30. Output Capability

Model output capability should correspond to the required operational output.

Capabilities irrelevant to the assigned execution should not determine allocation by default.

31. Model Role

In orchestrated execution, different models may serve different roles.

Examples include:

routing,

classification,

reasoning,

generation,

verification,

tool operation,

or exception handling.

Each role should have its own capability requirement.

32. Role-Specific Allocation

A workflow need not assign the same model to every execution stage.

Different roles may justify different model classes.

33. Uniform Model Allocation

Using one high-capability model for every workflow stage may simplify implementation while increasing resource consumption.

Therefore:

Operational Convenience ≠ Model Allocation Efficiency.

34. Task-Class Allocation

Tasks may be grouped into classes with similar model requirements.

This can support systematic model allocation.

35. Task Complexity

Model allocation should reflect task complexity where complexity materially affects required capability.

Complexity should be evidenced rather than assumed.

36. Routine Task Allocation

Routine tasks may justify lower-capability models where reliability remains sufficient.

37. Exceptional Task Allocation

Exceptional tasks may require greater model capability.

Higher-capability allocation can therefore be conditional rather than universal.

38. Static Model Allocation

Static allocation assigns a predefined model to a task class or execution stage.

This may be appropriate where requirements remain stable.

39. Dynamic Model Allocation

Dynamic allocation selects models according to current execution conditions.

The allocation mechanism should justify its own orchestration overhead.

40. Model Routing

Model Routing directs execution toward an appropriate model according to the governed requirement.

Routing may consider:

task class,

complexity,

uncertainty,

modality,

cognitive requirement,

or another legitimate factor.

41. Model Routing Basis

Every material routing decision should possess an identifiable Basis.

Routing should not depend solely on:

model popularity,

default provider configuration,

or maximum capability.

42. Model Escalation

Model Escalation assigns execution to a more capable model where the current model cannot reliably satisfy the requirement.

43. Escalation Trigger

Triggers may include:

failed completion,

unresolved uncertainty,

complexity,

insufficient capability,

or another evidenced condition.

44. Escalation Proportionality

Escalation should move only as far as necessary to resolve the unmet requirement.

Therefore:

Escalation ≠ Automatic Maximum Model Allocation.

45. Model De-Escalation

Model De-Escalation moves execution toward a less capability-intensive model where evidence demonstrates continued sufficiency.

46. De-Escalation Opportunity

A De-Escalation Opportunity exists where a lower-capability model may reliably satisfy the same execution requirement.

47. Escalation Ladder

Where useful, model allocation may follow a capability ladder:

Lower-Capability Model → Intermediate Model → Advanced Model → Specialized Escalation / Human where applicable

The exact ladder is implementation-specific.

48. Model Fallback

A fallback model may provide continuity where the preferred model is unavailable or unsuitable.

Fallback capability should still satisfy the minimum execution requirement.

49. Model Substitution

One model may substitute for another where sufficient capability equivalence exists for the governed task.

Substitution should be evidenced.

50. Capability Equivalence

Models do not need identical architecture or benchmark profiles to be operationally equivalent for a specific task.

The relevant question is whether both reliably satisfy the same governed requirement.

51. Task-Specific Equivalence

Task-specific equivalence should be established using relevant execution evidence.

Therefore:

General Model Equivalence ≠ Task-Specific Equivalence.

52. Model Allocation Baseline

MAEM should establish the existing model allocation before optimization.

The baseline may identify:

model,

task class,

role,

capability,

routing,

escalation,

resource consumption,

and outcome performance.

53. Allocation History

Historical allocation may provide useful evidence.

However:

Historical Model Choice ≠ Continuing Model Requirement.

54. Default Model

A default model may simplify operations.

Its default status should not prevent reassessment where task requirements differ materially.

55. Provider Default

A provider-selected default configuration may not correspond to the organization's minimum sufficient model requirement.

56. Model Availability

Temporary model availability may influence feasible allocation.

Availability does not redefine the underlying capability requirement.

57. Model Access Constraint

Access, geographic, contractual, security, technical, or other constraints may limit model options.

MAEM optimizes within the feasible set.

58. Constraint-Limited Model Allocation

Where the theoretically preferred model cannot be used because of a valid governed constraint, MAEM should identify the allocation as constraint-limited rather than treating the constraint as nonexistent.

59. Model Reliability

A model should reliably perform the assigned execution.

Average capability alone may not establish operational reliability.

60. Model Variability

Some models may exhibit variable performance across equivalent tasks.

Variability should be considered where it materially affects sufficiency.

61. Failure Rate Relationship

A lower-capability model may consume fewer resources per attempt but fail more often.

Complete allocation assessment should therefore consider failed execution.

62. Retry Relationship

Model insufficiency may create retries.

The computational effect of retries should remain part of the allocation assessment.

63. Correction Relationship

A lower-capability model may require additional machine or human correction.

That correction should not disappear from efficiency analysis.

64. Validation Relationship

Some models may require more intensive validation to reach the same governed confidence in the outcome.

The additional validation belongs to the complete execution effect.

65. Total Execution Effect

MAEM should evaluate model allocation within the complete execution rather than model invocation in isolation.

Therefore:

Lower Model Consumption ≠ Lower Total Execution Consumption by default.

66. Model-Induced Orchestration

A selected model may create additional orchestration requirements.

For example, insufficient capability may require:

additional agents,

tools,

verification,

or escalation.

OEM governs orchestration efficiency.

MAEM should account for its model-allocation consequence.

67. Model-Induced Context Demand

Different models may require different context structures or volumes to perform reliably.

Context consequences should remain visible.

68. Model-Induced Compute Demand

Different models may require materially different computational resources.

CAEM subsequently governs whether compute allocation to the selected model configuration is proportionate.

69. Model-Induced Hardware Demand

A model may constrain the hardware configurations capable of executing it.

HEEM subsequently governs Hardware Execution Efficiency.

70. Model Allocation and Cognitive Requirement

CGEM establishes the required cognitive work.

MAEM should allocate a model capable of satisfying that cognitive state without unnecessary capability excess.

71. Model Allocation and Orchestration

OEM establishes the required execution structure.

MAEM may allocate different models to different orchestration roles.

72. Model Allocation and Resources

RGS provides resource allocation and consumption evidence.

MAEM may use that evidence when comparing model configurations.

73. Model Allocation and Productivity

IPS governs productivity.

MAEM may use productivity evidence to determine whether additional model capability produces meaningful productive improvement.

Therefore:

Higher Model Capability ≠ Higher Productivity by default.

74. Model Allocation and Value

VGS governs Value.

A more capable model does not independently create greater Value.

Therefore:

Higher Model Capability ≠ Higher Value by default.

75. Model Allocation and Economics

IES governs execution economics.

MAEM establishes model-allocation efficiency rather than economic justification.

76. Model Allocation and Sustainability

ISS may use model-related resource evidence in long-term sustainability assessment.

MAEM does not govern sustainability independently.

77. Model Capability and Authority

A model's ability to perform an action does not create authority to perform it.

Therefore:

Model Capability ≠ Execution Authority.

78. Model Optimization and Permission

Selecting a computationally efficient model does not create permission for the underlying execution.

Therefore:

Model Optimization ≠ Permission.

79. Model Selection Evidence

Model allocation should be supported by evidence appropriate to the governed task.

Evidence may include:

controlled task evaluation,

validated completion,

failure rates,

retry rates,

correction requirements,

latency,

resource consumption,

or another relevant measure.

80. Representative Evaluation

Evaluation data should sufficiently represent the task class for which allocation is being determined.

A model performing well on unrelated tasks does not establish sufficiency.

81. Outcome Equivalence

Comparisons between models should preserve equivalent required outcomes.

A model is not more efficient merely because it produces a lower-quality result using fewer resources.

82. Model Comparison

Alternative models may be compared according to:

required capability,

validated outcome,

reliability,

resource consumption,

retry,

correction,

validation,

and execution consequences.

83. Model Allocation Optimization Hypothesis

A proposed allocation change should identify:

which model will change,

why current capability appears insufficient or excessive,

what execution effect is expected,

and which required outcome must remain preserved.

84. Alternative Model Configuration

An alternative may involve:

a different model,

different model class,

specialized model,

smaller model,

larger model,

or dynamic routing among multiple models.

85. Comparative Model Execution

Where appropriate, alternatives should be tested under sufficiently equivalent conditions.

The comparison should represent the real governed execution rather than isolated benchmark performance alone.

86. Allocation Improvement

An allocation improvement exists where a model configuration provides a superior capability-to-requirement relationship while preserving the required outcome and applicable constraints.

87. Model Allocation Regression

A lower-capability allocation may reduce per-call consumption while increasing:

failure,

retry,

correction,

validation,

latency,

or escalation.

Such regression should remain visible.

88. Model Allocation Rebound

Resource reductions from model de-escalation may create additional resource consumption elsewhere.

Therefore:

Smaller Model ≠ Lower Total Resource Consumption by default.

89. Capability Displacement

Removing capability from one model may move required work to:

another model,

agent,

tool,

or human.

Displacement should not be represented as elimination.

90. Model Externalization

A model may appear efficient because substantial processing occurs in external tools or services.

The relevant execution boundary should remain visible.

91. Model Allocation Uncertainty

Where evidence is insufficient to determine whether a model is excessive or insufficient, MAEM should preserve an unresolved state.

Therefore:

Suspected Oversizing ≠ Proven Model Excess.

92. Model Allocation State

A model allocation may be represented as:

Insufficient,

Minimum Sufficient,

Proportionate,

Excessive,

Conditionally Appropriate,

Constraint-Limited,

Escalation Required,

De-Escalation Candidate,

or Unresolved.

93. Allocation Threshold

Where useful, evidence may establish a threshold at which a model class becomes insufficient or greater capability becomes justified.

Thresholds should remain task-specific.

94. Capability Margin

A model may possess some capability margin beyond the minimum requirement.

A reasonable margin may support:

reliability,

variability,

or operational resilience.

Therefore:

Capability Margin ≠ Model Excess by default.

95. Excess Capability Margin

A margin becomes an optimization concern where materially greater capability produces no sufficient operational benefit relative to its additional resource consequences.

96. Model Saturation

Model Saturation occurs where greater model capability produces little or no material improvement in the required outcome.

97. Marginal Capability Benefit

MAEM may evaluate whether additional model capability produces sufficient incremental operational benefit.

98. Model Allocation Drift

Allocation Drift occurs where model capability changes over time without corresponding change in the Operational Requirement.

Examples include:

routine migration to larger models,

default-model upgrades,

or accumulated escalation.

99. Requirement Drift

The task itself may change.

A previously sufficient model may become insufficient, or a previously necessary advanced model may become excessive.

100. Model Evolution

Models improve over time.

A smaller or newer model may eventually satisfy requirements that previously required a larger model.

Allocation should therefore remain reassessable.

101. Model Deprecation

A model may become unavailable, unsupported, or inappropriate.

MAEM should support reassessment rather than treating historical allocation as permanent.

102. Model Allocation Reassessment

Reassessment should occur where:

task requirements change,

cognitive requirements change,

orchestration changes,

model capabilities change,

failure patterns change,

resource conditions change,

or new evidence becomes available.

103. Model Allocation Versioning

Material model-allocation changes should remain versioned where necessary for:

comparison,

traceability,

and optimization evidence.

104. Model Allocation Provenance

A Governed Model Allocation Efficiency State should preserve sufficient provenance to identify:

task requirement,

model requirement,

allocated model,

capability Basis,

comparison evidence,

constraints,

routing logic,

escalation conditions,

outcome evidence,

version,

and determination.

105. Model Allocation Integrity

MAEM should resist:

largest-model-by-default allocation,

benchmark-driven allocation without task evidence,

provider-default allocation without reassessment,

uniform model allocation across heterogeneous tasks,

unnecessary reasoning-model use,

unnecessary multimodal capability,

unnecessary context capability,

premature escalation,

ignoring retries and correction,

treating smaller models as inherently efficient,

and shifting required work elsewhere while claiming model optimization.

The governing principle is:

Allocate capability to the requirement — not the requirement to the capability.

108. Minimum Implementation Framework

A conforming implementation of MAEM must provide exactly the following six capabilities:

1. Model Requirement & Capability Governance

Capability to establish the Model Allocation Object, required capability, available model capability, sufficiency, insufficiency, and capability excess.

2. Model Proportionality & Role Governance

Capability to govern model scale, specialization, modality, context capability, tool capability, model roles, task classes, and minimum sufficient allocation.

3. Model Routing, Escalation & Substitution Governance

Capability to govern static and dynamic allocation, routing, escalation, de-escalation, fallback, substitution, and capability- equivalent alternatives.

4. Model Execution Consequence Governance

Capability to account for reliability, failure, retry, correction, validation, orchestration, context, compute, and hardware consequences of model allocation.

5. Model Allocation Evidence & Integrity Governance

Capability to establish baselines, compare alternative models, preserve outcome equivalence, detect regression, rebound, displacement, drift, uncertainty, and maintain versioning and provenance.

6. COS Compute Allocation Efficiency Handoff Governance

Capability to produce a Governed Model Allocation Efficiency State sufficiently explicit for subsequent Compute Allocation Efficiency governance.

114. Use Case 1 — Frontier Model Used for Routine Classification

An organization routes every incoming classification task to its most capable frontier model.

The tasks are bounded, repetitive, and supported by stable structured inputs.

MAEM evaluates the actual Model Requirement and compares task-specific performance across feasible model classes.

A smaller specialized model reliably produces the same required validated outcome for routine cases.

The frontier model remains available for exceptional cases requiring escalation.

The allocation therefore changes from universal maximum capability to requirement-based model routing.

Model Capability ≠ Model Requirement.

115. Use Case 2 — Smaller Model Appears Cheaper but Creates Retries

A company replaces an advanced model with a smaller model because the smaller model consumes fewer resources per invocation.

Initial compute consumption falls.

However, the smaller model produces more incomplete outputs, causing repeated retries, additional validation, tool calls, and human correction.

MAEM evaluates the complete execution consequence rather than the model invocation alone.

The smaller model is not classified as more efficient merely because its individual calls are cheaper.

Lower Model Consumption ≠ Lower Total Execution Consumption by default.

116. Canonical Closing Statement

A model should not receive a task because it is the most capable model available.

It should receive the task because its capability matches what the execution requires.

Too little capability creates failure, retry, correction, and escalation.

Too much capability can consume resources without improving the governed outcome.

The objective is therefore neither the smallest model nor the largest.

It is the minimum sufficient model for the execution being performed.

Model Capability ≠ Model Requirement.

Allocate capability to the requirement — not the requirement to the capability.

The strongest model-allocation system is not the one that uses the strongest model most often. It is the one that knows when stronger capability is actually necessary.
