1. Canonical Definition

The Problem-Space Efficiency Module (PSEM) governs whether an Operational Requirement has been formulated, bounded, decomposed, represented, and assigned to an intelligence mechanism at a level of complexity proportionate to the validated operational outcome required.

PSEM operates before model, compute, and hardware optimization.

It determines whether computational demand originates from genuine problem complexity or from avoidable complexity introduced by problem formulation, unnecessary scope, excessive input, inappropriate decomposition, redundant requirements, or premature assignment to a computationally complex intelligence mechanism.

PSEM prevents computational optimization from beginning with an execution configuration whose underlying problem is itself unnecessarily expensive to solve.

Its principal output is:

Governed Problem-Space Efficiency State

Its foundational distinction is:

Problem Complexity ≠ Required Computational Complexity.

2. Operational Role

The operational role of PSEM is:

to establish the minimum sufficient problem formulation that preserves the required validated operational outcome before downstream computational mechanisms are optimized.

A system should not optimize how efficiently it solves an unnecessarily complex problem before asking whether that complexity is required.

3. Position in the COS Internal Flow

The COS internal governance flow is:

Problem-Space Efficiency → Cognitive Efficiency → Orchestration Efficiency → Model Allocation Efficiency → Compute Allocation Efficiency → Hardware Execution Efficiency

PSEM governs:

Problem-Space Efficiency

Its principal output is:

Governed Problem-Space Efficiency State

That state proceeds to:

CGEM — Cognitive Efficiency Module

4. Central Operational Question

What is the minimum sufficient formulation of the problem that preserves the required validated operational outcome within applicable governed constraints?

5. Problem Object

Every PSEM assessment should identify the Problem Object being solved.

The Problem Object should be connected to a defined Operational Requirement rather than inferred solely from the capabilities of the available system.

6. Operational Requirement

Problem-space optimization begins with the Operational Requirement.

The requirement establishes what must be achieved.

Technology selection follows.

Therefore:

Available Intelligence ≠ Required Problem Formulation.

7. Required Outcome

The problem should be formulated around the required outcome.

Requirements unrelated to that outcome should not automatically become part of the computational problem.

8. Problem Boundary

The Problem Boundary establishes what belongs inside and outside the problem being assigned to the intelligence execution.

An unnecessarily broad boundary can create unnecessary computation before execution begins.

9. Boundary Sufficiency

A problem boundary should include everything materially necessary to satisfy the Operational Requirement.

Removing required information merely to reduce computational demand does not establish efficiency.

10. Boundary Excess

Boundary Excess exists where the problem includes material scope that is not necessary for the required outcome.

Therefore:

Broader Problem Scope ≠ Better Problem Definition.

11. Problem Scope

PSEM should establish the operational scope of the problem.

Scope may include:

objects,

events,

inputs,

conditions,

decisions,

time periods,

or other relevant dimensions.

12. Scope Necessity

Each material scope element should possess a defensible relationship to the required outcome.

Where no such relationship exists, it may represent avoidable problem-space complexity.

13. Scope Reduction

Problem scope may be reduced where excluded elements are unnecessary to satisfy the required outcome.

Scope reduction must preserve outcome sufficiency.

14. Problem Formulation

Problem Formulation determines how the Operational Requirement is translated into a solvable computational object.

Different formulations of the same requirement may create materially different computational demand.

15. Formulation Efficiency

A formulation is efficient where it captures the necessary operational problem without introducing avoidable computational complexity.

16. Formulation Excess

Formulation Excess exists where the representation of the problem makes execution materially more complex than the Operational Requirement requires.

17. Problem Representation

A problem may be represented through:

rules,

structured data,

mathematical relationships,

statistical variables,

natural language,

search spaces,

optimization objectives,

or another mechanism.

Representation choice may materially alter computational demand.

18. Representation Necessity

The richest available representation is not automatically necessary.

Therefore:

More Expressive Representation ≠ More Efficient Problem Representation.

19. Representation Simplification

Where a simpler representation preserves the required outcome, PSEM may identify it as a more efficient problem-space configuration.

20. Problem Decomposition

A complex problem may contain multiple subproblems with different computational requirements.

PSEM should support decomposition where this creates clearer and more proportionate execution.

21. Decomposition Object

Each decomposed problem component should have:

a defined purpose,

input,

required output,

and relationship to the complete Operational Requirement.

22. Decomposition Benefit

Decomposition may allow:

simple components to use simple mechanisms,

complex components to receive greater intelligence,

parallel handling,

specialized execution,

or selective escalation.

23. Decomposition Overhead

Decomposition itself may create:

coordination,

data-transfer,

state-management,

or orchestration overhead.

Therefore:

More Decomposition ≠ More Efficiency by default.

24. Excessive Decomposition

A problem can be fragmented so aggressively that coordination overhead exceeds the computational benefit of decomposition.

PSEM should preserve this possibility.

25. Problem Aggregation

Some problems may be more efficiently solved together where shared information or processing reduces duplicated work.

Aggregation should be evaluated against the operational requirement.

26. Excessive Aggregation

Combining unrelated problems may force the execution mechanism to process unnecessary complexity.

Therefore:

One Large Problem ≠ One Efficient Problem.

27. Problem Segmentation

Different task classes may justify separate problem paths.

Segmentation may support later routing toward different intelligence mechanisms.

28. Task Classification

Where useful, PSEM may classify problem instances according to:

complexity,

uncertainty,

required output,

known structure,

or another operationally relevant property.

29. Routine Problem State

A Routine Problem State exists where the problem is sufficiently predictable or structured to permit a low-complexity execution mechanism.

Routine does not mean unimportant.

30. Exceptional Problem State

An Exceptional Problem State exists where ordinary execution mechanisms are insufficient because of:

complexity,

uncertainty,

novelty,

or another material condition.

Such cases may justify greater intelligence.

31. Problem Complexity

Problem Complexity should be connected to the actual computational challenge presented by the Operational Requirement.

Complexity should not be inferred merely from domain prestige or perceived importance.

32. Necessary Complexity

Necessary Complexity is complexity that cannot be removed without materially compromising the required outcome or violating applicable constraints.

33. Artificial Complexity

Artificial Complexity is complexity introduced by the formulation or surrounding process rather than required by the underlying Operational Requirement.

34. Complexity Source

Where material, PSEM should identify whether complexity originates from:

the problem itself,

input structure,

scope,

representation,

dependencies,

uncertainty,

workflow design,

or another source.

35. Complexity Attribution

Understanding the source of complexity helps prevent unnecessary computational demand from being attributed automatically to the inherent difficulty of the task.

36. Input Necessity

Only inputs materially relevant to the required outcome should be treated as necessary problem inputs.

More input is not inherently better.

37. Input Relevance

PSEM may assess whether an input contributes meaningfully to solving the problem.

Irrelevant inputs can increase:

context,

processing,

reasoning,

or retrieval demand.

38. Input Redundancy

Multiple inputs may contain materially duplicated information.

Where duplication is unnecessary, it may represent avoidable computational burden.

39. Input Compression

Where information can be represented more compactly without losing materially required meaning, a compressed problem representation may reduce downstream computation.

40. Input Preprocessing

Deterministic or specialized preprocessing may reduce the complexity presented to a more computationally demanding intelligence mechanism.

This may include:

filtering,

normalization,

classification,

aggregation,

or structured extraction.

41. Preprocessing Boundary

Preprocessing should not remove information necessary for the required outcome.

Therefore:

Less Input ≠ Better Problem-Space Efficiency by default.

42. Known Information

Information already established through reliable mechanisms should not necessarily require repeated cognitive reconstruction.

PSEM may identify opportunities to provide structured known information rather than repeatedly infer it.

43. Unknown Information

Unresolved information may legitimately require greater computational or cognitive work.

The distinction between known and unknown information should remain visible.

44. Uncertainty

Problem uncertainty may increase legitimate computational demand.

PSEM should distinguish inherent uncertainty from uncertainty created by poor problem definition.

45. Reducible Uncertainty

Some uncertainty can be reduced through:

better inputs,

structured data,

retrieval,

clarification,

or deterministic preprocessing.

Reducing uncertainty before advanced reasoning may improve efficiency.

46. Irreducible Uncertainty

Some uncertainty cannot be eliminated with available evidence.

PSEM should preserve this uncertainty rather than create unnecessary computation attempting to manufacture certainty.

47. Requirement Ambiguity

Ambiguous requirements may cause an intelligent system to explore unnecessarily large solution spaces.

Where practical, clarification may be computationally more efficient than additional reasoning.

48. Requirement Precision

Requirements should be sufficiently precise to constrain the problem without eliminating legitimate solution flexibility.

49. Objective Definition

Where an execution optimizes or selects among alternatives, the objective should be explicit enough to prevent unnecessary search or reasoning.

50. Objective Overload

A problem may include too many simultaneous objectives.

Where some objectives are irrelevant or subordinate, their inclusion may unnecessarily increase computational complexity.

51. Constraint Identification

Applicable constraints should be identified before computational solution search begins.

Known constraints can reduce the feasible problem space.

52. Constraint Filtering

Invalid solution regions may be removed before expensive reasoning where applicable constraints already exclude them.

This can reduce unnecessary computational exploration.

53. Search-Space Efficiency

Where execution involves search, PSEM should evaluate whether the search space can be legitimately narrowed before high-cost computational exploration.

54. Search-Space Excess

A system may search possibilities that are already:

invalid,

irrelevant,

duplicated,

or outside the Operational Requirement.

Such search represents avoidable problem-space computation.

55. Candidate Reduction

Where deterministic or lower-cost methods can eliminate unsuitable candidates, advanced intelligence may operate only on the remaining feasible set.

56. Decision-Space Efficiency

Where the required outcome is a decision, the relevant decision space should contain only legitimate alternatives.

Unnecessary alternatives create unnecessary computational burden.

57. Problem-Solution Separation

PSEM distinguishes:

what problem must be solved

from

how the problem will be solved.

Technology should not redefine the Operational Requirement merely because it offers additional capabilities.

58. Technology-Induced Problem Expansion

Available technology may encourage organizations to expand the problem because additional capabilities exist.

PSEM should resist unnecessary expansion.

Therefore:

Capability Availability ≠ Requirement Expansion.

59. AI-Induced Problem Expansion

An organization may assign tasks to AI that were not part of the original Operational Requirement simply because the model can perform them.

Such expansion should possess an independent operational Basis.

60. Mechanism Necessity

Before selecting a model, PSEM should consider what type of mechanism is actually necessary.

The mechanism hierarchy may include:

No Intelligence → Deterministic Rule → Mathematics → Statistics → Specialized Algorithm → Machine Learning → Small Model → Advanced Model → Reasoning Intelligence → Multi-Agent Configuration → Human

61. No-Intelligence Solution

Some Operational Requirements can be satisfied without intelligence.

Examples may include:

static mappings,

simple arithmetic,

fixed rules,

or direct retrieval.

Where such mechanisms are sufficient, intelligent execution may represent unnecessary complexity.

62. Deterministic Solution

A deterministic mechanism may be appropriate where the relationship between input and required output is sufficiently defined.

Deterministic execution should not be rejected merely because advanced intelligence is available.

63. Mathematical Solution

Some problems are fundamentally mathematical rather than cognitive.

Using a language or reasoning model to reproduce a reliable mathematical operation may introduce unnecessary computation.

64. Statistical Solution

Where statistical inference sufficiently satisfies the Operational Requirement, more computationally complex mechanisms may not be necessary.

65. Specialized Algorithm

A specialized algorithm may outperform a general intelligence mechanism for a narrow, well-defined problem.

PSEM remains neutral regarding mechanism prestige.

66. Machine Learning Requirement

Machine learning may be justified where deterministic or simpler mechanisms cannot reliably capture the required relationship.

Its use should follow operational need.

67. Advanced Model Requirement

Advanced models may be justified where lower-complexity mechanisms cannot reliably satisfy the problem.

Their use should not be assumed from availability alone.

68. Reasoning Requirement

Reasoning intelligence should be introduced where the problem genuinely requires cognitive processing beyond simpler mechanisms.

CGEM subsequently governs the efficiency of that cognitive work.

69. Multi-Agent Requirement

A multi-agent configuration should arise from a problem structure that materially benefits from multiple governed execution roles.

Agent architecture should not be created before the problem demonstrates the need.

70. Human Requirement

Some problems may require human judgment, authority, contextual understanding, or intervention.

PSEM may identify the requirement without treating human involvement as computational failure.

71. Hybrid Problem Solution

A problem may be solved most efficiently through multiple mechanisms.

For example:

Deterministic Filtering → Specialized Algorithm → Small Model → Advanced Model Escalation → Human Exception

PSEM may establish the problem structure supporting such later execution design.

72. Escalation Logic

A lower-complexity mechanism may handle normal cases while unresolved cases escalate.

This allows greater intelligence to be reserved for problems that actually require it.

73. De-Escalation Opportunity

Where evidence shows that a class of problems previously assigned to a complex mechanism can be reliably solved by a simpler mechanism, PSEM may identify a de-escalation opportunity.

74. Problem Routing Basis

Problem classes may be routed according to:

complexity,

uncertainty,

required output,

known structure,

or another evidenced property.

Routing logic should reflect operational need.

75. Problem-Space Baseline

PSEM should establish the current problem formulation before optimization.

The baseline may identify:

scope,

inputs,

representation,

decomposition,

complexity,

mechanism assumptions,

and required outcome.

76. Alternative Problem Formulation

PSEM may generate or evaluate alternative formulations capable of satisfying the same Operational Requirement.

Alternatives should preserve required outcome equivalence.

77. Formulation Comparison

Problem formulations should be compared according to:

outcome sufficiency,

complexity,

required intelligence,

downstream computational demand,

and applicable constraints.

78. Problem-Space Optimization Hypothesis

A proposed change should identify:

what problem-space complexity will be reduced,

why it is unnecessary,

what computational consequence is expected,

and what required outcome must remain preserved.

79. Problem-Space Validation

An optimized problem formulation should be validated to confirm that the required operational outcome remains achievable.

Simplification without outcome preservation is not optimization.

80. Problem-Space Regression

A simplified formulation may create:

missing information,

reduced reliability,

new failure states,

or downstream correction.

These effects should remain visible.

81. Downstream Computational Effect

PSEM should evaluate whether problem-space changes reduce or increase downstream:

reasoning,

orchestration,

model requirements,

compute,

or hardware demand.

82. Complexity Displacement

Problem simplification may merely move complexity elsewhere.

For example:

removing preprocessing may increase model reasoning,

or

reducing structured inputs may increase inference uncertainty.

Therefore:

Removed Problem Complexity ≠ Eliminated System Complexity by default.

83. Problem-Space Rebound

A simplified formulation may create more:

retries,

clarification,

validation,

or correction.

The complete downstream effect should therefore be considered.

84. Problem-Space Evidence

Evidence may include:

task definitions,

input structures,

execution traces,

failure patterns,

routing data,

comparative tests,

resource-consumption traces,

and validated outcomes.

85. Problem-Space Measurement

Relevant measures may include:

input volume,

number of problem variables,

candidate-space size,

task classes,

decomposition depth,

required mechanism classes,

or downstream computational demand.

No single metric universally defines Problem-Space Efficiency.

86. Problem-Space Uncertainty

Where evidence is insufficient to establish whether simplification is safe, PSEM should preserve uncertainty.

Therefore:

Possible Simplification ≠ Proven Efficient Formulation.

87. Problem-Space Drift

The operational problem may change over time.

A formulation that was once proportionate may become:

too broad,

too narrow,

or structurally inappropriate.

88. Problem-Space Reassessment

Reassessment should occur where:

Operational Requirement changes,

inputs change,

task classes change,

constraints change,

failure patterns change,

or new execution evidence becomes available.

89. Problem-Space Versioning

Material changes to:

scope,

representation,

decomposition,

input requirements,

or mechanism assumptions

should remain versioned where necessary for traceability.

90. Problem-Space Provenance

A Governed Problem-Space Efficiency State should preserve sufficient provenance to identify:

Operational Requirement,

Problem Object,

required outcome,

problem boundary,

inputs,

constraints,

formulation,

decomposition,

mechanism assumptions,

evidence,

version,

and optimization determination.

91. Problem-Space Integrity

PSEM should resist:

starting optimization at the model layer,

assuming every problem requires AI,

expanding requirements because capability exists,

processing irrelevant inputs,

preserving unnecessary ambiguity,

searching invalid solution spaces,

using advanced models for deterministic problems by default,

creating multi-agent structures before the problem requires them,

simplifying problems below outcome sufficiency,

and shifting complexity elsewhere while claiming it has been eliminated.

The governing principle is:

Optimize the problem before optimizing the computation used to solve it.

94. Minimum Implementation Framework

A conforming implementation of PSEM must provide exactly the following six capabilities:

1. Problem Object & Requirement Governance

Capability to establish the Problem Object, Operational Requirement, required outcome, scope, and problem boundary.

2. Problem Formulation & Complexity Governance

Capability to identify necessary and artificial complexity, representation choices, ambiguity, uncertainty, objectives, and relevant constraints.

3. Decomposition, Input & Search-Space Governance

Capability to govern decomposition, aggregation, segmentation, input necessity, candidate reduction, search-space reduction, and decision-space boundaries.

4. Mechanism Requirement Governance

Capability to determine whether the problem requires no intelligence, deterministic logic, mathematics, statistics, specialized algorithms, machine learning, models, reasoning, multi-agent execution, human involvement, or hybrid mechanisms.

5. Problem-Space Evidence & Integrity Governance

Capability to compare alternative formulations, detect complexity displacement and rebound, preserve uncertainty, validate outcome sufficiency, and maintain versioning and provenance.

6. COS Cognitive Efficiency Handoff Governance

Capability to produce a Governed Problem-Space Efficiency State sufficiently explicit for subsequent Cognitive Efficiency governance.

100. Use Case 1 — Advanced AI Used for a Deterministic Business Rule

An organization routes every incoming request to an advanced reasoning model.

One class of requests requires only:

reading a structured field,

checking it against a fixed threshold,

and returning one of two predefined outcomes.

PSEM separates this task class from the broader problem and evaluates its actual operational requirement.

The required outcome can be reliably produced through deterministic logic.

The problem is therefore removed from the advanced-model path before downstream model or compute optimization is necessary.

Problem Requirement ≠ AI Requirement.

101. Use Case 2 — Complex AI Workflow Receives Excessive Information

An intelligent operational system receives large documents, historical records, multiple databases, and extensive contextual information for every case.

Only a small subset of that information is relevant to most routine cases.

PSEM identifies the required inputs, separates routine from exceptional problem states, and establishes a narrower initial problem formulation.

Additional information becomes available only where unresolved conditions justify escalation.

The downstream system therefore performs less unnecessary processing while preserving access to greater complexity when required.

More Input ≠ Better Problem Definition.

102. Canonical Closing Statement

The first computational decision is not which model to use.

It is what problem should actually be given to computation.

An unnecessarily broad problem creates unnecessary context.

An unnecessarily ambiguous problem creates unnecessary reasoning.

An unnecessarily large search space creates unnecessary exploration.

And a deterministic problem assigned to advanced intelligence creates computational demand that should never have existed.

Optimization therefore begins before the first model call, agent action, compute allocation, or hardware cycle.

Problem Complexity ≠ Required Computational Complexity.

Optimize the problem before optimizing the machine that solves it.

The most efficient computation is often the computation that a better problem formulation makes unnecessary.
