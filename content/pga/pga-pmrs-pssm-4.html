Governed Space

PSSM governs the controlled transition by which a newer Governed Prediction State becomes the current prediction while the prediction state it replaces is preserved as a historically valid predecessor.

It establishes:

which prediction state is current; which prediction state has been superseded; when supersession becomes effective; what relationship exists between predecessor and successor; how supersession propagates across systems; how stale prediction states are identified; how historical continuity is protected.

PSSM governs the transition:

Prior Current Prediction State + Eligible Successor Prediction State + Supersession Determination → Governed Current Prediction State

Its foundational principle is:

Supersession changes which prediction is current. It does not change what was previously predicted.

Canonical Definition

The Prediction Supersession Module (PSSM) defines the operational governance requirements by which an eligible successor prediction state formally replaces a preceding prediction state as the current governed prediction without deleting, rewriting, invalidating by default, or obscuring the historical prediction state that preceded it.

PSSM governs:

supersession eligibility; predecessor identification; successor identification; Current Prediction State; supersession authority; effective supersession time; supersession reason; predecessor-successor relationship; version transition; partial and complete supersession; downstream propagation; stale-version detection; supersession conflict; historical preservation; lifecycle continuity.

The canonical relationship is:

P1 — Current

→ Governed Successor Established

→ Supersession

→ P1 — Superseded · P2 — Current

not:

P1 disappears and P2 becomes the only prediction that ever existed.

Operational Role

PSSM is the fourth operational module within PMRS.

Its focused operational question is:

When a legitimate successor prediction state exists, under what conditions may it replace the preceding prediction as the current governed state, and how must the predecessor remain preserved throughout that transition?

PSSM receives eligible successor states from preceding governance, particularly PRVM.

It determines the current-state transition.

It does not determine how the successor prediction was calculated.

It does not determine whether the prediction should be withdrawn entirely.

Internal Module Flow

Current Position:

Prediction Supersession

1. Prediction Supersession

Prediction Supersession is the governed transition by which one prediction state ceases to be the current state because another legitimate prediction state takes its place.

Supersession concerns:

Current-State Authority

not:

Historical Existence

A superseded prediction remains part of Prediction History.

2. Supersession Eligibility

A successor prediction must be eligible before it may supersede the current state.

Eligibility may require:

valid prediction identity; legitimate Revision Basis; completed applicable governance; sufficient version distinction; preserved predecessor relationship; identifiable effective time; appropriate authorization.

Newer Prediction ≠ Automatically Eligible Successor

3. Predecessor Prediction

The Predecessor Prediction is the governed state that is current immediately before supersession.

It should remain identifiable by:

Prediction ID; version; predictive state; effective period; historical context.

4. Successor Prediction

The Successor Prediction is the governed prediction state proposed to become current.

The successor should identify its relationship to the predecessor.

Possible relationships include:

Revision Successor

Correction Successor

Reformation Successor

Conditional Successor

Scope-Specific Successor

5. Predecessor–Successor Relationship

PSSM requires explicit lineage between the two states.

Canonical structure:

P1 → P2

The relationship should answer:

what P2 supersedes; why; when; to what extent; under what conditions.

6. Current Prediction State

At any governed point in time, the system should be capable of identifying which prediction state is current.

Possible lifecycle status:

Current

Current with Qualification

Pending Supersession

Superseded

Withdrawn

Historical

Unable to Determine

7. Current-State Uniqueness

Where the prediction structure requires one authoritative current state, simultaneous conflicting current versions should not remain unresolved.

Multiple Available Versions ≠ Multiple Current Versions

Historical availability does not create current-state equivalence.

8. Current-State Authority

Current-State Authority indicates which prediction version should be treated as the current governed prediction for applicable downstream governance.

It does not create:

Decision Authority; Reliance Authority; Use Permission; Execution Authority.

Current Prediction ≠ Authorized Action

9. Supersession Determination

A Supersession Determination establishes whether the eligible successor should become current.

Possible determinations include:

Supersession Approved

Supersession Approved with Qualification

Supersession Pending

Supersession Restricted

Supersession Not Supported

Unable to Determine

10. Supersession Basis

Every material supersession should have an identifiable basis.

Examples:

approved revision; corrected predictive state; changed probability; changed uncertainty; changed assumptions; changed feasibility; changed Prediction Horizon; changed Predictive Boundary; formal lifecycle update.

Version Difference ≠ Supersession Basis by Default

11. Supersession Effective Time

The Supersession Effective Time identifies when the successor becomes current.

Before that time:

P1 may remain current.

After that time:

P2 becomes current.

The effective time should remain historically preserved.

12. Revision Time vs Supersession Time

A prediction may be revised before it becomes operationally current.

Therefore:

Revision Time ≠ Supersession Time

Example:

10:00 — P2 revision completed

10:30 — P2 approved

11:00 — P2 supersedes P1

These states should remain distinguishable.

13. Supersession Latency

Supersession Latency is the interval between successor eligibility and effective supersession.

Excessive latency may cause stale-state persistence.

Immediate supersession may also be inappropriate where:

approval is required; propagation must be coordinated; downstream systems require preparation.

14. Immediate Supersession

Immediate supersession may be justified where continued use of the predecessor would create material governance risk.

Examples:

critical correction; materially invalidated probability; major feasibility change; serious integrity correction.

15. Scheduled Supersession

A successor may become current at a defined future time.

Example:

New prediction becomes effective at market opening tomorrow.

The predecessor remains current until the defined transition point unless otherwise restricted.

16. Conditional Supersession

Supersession may depend upon a defined condition.

Example:

P2 becomes current if regulatory approval occurs.

Until the condition is satisfied, the predecessor relationship must remain explicit.

17. Partial Supersession

A successor may supersede only part of a predictive structure.

Example:

P1 covers:

Regions A + B + C

P2 may supersede:

Region A only

while P1 remains current for B and C.

Partial Supersession ≠ Complete Supersession

18. Complete Supersession

Complete Supersession occurs where the successor replaces the predecessor across the entire applicable governed scope.

The predecessor then becomes historical across that scope.

19. Scope-Specific Supersession

Supersession may differ by:

geography; population; product; system; Prediction Horizon; scenario; operational context.

The applicable scope must remain explicit.

20. Supersession Boundary

The Supersession Boundary defines exactly where the successor becomes current.

Without this boundary, different systems may interpret supersession differently.

Successor Existence ≠ Universal Supersession

21. Supersession Qualification

A successor may become current with qualifications.

Example:

P2 — Current with Qualification

where:

uncertainty remains elevated; monitoring is intensified; use is temporarily restricted.

The qualification should travel with current-state identification.

22. Prediction Version Transition

Supersession should preserve explicit version transition.

Example:

Prediction 00421-v1 → Prediction 00421-v2

The current version changes.

The historical version remains identifiable.

23. Version Lineage

Version Lineage may become:

P1 → P2 → P3 → P4

PSSM must preserve the chain.

The architecture must not collapse this into:

P4

24. Branching Prediction Lineage

Some prediction lifecycles may branch.

Example:

P1

→ P2-A for Scenario A

→ P2-B for Scenario B

PSSM should distinguish branching from universal supersession.

25. Merged Prediction Lineage

Two prediction branches may later converge into a successor state.

Where this occurs, predecessor relationships should remain traceable.

Merged State ≠ Single Historical Origin

26. Prediction State Continuity

Supersession should preserve continuity between:

prior current state; transition; successor state; historical predecessor.

The system should be able to answer:

What was current at Time T?

27. Historical Current-State Reconstruction

Historical reconstruction should permit identification of the prediction state that was current at any materially relevant past time.

Example:

1 January → P1

15 February → P2

3 April → P3

This becomes essential for later decision and performance analysis.

28. Superseded Prediction State

A superseded prediction should remain explicitly marked:

Superseded

rather than simply:

Inactive

The distinction explains why it ceased to be current.

29. Superseded ≠ Invalid

A superseded prediction is not automatically invalid.

It may have been fully legitimate during its effective period.

Superseded ≠ Wrong

Superseded ≠ Invalid

Superseded ≠ Failed

30. Superseded ≠ Withdrawn

Supersession means:

A newer legitimate state replaced the older current state.

Withdrawal means:

The prediction is removed from active predictive status without ordinary successor continuity.

These lifecycle events must remain distinct.

31. Superseded ≠ Deleted

Historical preservation is mandatory.

Supersession ≠ Deletion

The predecessor must remain available for governed history.

32. Supersession and Prediction Revision

Revision creates or modifies a successor prediction state.

Supersession determines whether that successor becomes current.

Therefore:

Revision ≠ Supersession

A revised prediction may exist before supersession.

33. Supersession Without Revision

Not every supersession must arise from ordinary PRVM revision.

A successor may result from:

reformation; correction; scheduled prediction cycle; externally governed successor process.

PSSM still governs the current-state transition.

34. Supersession Authority

Where applicable, the authority capable of approving supersession should remain identifiable.

Supersession Authority may differ from Revision Authority.

Revision Authority ≠ Supersession Authority by Default

35. Human Supersession

Humans may approve supersession.

The transition should preserve:

predecessor; successor; rationale; authority; effective time; scope.

36. AI-Assisted Supersession

AI may recommend which version should become current.

The recommendation itself does not establish supersession unless governance permits it.

AI Recommendation ≠ Supersession Determination

37. Autonomous Supersession

Autonomous systems may execute supersession where explicitly authorized.

The transition must still remain:

attributable; versioned; traceable; reversible where appropriate; historically preserved.

Autonomous Supersession ≠ Autonomous Historical Rewrite

38. Supersession Propagation

A current-state transition may need to propagate across:

APIs; dashboards; databases; AI agents; autonomous systems; decision-support systems;

reports; public interfaces.

PSSM governs the state relationship being propagated.

PCRS governs downstream communication, reliance, and use.

39. Propagation Target

Each material destination receiving the prediction may be treated as a Propagation Target.

Where appropriate, the system should identify whether the target received:

predecessor; successor; supersession signal; effective time; qualification.

40. Supersession Signal

A Supersession Signal communicates that:

Prediction P1 is no longer current and Prediction P2 is the successor state.

The signal should not require deletion of P1.

41. Machine-Readable Supersession

Machine-readable environments may express:

predecessor ID; successor ID; supersession state; effective time; scope; qualification; lineage.

Machine-Readable Supersession ≠ Autonomous Use Permission

42. Stale Prediction Version

A Stale Prediction Version is an earlier prediction state that remains active or represented as current after supersession.

Example:

Source System = P2

while:

Downstream AI Agent = P1

P1 is historically valid but operationally stale.

43. Stale-Version Detection

PSSM should support detection of mismatches between:

Authoritative Current State

and:

Downstream Active State

This is essential in distributed prediction systems.

44. Stale-Version Propagation Risk

A stale version may continue influencing:

decisions; alerts; rankings; resource allocation; automated actions.

The fact that the version was once legitimate does not make its continuing use legitimate.

Historically Valid ≠ Currently Valid for Active Use

45. Propagation Failure

Propagation Failure occurs where a valid supersession exists but relevant downstream systems do not receive or apply the transition.

Supersession at Source ≠ Supersession Everywhere

46. Partial Propagation

Some systems may receive P2 while others remain on P1.

PSSM should allow the ecosystem to represent this state explicitly.

Possible state:

Supersession Partially Propagated

47. Propagation Confirmation

Where consequence justifies it, systems may confirm that supersession was received and activated.

Confirmation may include:

target; received version; activation time; state.

48. Supersession Conflict

A Supersession Conflict occurs where systems disagree about which prediction state is current.

Example:

System A → P2 Current

System B → P1 Current

System C → P3 Current

The conflict must not be silently resolved through arbitrary recency.

49. Conflicting Successors

Multiple candidate successors may exist.

Example:

P2-A

and:

P2-B

both claim to supersede P1.

PSSM must preserve the conflict until legitimate current-state authority is established.

Newest Timestamp ≠ Legitimate Successor by Default

50. Duplicate Supersession

Repeated propagation of the same supersession event should not create multiple lifecycle transitions.

Repeated Supersession Signal ≠ Multiple Supersessions

51. Supersession Rollback

A successor may later be found to contain a serious problem.

Where governance permits, rollback may restore a prior prediction state or another eligible state as current.

Rollback must create a new governed lifecycle event.

It must not erase the supersession that occurred.

52. Rollback ≠ Historical Reversal

If:

P1 → P2 → Rollback to P1

the historical record remains:

P1 Current → P2 Current → P1 Reinstated

not:

P2 never existed.

53. Prediction Reinstatement

A previously superseded prediction may become current again under exceptional governed conditions.

Reinstatement should establish:

why; when; under what conditions; whether its predictive support remains current.

Historical Availability ≠ Reinstatement Eligibility

54. Supersession Cancellation

A planned supersession may be cancelled before its effective time.

The cancellation should remain historically traceable where material.

55. Pending Supersession

A successor may be eligible but not yet effective.

State:

Pending Supersession

This prevents premature treatment of the successor as current.

56. Supersession Freeze

Supersession may temporarily be frozen where:

governance conflict exists; validation is incomplete; successor integrity is questioned; authority is unresolved.

A freeze preserves the transition state without silently selecting a winner.

57. Supersession and Prediction Horizon

A successor may retain or modify Prediction Horizon.

PSSM should preserve which horizon applied to each version.

Successor Horizon ≠ Historical Predecessor Horizon

58. Supersession and Predictive Boundary

Where successor scope differs, the Supersession Boundary must identify where replacement actually applies.

A narrower successor may not supersede the predecessor outside its scope.

59. Supersession and Probability

A probability change may be one reason for successor creation.

PSSM does not govern probability formation.

It preserves which probability belonged to which current prediction state.

60. Supersession and Uncertainty

A successor may carry materially different uncertainty.

The uncertainty state should remain version-specific.

Current Probability Without Current Uncertainty Context ≠ Complete Current Prediction State

61. Supersession and Assumptions

Assumptions may differ between predecessor and successor.

The historical assumption structure must remain associated with the version to which it applied.

62. Supersession and Feasibility

Feasibility states may change across versions.

Example:

P1 — Feasible

→

P2 — Conditionally Feasible

PSSM preserves the version-specific relationship.

63. Supersession and Collective Prediction

A collective prediction successor may reflect:

changed participants; changed aggregation; changed independence; changed concentration;

changed probability.

CPGS owns the collective governance.

PSSM governs current-state transition.

64. Supersession and Predictor–Reality Proximity

Changes in Predictor–Reality Proximity associated with a successor should remain version-specific where materially relevant.

Later informational advantage must not be retroactively attributed to the predecessor.

65. Supersession and Communication

Once a successor becomes current, downstream representations should be capable of identifying the current state.

PRSM governs representation.

PSSM provides the authoritative supersession relationship.

66. Supersession and Interpretation

PIBM and PLDIM may need to operate against the successor state.

An interpretation derived from P1 should not silently be treated as an interpretation of P2.

Prediction Version Change ≠ Interpretation Continuity by Default

67. Supersession and Reliance

RLCM may need to reassess reliance when the prediction state changes.

Supersession ≠ Automatic Reliance Continuation

A successor may support stronger, weaker, or different reliance.

68. Supersession and Prediction Use

PUBM may need to reassess permitted use after supersession.

A new current prediction does not automatically inherit every prior use permission.

Current-State Continuity ≠ Use-Permission Continuity

69. Supersession and Automated Rules

Automated systems may contain rules linked to prediction version or probability.

A successor may therefore change operational behavior.

PSSM does not authorize that behavior.

Supersession Signal ≠ Execution Authority

70. Supersession and Decision History

A historical decision should remain associated with the prediction version that was current or available when the decision occurred.

Example:

Decision D1 relied on P1

even if:

P2 later superseded P1.

Later Current Prediction ≠ Earlier Decision Input

71. Supersession and Outcome Assessment

POFPS must later be able to determine which prediction version is relevant to outcome comparison.

PSSM therefore preserves effective periods.

A later successor must not replace the predecessor in historical performance assessment.

72. Effective Prediction Period

Each current prediction state may have an Effective Prediction Period.

Example:

P1: 1 Jan–14 Feb

P2: 15 Feb–2 Apr

P3: 3 Apr–Outcome

These periods support lifecycle reconstruction.

73. Overlapping Effective Periods

Some architectures may permit overlapping predictions for different scopes or scenarios.

Where overlap exists, scope must remain explicit.

Overlapping Effective Periods ≠ Current-State Conflict by Default

74. Current-State Query

A governed implementation should be capable of answering:

Which prediction was current for Object X, Scope Y, at Time T?

This is one of PSSM's fundamental operational capabilities.

75. Supersession Record

A Supersession Record should preserve:

predecessor; successor; relationship; basis; scope; determination; effective time; authority where applicable; qualification; propagation state.

76. Supersession History

Supersession History preserves all material current-state transitions.

Example:

P1 → P2 → P3 → P4

Each transition remains reconstructable.

77. Historical Integrity

Later successors must not modify the predictive state of earlier versions.

Later Prediction State ≠ Earlier Prediction State

Historical integrity applies even when the later prediction is demonstrably better.

78. Outcome Knowledge Boundary

Outcome knowledge must not be used to retroactively change which prediction was current before the outcome became known.

Known Outcome ≠ Permission to Rewrite Current-State History

79. Supersession Gaming

Potential Supersession Gaming includes:

backdating successor effective time; hiding predecessor versions; retroactively declaring a favorable version current; deleting adverse versions;

changing scope after outcome; selectively preserving only successful prediction states.

PSSM must prevent these practices from appearing as legitimate lifecycle governance.

82. Governance Logic

PSSM applies the following operational logic:

Does an eligible successor prediction state exist?

If no:

→ preserve the existing Current Prediction State.

If yes:

→ identify predecessor and successor.

Is the successor sufficiently governed to become current?

If no:

→ classify Supersession Pending , Restricted , or Not Supported .

If yes:

→ determine Supersession Scope.

Does the successor replace the predecessor across the complete predictive scope?

If yes:

→ Complete Supersession.

If no:

→ establish Partial or Scope-Specific Supersession.

When should the successor become current?

→ establish Supersession Effective Time.

Does the transition require qualification?

If yes:

→ attach Supersession Qualification.

At effective transition:

Predecessor → Superseded

Successor → Current

Then:

→ propagate Supersession Signal;

→ identify stale downstream versions;

→ preserve predecessor;

→ preserve version lineage;

→ preserve effective periods;

→ preserve historical transition.

The canonical state transition is:

P1 Current → Supersession → P1 Superseded + P2 Current

never:

P1 deleted → P2 presented as original state

PSSM can govern prediction-state transitions across:

enterprise forecasting; financial forecasting; investment analysis; insurance; manufacturing; supply-chain planning; predictive maintenance; logistics; energy systems; critical infrastructure; public-sector forecasting; emergency planning; AI prediction systems; autonomous systems; AI agents; prediction markets; model ensembles; Human-AI forecasting; multi-agent prediction environments.

87. Use Case 1 — Revised Supply Forecast Reaches Some Systems but Not Others

A manufacturer maintains:

P1 — 72% probability of sufficient semiconductor supply over six months.

Following a major export restriction, governed revision produces:

P2 — 41% probability.

PRVM has completed the revision.

PSSM establishes:

P1 — Superseded

P2 — Current

with an Effective Supersession Time of:

10 September 2026 · 14:00

The central forecasting platform and procurement dashboard receive P2.

However:

an inventory AI still uses P1; a production-planning API still returns P1; a management report generated earlier continues displaying P1 as current.

The critical governance question is:

Has the prediction been successfully superseded merely because the source system contains P2?

PSSM determines:

Supersession at Source: Complete

Propagation State: Partial

Stale Prediction Versions: Active

The system preserves:

P1 = historically valid predecessor

while identifying:

P1 = no longer current for active predictive use

The distinction is essential:

Historically Valid ≠ Currently Valid for Active Use

Supersession at Source ≠ Supersession Everywhere

PSSM enables the organization to identify exactly where the prediction lifecycle has diverged across systems.

88. Use Case 2 — Organization Attempts to Replace an Earlier Failed Forecast

A forecasting organization published:

P1 — 78% probability that Technology X will reach commercial deployment by December 2027.

In June 2027, delays become substantial.

A governed revision creates:

P2 — 46% probability of commercial deployment by December 2027.

P2 legitimately supersedes P1 in June.

Later, the outcome becomes known:

Technology X does not reach commercial deployment by December 2027.

The organization publishes a historical performance database containing only:

P2 — 46%

and removes P1.

The critical governance question is:

Can the latest prediction version replace earlier prediction states when historical performance is reconstructed?

PSSM determines:

No.

The legitimate history is:

P1 — Current during Period A

→ P2 — Superseded P1 during Period B

→ Outcome

P1 must remain historically visible because it was genuinely the current prediction during Period A.

P2 must remain visible because it became current during Period B.

Neither may erase the other.

Supersession ≠ Deletion

Current Prediction State ≠ Complete Prediction History

Known Outcome ≠ Permission to Rewrite Current-State History

This preserved sequence later allows POFPS to assess predictive performance against the prediction states that actually existed.

89. Canonical Boundary

PSSM governs the transition by which an eligible successor Governed Prediction State replaces a predecessor as the current prediction. It governs Supersession Eligibility, Predecessor and Successor identification, Current Prediction State, Supersession Basis, determination, authority, effective time, latency, scope, boundary, qualification, partial and complete supersession, version transition, branching and merged lineage, effective prediction periods, machine-readable supersession, propagation, stale-version detection, propagation failure, supersession conflict, rollback, reinstatement, historical current-state reconstruction, and complete supersession history. It does not form or revise the prediction, calculate probability, determine Prediction Withdrawal, authorize downstream reliance, grant Prediction Use Permission, create Decision Authority, establish Operational Reality, determine outcomes, or assess predictive performance.

PCHM owns:

Prediction Change Monitoring

RTM owns:

Prediction Review Trigger Determination

PRVM owns:

Prediction Revision

PSSM owns:

Prediction Supersession

PWM owns:

Prediction Withdrawal

90. Canonical Closing Statement

A prediction architecture must be able to move forward without rewriting where it came from.

PSSM makes one prediction current while preserving every predecessor that legitimately occupied that position before it, allowing humans and machines to distinguish current predictive authority from historical predictive truth.

Supersession changes the present state of the prediction. It does not erase its past.
