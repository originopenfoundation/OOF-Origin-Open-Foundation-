About Liability Object Standard (LOS)

About Liability Object Standard (LOS)

Canonical Meaning

A Liability Object is the governed matter against which potential Liability is structured and evaluated.

It is not automatically the:

occurrence, Harm, Loss, Damage, Claim, obligation, person, organization, product, system, action, omission, or operational mechanism from which Liability relevance arose.

Any of these may contribute to formation of the Liability Object.

None automatically defines it.

The foundational distinction is:

Liability-Relevant Matter ≠ Liability Object by default.

Why Is a Liability Object Necessary?

A Liability Context may contain many interconnected matters.

An industrial incident may involve:

equipment, maintenance, operators, suppliers, software, contracts, earlier modifications, Harm, Loss, and later remedial actions.

An AI-related matter may involve:

a model, deployment configuration, system output, autonomous action, human decision, data source, external platform, and resulting consequence.

If the governed object is not explicitly established, different stages of Liability governance may unknowingly evaluate different matters.

The Liability Basis may be applied to one object.

Conditions may be evaluated against another.

Connection may be assessed against another.

Liability may then appear to be determined without a stable governed object.

LOS prevents that structural failure.

Why Is LOS Important?

Liability governance requires more than identifying that something happened.

It requires a stable answer to:

What exactly is the matter against which potential Liability is being evaluated?

This distinction becomes increasingly important where systems are:

distributed, multi-party, AI-enabled, autonomous, digitally interconnected, contractually layered, or operationally complex.

One occurrence may contain multiple Liability Objects.

One Liability Object may participate in multiple Liability Relationships.

Several apparently separate matters may form one Composite Liability Object.

A Liability Object may also exist even where subsequent governance determines that no Liability attaches.

LOS creates the object stability necessary for those later distinctions.

What Does LOS Govern?

LOS governs the formation and maintenance of the Liability Object.

This includes:

Object Identification, Object Formation, Object Identity, Object Boundary, Object Granularity, Object Distinction, Object Representation, Object Classification, Object State, Object Uncertainty, Composite Objects, Multiple Objects, Object Separation, Object Consolidation, Object Change, Object Correction, Object Reassessment, and Object Continuity.

The intended result is a:

Governed Liability Object

that can proceed into Liability Basis governance.

What Does LOS Not Govern?

LOS does not determine whether Liability exists.

It does not determine:

the legal basis for Liability, who bears Liability, the relationships between Liability Subjects, whether required Liability Conditions are satisfied, whether a sufficient Liability-Relevant Connection exists, whether Liability attaches, the Scope of Liability, the Allocation of Liability, Transfer or Recourse, Resolution, Discharge, or Finality.

It also does not replace governance of:

Operational Reality, Harm, Accountability, Claims, Evidence, Validation, AI behavior, autonomous-system operation, Simulation, Prediction, Identity, or Value.

LOS governs one specific question:

What is the Liability Object?

Where Does LOS Sit in LIGA™?

The LIGA™ Governance Flow is:

Liability Context → Liability Object → Liability Basis → Liability Relationships → Liability Conditions → Liability Connection → Liability Determination → Liability Scope & Allocation → Liability State & Change → Liability Transfer & Recourse → Liability Resolution & Discharge → Liability Continuity & Finality LOS occupies the second governance position.

It receives:

Governed Liability Context

from the Liability Context Standard (LCS).

It produces:

Governed Liability Object

for the Liability Basis Standard (LBS).

The transition is:

Governed Liability Context → Liability Object Formation → Governed Liability Object → Liability Basis

Governance

Context Is Not the Object

The Liability Context contains the environment necessary to understand the Liability-relevant matter.

The Liability Object identifies the specific matter against which potential Liability will be structured.

Therefore:

Liability Context ≠ Liability Object.

A Context may contain:

multiple Object Candidates, multiple Governed Liability Objects, or contextual information that never becomes part of any Liability Object.

Similarly:

Liability Context Boundary ≠ Liability Object Boundary.

The Context Boundary defines what must be considered as context.

The Object Boundary defines what constitutes the governed object itself.

Occurrence Is Not the Object

An occurrence may initiate Liability governance without defining the complete Liability Object.

One occurrence may contain:

several actions, several omissions, multiple products, multiple decisions, several operational stages, or multiple independently governable matters.

Therefore:

Occurrence ≠ Liability Object.

A single occurrence may produce multiple Liability Objects.

Conversely, several occurrences may form one Composite Liability Object where they constitute one materially coherent governed matter.

Harm Is Not the Object

Harm and Liability Object are separate governed concepts.

HAGA™ governs Harm.

LOS governs the Liability Object.

Harm may:

form part of the Liability Context, contribute to Object formation, relate to the Object, or become relevant later in the Liability lifecycle.

But:

Harm ≠ Liability Object by default.

A Liability Object may exist without established Harm.

Liability governance must therefore not depend on treating Harm as the object automatically.

Claim Is Not the Object

A Claim may assert a particular version of the matter.

That assertion does not establish the canonical Liability Object.

A Claim may be:

too broad, too narrow, incomplete, incorrectly structured, or composed of several distinct matters.

Therefore:

Claim Object ≠ Liability Object by default.

LOS forms the Liability Object independently from the procedural or asserted structure of a Claim.

This allows Liability governance to remain methodologically stable even where Claims change.

Subject Is Not the Object

The Liability Subject is the person, organization, system-related entity, or other governed participant potentially involved in a Liability Relationship.

The Liability Object is the matter in relation to which Liability is being evaluated.

Therefore:

Liability Object ≠ Liability Subject.

A company may be a Liability Subject.

A product failure, transaction, action, omission, service performance, system operation, or another matter may be the Liability Object.

These must remain separate.

Basis Is Not the Object

The Liability Object answers:

What is being governed?

The Liability Basis answers:

On what governed basis can Liability potentially exist in relation to that object?

Therefore:

Liability Object ≠ Liability Basis.

This distinction defines the transition between LOS and the next LIGA™ Parent Standard.

Object first.

Basis second.

Relationship Is Not the Object

A Liability Object may later participate in one or many Liability Relationships.

Therefore:

Liability Object ≠ Liability Relationship.

One object may involve several Liability Subjects.

Several different Liability Bases may potentially apply.

Secondary relationships may later arise through transfer, insurance, indemnification, contribution, succession, or recourse.

The object must remain identifiable independently from those relationships.

Operational Mechanism Is Not the Object

An operational mechanism may create or contribute to a Liability-relevant matter.

Examples include:

physical contact, software execution, autonomous action, mechanical movement, data transfer, communication, payment, or another operational mechanism.

The mechanism itself remains governed by the architecture whose domain contains that mechanism.

Therefore:

Operational Mechanism ≠ Liability Object by default.

LOS governs only whether and how a matter becomes a Liability Object.

Object Granularity

The Liability Object must be neither artificially narrow nor unnecessarily broad.

The smallest identifiable element is not automatically the correct object.

The largest connected matter is not automatically the correct object.

The correct level of granularity is the level at which the governed matter retains sufficient coherence for subsequent Liability governance.

Therefore:

Smallest Identifiable Matter ≠ Correct Liability Object by default.

Largest Connected Matter ≠ Correct Liability Object by default.

Composite Liability Objects

Some Liability matters are inherently composite.

A governed object may require:

several actions, several omissions, a sequence of system states, multiple operational stages, or several materially inseparable components.

LOS permits these to form one Composite Liability Object where separating them would distort the governed matter.

Therefore:

Multiple Components ≠ Multiple Liability Objects by default.

Multiple Liability Objects

The opposite situation is also possible.

One Liability Context may contain several genuinely distinct Liability Objects.

For example, one industrial incident may produce separate objects concerning:

equipment condition, maintenance intervention, operational decision, and later remedial action.

These objects may share a common Context while requiring different Liability Bases, Relationships, Conditions, or Connections.

Therefore:

One Liability Context ≠ One Liability Object.

Neutral Object Representation

A Liability Object must be represented without embedding an ungoverned conclusion.

The object should not be defined using language that presupposes:

fault, breach, negligence, wrongdoing, responsibility,

or Liability

unless that state has already been independently established and is legitimately relevant.

LOS therefore applies the principle:

Object Representation Must Not Predetermine Liability.

The object establishes what is being evaluated.

It does not establish the result of that evaluation.

Object Change and Continuity

A Liability Object may evolve as governance progresses.

Its description may improve.

Its boundary may be refined.

New components may be discovered.

Incorrect assumptions may be corrected.

Several candidates may be consolidated.

One object may need to be separated.

These changes do not automatically create a new object.

Therefore:

Object Change ≠ New Liability Object by default.

LOS preserves Object Continuity so that the history of the governed object remains reconstructable.

Relationship to the Wider OOF® Ecosystem

LOS operates within the wider modular OOF® Architecture Ecosystem.

LCS establishes the Governed Liability Context.

ORA™ may establish the Operational Reality from which an Object Candidate emerges.

HAGA™ governs Harm that may become relevant to Object formation.

AGA™ governs Authority, Responsibility, Accountability, and related structures.

ADIT® governs evidence supporting Object Identification and reconstruction.

VALIDOS™ governs Validation.

OBIDENITY® may establish identity, origin, ownership, provenance, and other relevant governed states.

AIG® and ASGA™ govern AI and autonomous-system domains that may generate Liability-relevant matters.

SIMULOS® governs Simulation.

PGA™ governs Prediction.

LOS may consume relevant outputs from these architectures without absorbing their governed objects.

The governing principle is:

An object governed elsewhere may become relevant to a Liability Object without transferring ownership of its original governed meaning to LIGA™.

Use Case 1 — Autonomous AI Action

An autonomous system performs an action that produces an unexpected real-world consequence.

The surrounding Liability Context contains:

the AI system, its deployment configuration, the autonomous action, the system operator, an external service, the affected operational environment, and the resulting consequence.

LOS does not automatically designate the AI system or the consequence as the Liability Object.

It determines what specific matter requires Liability governance.

The resulting Liability Object might concern a particular autonomous action, a defined execution sequence, or another sufficiently bounded matter.

Only after that object is established does the inquiry proceed to:

On what governed basis can Liability potentially exist in relation to this object?

Use Case 2 — Industrial Incident With Multiple Potential Objects

A production incident involves equipment failure, an earlier maintenance intervention, a component supplied by another organization, and an operational decision made shortly before the incident.

All of these matters exist within the Liability Context.

They do not automatically form one Liability Object.

LOS determines whether the matter requires:

one Composite Liability Object, several separate Liability Objects, or another appropriate object structure.

It establishes those objects without determining which party bears Liability.

This prevents later Liability Basis, Relationship, Condition, and Connection governance from being performed against an undefined or unstable matter.

Canonical Boundary

LOS governs the formation of the matter against which potential Liability will subsequently be structured and evaluated.

It begins with a:

Governed Liability Context

and ends with a:

Governed Liability Object.

LOS does not establish:

Liability Basis, Liability Relationship, Liability Conditions, Liability-Relevant Connection, Liability Attachment, Liability Determination, Liability Scope, Liability Allocation, Transfer, Recourse, Resolution, Discharge, or Finality.

Its canonical boundary can be expressed as:

LOS determines what the Liability inquiry is about — not why Liability may exist, who may bear it, or whether it ultimately attaches.

Canonical Meaning in One Sentence

A Liability Object is the explicitly governed matter against which potential Liability is structured and evaluated, distinct from the surrounding Context, occurrence, Harm, Claim, Subject, Basis, Relationship, and operational mechanism.

Canonical Closing Statement

Liability governance cannot remain coherent if the object of the inquiry changes silently as the lifecycle progresses.

An occurrence is not automatically the object. Harm is not automatically the object. A Claim does not define the object merely by asserting it. A person or organization is not the object merely because they may later become a Liability Subject.

LOS establishes the governed matter before Liability reasoning begins.

That separation allows every subsequent LIGA™ stage to ask its own question against the same identifiable object.

Occurrence ≠ Harm ≠ Liability Object ≠ Liability Relationship.

Define the object first. Then determine on what basis Liability may exist in relation to it.
