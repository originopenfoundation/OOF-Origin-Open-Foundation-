Canonical Definition

The Code & Artifact Integrity Module (CRIM) governs how software code and

creation artifacts are identified, originated, generated, modified,
transformed, preserved, evaluated, and maintained as
integrity-governed objects throughout software creation.

CRIM establishes the methodological conditions under which the identity,

origin, content continuity, transformation history, and evidentiary
integrity of a software artifact may be recognized as sufficiently
established for its intended creation-governance use.

It distinguishes the existence of a software artifact from its integrity,

the technical consistency of its contents from the legitimacy of its
creation or modification, and the preservation of artifact provenance
from evidence that the artifact satisfies its governing software
requirements.

CRIM applies to source code, generated code, scripts, executable artifacts,

intermediate generation outputs, machine-readable software
definitions, and other material software creation artifacts.

It applies regardless of whether artifacts are produced or transformed
by humans, organizations, AI coding assistants, autonomous development
agents, automated generation systems, or combinations of these actors.

Its principal output is:

Governed Code & Artifact Integrity State

Its foundational distinction is:

Artifact Existence ≠ Governed Artifact Integrity.

Operational Role

The operational role of CRIM is:

To ensure that material software creation artifacts remain
identifiable, attributable to sufficiently supported origins,
protected against unrecognized transformation, and reconstructable
across their creation and modification histories without confusing
content integrity with functional correctness, legitimate authority,
or software lifecycle acceptance.

CRIM establishes integrity governance over the artifacts produced during

software creation.

It supports the Software Creation Standard (SCS) by preserving the evidence

necessary to understand:

  • What software artifact was created
  • Which artifact version is being evaluated
  • Where the artifact originated
  • Which material inputs contributed to its formation
  • How its contents changed
  • Which actors or mechanisms performed material transformations
  • Whether the current artifact corresponds to its claimed origin
    and
  • Which integrity conditions remain unresolved

history.

CRIM does not independently determine that software is functionally
correct, secure, legally owned, or authorized for deployment.

Central Operational Question

How can a software artifact remain identifiable, origin-supported,
transformation-aware, and evidentially intact throughout creation,
including when its contents are generated or modified by multiple
humans, AI agents, tools, and autonomous systems?

Code & Artifact Integrity Governance Object

Every CRIM assessment shall identify the Code & Artifact Integrity

Governance Object.

The object represents a defined software artifact, artifact version, or

material artifact transformation whose integrity is being governed.

It should identify, where applicable:

Artifact Identity: The identifiable software creation artifact.

Artifact Type: The relevant code or artifact classification.

Artifact Version: The version or state under assessment.

Creation Reference: The associated software creation activity.

Artifact Origin: The supported source or creation event.

Artifact Content Reference: The identifiable content being assessed.

Transformation History: Material modifications affecting the artifact.

Actor References: Relevant creators, modifiers, or transformation

mechanisms.

Integrity Evidence: Evidence supporting artifact identity and content

continuity.

Applicable Context: The relevant creation, version, and assessment

conditions.

Integrity State: The current governance condition of the artifact.

The integrity object shall remain distinguishable from the software

creation activity that produced it.

Artifact Identity ≠ Creation Activity Identity.

Software Artifact Classification

CRIM shall identify the type and relevant role of each material
artifact.

Possible artifact classes include:

  • Human-authored source code
  • AI-generated source code
  • Automatically transformed source code
  • Scripts
  • Generated configuration artifacts
  • Intermediate representation artifacts
  • Compiled binaries
  • Executable packages
  • Machine-readable interface definitions
  • Code-generation templates
  • Generated application components
  • Software assembly outputs
  • Material build artifacts

Classification shall support the integrity assessment without imposing a

universal artifact taxonomy on every development environment.

The same artifact may have multiple relevant classifications.

For example, a generated executable may be both a build output and a
deployable software artifact.

Artifact Classification ≠ Artifact Integrity Determination.

Artifact Identity Governance

CRIM shall establish sufficiently stable references for material software

artifacts.

Identity may be supported by:

  • Unique artifact identifiers
  • Repository object references
  • Version references
  • Content-derived identifiers
  • Build or generation identifiers
  • Controlled artifact records
  • Other suitable identification mechanisms

Artifact identity shall not depend exclusively on a filename, directory

path, or display label.

The same filename may represent different artifacts across versions.

An artifact may also move between repositories without losing its
historical identity.

Artifact Name ≠ Artifact Identity.

Artifact Location ≠ Artifact Identity.

Artifact Content Identity

CRIM shall distinguish artifact identity from the identity of its
contents.

A logical software artifact may retain its identity while its contents
change across versions.

Conversely, identical contents may appear in multiple artifacts with
different origins, ownership conditions, or creation histories.

CRIM shall preserve the relationship between:

Artifact Identity → Artifact Version → Artifact Content State

Where content-derived identifiers are used, the relevant hashing or
identification conditions shall remain sufficiently explicit.

Identical Content ≠ Identical Artifact Governance State.

Artifact Origin Governance

CRIM shall identify the supported origin of material software
artifacts.

Possible origins include:

  • Human-authored creation
  • AI-generated creation
  • Automated code generation
  • Transformation of existing software
  • Reuse of internal components
  • Incorporation of external software
  • Software synthesis
  • Compilation or packaging
  • Multi-agent creation activities

Origin records shall distinguish an asserted origin from an evidentially

supported origin.

A repository entry naming an author does not necessarily establish who
or what generated the underlying contents.

Recorded Author ≠ Established Artifact Origin.

Artifact Provenance

CRIM shall preserve material provenance relationships.

These may include:

Source Artifact → Creation or Transformation Mechanism → Resulting

Artifact

Relevant provenance information may include:

  • Source references
  • Creation actor
  • Generation mechanism
  • Material inputs
  • Transformation method
  • Tool references
  • Relevant execution context
  • Artifact versions
  • Supporting evidence

Provenance may be incomplete or partially reconstructed.

Where material provenance is unknown, CRIM shall preserve that
limitation rather than invent a continuous history.

Provenance Record ≠ Provenance Verification.

Artifact Creation Event

CRIM shall identify material events through which software artifacts
first become recognizable creation objects.

A creation event may include:

  • Initial source-code creation
  • AI code generation
  • Compilation
  • Software synthesis
  • Transformation from another artifact
  • Extraction of a software component
  • Creation of a new artifact through assembly

The creation event should remain connected to the relevant software
creation object and applicable method.

The existence of a creation event does not independently establish
authorization.

Artifact Creation Event ≠ Authorized Artifact Creation.

Artifact Transformation Governance

Software artifacts may undergo multiple transformations.

Examples include:

  • Editing
  • Refactoring
  • Regeneration
  • Compilation
  • Formatting
  • Optimization
  • Translation between programming languages
  • Code synthesis
  • Automated rewriting
  • Extraction or splitting
  • Merging
  • Packaging

CRIM shall preserve material transformation relationships.

The governance chain is:

Source Artifact State → Transformation Event → Resulting Artifact State

Where the transformation materially changes artifact behavior, origin
interpretation, or integrity conditions, the change shall remain
identifiable.

Successful Transformation ≠ Preserved Artifact Integrity.

Transformation Identity and Attribution

CRIM shall distinguish artifact identity from transformation-event
identity.

A single artifact may undergo multiple transformations.

A single transformation may produce multiple resulting artifacts.

A transformation record should identify:

  • Transformation event
  • Source artifact state
  • Resulting artifact state
  • Transformation mechanism
  • Relevant actor
  • Applicable execution context
  • Supporting evidence

Where transformation attribution is uncertain, the uncertainty shall
remain explicit.

Artifact Contributor ≠ Automatically Authorized Transformer.

Artifact Version Integrity

CRIM shall preserve material relationships between artifact versions.

Version integrity should support reconstruction of:

  • Previous content state
  • Current content state
  • Material changes
  • Transformation basis
  • Relevant actor or mechanism
  • Supporting evidence
  • Supersession relationships

A version identifier shall not be treated as sufficient evidence that
the artifact contents are correct or historically authentic.

Version Label ≠ Version Integrity.

Artifact Continuity

CRIM shall preserve artifact continuity across relevant changes in:

  • Development actors
  • Repositories
  • Tools
  • AI models
  • Generation mechanisms
  • File locations
  • Build environments
  • Organizational control
  • Artifact formats

Continuity may be supported by identity references, provenance,
transformation history, and relevant evidence.

It shall not be inferred solely from an unchanged artifact name.

Naming Continuity ≠ Artifact Continuity.

Artifact Integrity Dimensions

CRIM shall distinguish material integrity dimensions.

Identity Integrity: Whether the artifact under assessment is
sufficiently identifiable.

Content Integrity: Whether its contents correspond to the claimed content

state.

Origin Integrity: Whether the claimed origin is adequately supported.

Transformation Integrity: Whether material modifications are
identifiable and sufficiently evidenced.

Version Integrity: Whether the relationship between artifact versions
is sufficiently supported.

Provenance Integrity: Whether material source and derivation

relationships remain reconstructable.

Evidence Integrity: Whether the supporting integrity evidence is
sufficiently reliable.

Continuity Integrity: Whether material artifact relationships remain

preserved across changes.

These dimensions may have different governance states.

Strong content integrity does not automatically establish origin or
transformation integrity.

Content Integrity ≠ Complete Artifact Integrity.

Content Integrity Evidence

CRIM may use technical evidence to assess whether artifact contents
correspond to an identified state.

Such evidence may include:

  • Cryptographic hashes
  • Digital signatures
  • Repository object identifiers
  • Controlled snapshots
  • Build records
  • Artifact manifests
  • Content comparison records
  • Other suitable integrity mechanisms

Technical evidence shall be interpreted within its actual evidentiary
scope.

A matching hash can support a claim that two content representations
are identical under the applicable hashing conditions.

It does not independently establish that the contents were
legitimately created, reviewed, or approved.

Hash Match ≠ Creation Legitimacy.

Artifact Authenticity

CRIM shall distinguish content integrity from authenticity.

Content integrity concerns whether contents correspond to an identified

state.

Authenticity concerns whether the artifact or associated claim can be
sufficiently connected to its asserted source or origin.

An artifact may retain unchanged contents while its claimed origin
remains unsupported.

A digitally signed artifact may establish a relevant signing
relationship without proving that every underlying creation activity
was authorized.

Content Integrity ≠ Artifact Authenticity.

Valid Signature ≠ Universal Governance Validity.

Artifact Integrity and Creation Authority

CRIM shall preserve the distinction between integrity and
authorization.

A software artifact may have:

  • Stable identity
  • Verified content
  • Complete transformation history
  • Strong provenance evidence

Yet its creation or modification may have occurred outside the
applicable authority boundary.

CRIM shall preserve relevant creation authority references without

independently determining general authority.

Integrity-Preserved Artifact ≠ Authorized Artifact.

The competent SCS and authority-governance processes determine the

applicable creation authorization conditions.

Artifact Integrity and Requirements Alignment

CRIM shall preserve relevant relationships between software artifacts and

their governing requirements.

However, artifact integrity does not establish that the artifact
implements the correct requirements.

A software component may remain byte-for-byte unchanged while its
governing requirements have been modified.

The artifact's content integrity may remain established.

Its requirements alignment may require reassessment.

Unchanged Artifact ≠ Current Requirements Conformance.

Requirements governance remains within the Software Requirements
Standard (SRS).

AI-Generated Artifact Integrity

CRIM applies to software artifacts generated by AI systems.

Relevant integrity conditions may include:

  • Generated artifact identity
  • Relevant model or generation mechanism
  • Material input references
  • Generation context
  • Output version
  • Subsequent human or machine modifications
  • Evidence of transformation
  • Relevant uncertainty

A generated artifact shall not be treated as origin-verified merely because

an AI system claims to have produced it.

Likewise, a model-generated explanation of how code was created is not
automatically an accurate historical record.

AI-Generated Explanation ≠ Verified Creation Provenance.

Autonomous Artifact Modification

Autonomous systems may modify software artifacts without direct human
editing.

CRIM shall preserve material modification events and their resulting

artifact states.

Relevant information may include:

  • Autonomous actor reference
  • Source artifact
  • Modification objective
  • Transformation event
  • Resulting artifact
  • Relevant execution evidence
  • Applicable authority reference
  • Integrity assessment

CRIM does not independently authorize autonomous modification.

That responsibility remains within SCS and:

ASCCM — Autonomous Software Creation Control Module

Autonomous Modification Capability ≠ Modification Authority.

Multi-Agent Artifact Integrity

Software artifacts may pass through multiple agents.

For example:

Generation Agent → Refactoring Agent → Integration Agent → Review Agent

CRIM shall preserve material artifact states and transformation

relationships across these handoffs.

A later agent's successful processing of an artifact does not
establish the integrity of earlier transformations.

Each material transformation may require its own sufficient evidence.

Successful Agent Handoff ≠ Verified Artifact History.

Where evidence continuity breaks, the integrity state shall identify
the affected relationship.

Human–AI Artifact Transformation

Human developers may edit AI-generated artifacts.

AI agents may subsequently transform human-authored code.

CRIM shall preserve material source and transformation relationships

without assuming that one actor category is inherently more reliable.

The relevant question is whether artifact identity, origin,
modification, and evidence remain sufficiently supported.

Human Modification ≠ Automatic Integrity Validation.

AI Modification ≠ Automatic Integrity Failure.

Governance conclusions shall depend on the applicable evidence and

conditions.

External and Reused Artifact Integrity

Software creation may incorporate externally sourced or previously
created artifacts.

CRIM shall preserve relevant source and integrity references.

These may include:

  • Source identity
  • Artifact version
  • Content reference
  • Origin evidence
  • Relevant transformation history
  • Integrity assessment conditions

An externally sourced artifact may have strong content integrity while
its origin or permitted use remains unresolved.

Verified External Content ≠ Authorized External Reuse.

Detailed software dependency governance and applicable rights assessments

remain within their competent domains.

Generated and Intermediate Artifacts

Software creation may produce intermediate artifacts that materially
influence final software outputs.

Examples include:

  • Generated source files
  • Intermediate representations
  • Transpiled code
  • Generated interface definitions
  • Compiler-generated objects
  • Transformation outputs
  • Model-generated implementation plans used as executable inputs

CRIM shall identify intermediate artifacts where their integrity is
material to the resulting software.

Not every temporary file requires independent governance treatment.

The necessary level of integrity governance depends on materiality and

reconstructability.

Intermediate Artifact ≠ Governance-Irrelevant Artifact.

Artifact Integrity Across Build Processes

A build process may transform source artifacts into executable
outputs.

CRIM shall preserve relevant relationships between:

Source Artifact State → Build or Transformation Process → Resulting

Artifact State

Where necessary, the relationship should identify:

  • Relevant source versions
  • Build mechanism
  • Material build inputs
  • Resulting artifact identity
  • Supporting integrity evidence

CRIM does not independently establish complete build reproducibility
or software quality.

A successful build does not establish that the correct source
artifacts were used.

Build Success ≠ Build Artifact Integrity.

Reproducibility and Integrity

Reproducibility may support artifact integrity assessment.

A reproducible build can provide evidence that defined inputs and
conditions produce a corresponding output.

However, reproducibility does not independently establish:

  • Legitimate source origin
  • Creation authorization
  • Requirements correctness
  • Security
  • Software quality
  • Operational suitability

Likewise, nondeterministic generation does not automatically imply
that artifact integrity cannot be governed.

Reproducibility ≠ Complete Integrity Governance.

CRIM shall preserve the actual evidentiary contribution of reproducibility

without overstating it.

Artifact Composition Boundary

Multiple artifacts may be combined into a larger software artifact.

CRIM governs the identity and integrity of the constituent artifacts and

relevant transformation states.

The governance of the composition relationship itself belongs to:

SACM — Software Artifact Composition Module

A collection of integrity-supported components does not automatically
establish the integrity of their assembled result.

Component Integrity ≠ Composite Artifact Integrity.

CRIM supplies relevant constituent integrity states for competent

composition governance.

Artifact Integrity and Software Dependencies

Software artifacts may incorporate or reference dependencies.

CRIM shall preserve integrity-relevant references to material dependency

artifacts where they affect creation.

The Software Dependency Standard governs the broader dependency

relationships and lifecycle conditions.

A dependency may have verifiable contents while remaining unsuitable
or unauthorized for the relevant software system.

Dependency Content Integrity ≠ Dependency Governance Validity.

Artifact Integrity and Configuration

Artifact integrity may depend on the configuration context in which an
artifact is interpreted or executed.

For example, identical source code may produce different behavior
under different runtime configurations.

CRIM governs artifact identity, content, and transformation evidence.

The Software Configuration Standard governs the relevant configuration

states.

Artifact Content Integrity ≠ Configuration Integrity.

CRIM shall preserve configuration references where they are material
to artifact identity or transformation interpretation.

Artifact Integrity and Software Quality

An integrity-supported artifact may contain defects.

It may be incomplete, inefficient, unreliable, or incompatible with
its intended function.

CRIM does not independently evaluate all such product-quality
properties.

Those determinations belong to the Software Quality Standard and other

competent assessment processes.

Artifact Integrity ≠ Software Correctness.

Artifact Integrity ≠ Software Quality.

CRIM establishes what artifact exists and whether its material integrity

claims are supported.

It does not establish that the artifact is a good implementation.

Artifact Integrity and Software Security

Artifact integrity may contribute to software security governance by
identifying unauthorized or unexplained changes.

However, integrity-supported software may still contain
vulnerabilities.

A cryptographically verified artifact may faithfully preserve insecure
code.

CRIM shall not represent content integrity as proof of security.

Verified Artifact Integrity ≠ Software Security.

The Software Security Standard governs security-specific assessment

conditions.

Artifact Integrity Evidence

CRIM shall preserve evidence sufficient to support material artifact

integrity claims.

Evidence may include:

  • Artifact identifiers
  • Content references
  • Source references
  • Creation-event records
  • Transformation-event records
  • Version histories
  • Repository records
  • Hashes
  • Signatures
  • Build records
  • Generation records
  • Actor references
  • Integrity assessments
  • Exception records

Evidence requirements shall reflect the artifact's materiality and intended

governance use.

The existence of numerous records does not automatically establish
sufficient evidence.

Evidence Volume ≠ Integrity Evidence Sufficiency.

Evidence Source Competence

CRIM shall evaluate whether evidence sources are competent to support
the specific integrity claims being made.

For example:

A repository may support claims about recorded file versions.

A cryptographic hash may support claims about content correspondence.

A signing system may support claims about a particular signing event.

A build system may support claims about recorded build execution.

An AI model may provide an inferred explanation of code origin.

These sources do not establish the same facts.

Evidence Availability ≠ Evidence Competence.

CRIM shall preserve the limits of each source's evidentiary meaning.

Artifact Integrity Uncertainty

Artifact integrity may remain uncertain where:

  • Origin records are incomplete
  • Transformation history is missing
  • Actor identity is disputed
  • Content references are inconsistent
  • Generated artifacts cannot be reliably attributed
  • Build inputs are unavailable
  • Evidence sources conflict
  • Historical records have been lost
  • Automated reconstruction remains inferential

CRIM shall preserve material uncertainty rather than convert incomplete

evidence into definitive integrity claims.

Uncertain Provenance ≠ Verified Provenance.

Artifact Integrity Conflict

Conflicting integrity evidence may arise when:

  • Two records claim different origins
  • Content identifiers disagree
  • Repository history contradicts build records
  • Artifact versions are mislabeled
  • Multiple actors claim the same creation event
  • A generated artifact differs from its recorded output
  • Transformation records are incomplete or contradictory

CRIM shall identify the conflict and preserve the relevant evidence.

Where competent resolution is unavailable, the integrity state shall
remain conflicted or unresolved.

Conflicting Evidence ≠ Permission to Select the Convenient Record.

Artifact Integrity Gaps

An Artifact Integrity Gap exists where a material identity, origin,
transformation, content, or evidence relationship cannot be
sufficiently established.

Examples include:

  • An artifact with no reliable version reference
  • Generated code with unknown source inputs
  • A binary without sufficient source-to-build linkage
  • A modification with no reconstructable transformation event
  • An artifact whose claimed hash does not match its contents
  • A software component with materially disputed origin

CRIM shall identify the gap and its governance significance.

A gap may affect one integrity dimension without invalidating every
other dimension.

Integrity Gap ≠ Universal Artifact Invalidity by default.

Critical Artifact Integrity Gap

A Critical Artifact Integrity Gap exists where insufficient or
contradictory integrity evidence prevents a materially consequential
artifact state from being reliably established.

Examples may include:

- A safety-critical executable whose contents cannot be matched to the

claimed artifact version. - A financial transaction component with
unexplained code modifications. - An autonomous system artifact with
materially missing transformation history. - A deployment candidate
whose binary cannot be reliably connected to its claimed creation
output.

CRIM shall preserve the critical gap and support competent escalation.

It does not independently determine whether the software must be
deployed, suspended, rejected, or retired.

Critical Integrity Gap Identification ≠ Operational Decision
Authority.

Unauthorized or Unrecognized Transformation

CRIM shall identify material transformations that lack sufficient
recognized provenance, authority reference, or integrity evidence.

Such transformations may include:

  • Unexplained source changes
  • Unauthorized code injection
  • Unrecorded automated rewriting
  • Artifact substitution
  • Modification outside recognized creation conditions
  • Replacement of generated outputs
  • Alteration of build inputs

CRIM shall distinguish:

Unrecognized Transformation

from:

Confirmed Unauthorized Transformation

The absence of sufficient evidence does not automatically establish
malicious or unauthorized conduct.

Unexplained Modification ≠ Proven Unauthorized Modification.

Competent processes determine authorization and responsibility.

Artifact Substitution and Misidentification

Artifact substitution occurs when an artifact is presented, delivered,
or processed as though it were another artifact or artifact state.

Possible causes include:

  • Incorrect version references
  • Build output replacement
  • Repository synchronization errors
  • Deliberate content substitution
  • Misleading artifact labels
  • Incorrect deployment package association

CRIM shall preserve the distinction between artifact identity claims and

supported content identity.

Artifact Label ≠ Artifact Content Proof.

Where substitution cannot be ruled out, the relevant integrity state
shall reflect the evidentiary limitation.

Artifact Integrity Drift

Artifact Integrity Drift occurs when previously supported artifact
integrity relationships no longer adequately represent the current
artifact state.

Possible causes include:

  • Unrecorded modification
  • Tool-generated rewriting
  • Regeneration
  • Changed source inputs
  • Build process changes
  • Artifact relocation without preserved references
  • Repository history rewriting
  • Loss of provenance evidence

CRIM shall identify material drift and support reassessment.

Previously Verified Integrity ≠ Permanently Verified Integrity.

Artifact Integrity Governance States

CRIM shall support identifiable governance states for material artifact

integrity assessments.

Possible states include:

Identified: The artifact is sufficiently identifiable for assessment.

Under Assessment: Material integrity dimensions are being evaluated.

Integrity-Supported: The relevant integrity claims have sufficient

supporting evidence.

Conditionally Supported: Integrity recognition depends on explicit

conditions.

Partially Supported: Some material integrity dimensions remain

insufficiently supported.

Origin-Unresolved: The claimed origin cannot be sufficiently
established.

Transformation-Unresolved: Material transformation history remains

incomplete.

Evidence-Limited: Supporting evidence is insufficient.

Conflicted: Material evidence contradictions remain unresolved.

Integrity-Failed: A material integrity condition has been determined not

to hold.

Superseded: A later governed artifact state has replaced the previous

state.

Unresolved: Available information does not support a sufficiently
determined integrity state.

An artifact may have different states across different integrity
dimensions.

A single overall state shall not conceal material failures or unresolved

conditions.

Artifact Integrity Recognition

CRIM shall determine whether the relevant artifact integrity claims
are sufficiently supported for their intended governance use.

Recognition should consider:

  • Artifact identity
  • Content identity
  • Origin evidence
  • Transformation history
  • Version integrity
  • Provenance
  • Evidence competence
  • Material uncertainty
  • Relevant conflicts
  • Applicable continuity conditions

Recognition shall remain limited to the integrity dimensions actually

assessed.

Recognized Artifact Integrity ≠ Universal Artifact Acceptance.

Artifact Integrity Reassessment

CRIM shall support reassessment when material artifact conditions
change.

Triggers may include:

  • Artifact modification
  • Regeneration
  • New provenance evidence
  • Conflicting integrity records
  • Build changes
  • Toolchain changes
  • Actor changes
  • Discovery of unrecognized transformations
  • New content identifiers
  • Evidence-integrity concerns
  • Changes in the relevant governance context

Reassessment shall preserve previous artifact integrity states where
necessary for historical reconstruction.

Artifact Integrity Continuity and Preservation

CRIM shall preserve material integrity relationships across relevant

lifecycle transitions.

Continuity may require preservation of:

  • Artifact identifiers
  • Version references
  • Content references
  • Provenance records
  • Transformation history
  • Integrity evidence
  • Historical integrity states
  • Supersession relationships

Continuity does not require every original tool or repository to
remain operational.

It requires sufficient preserved information to reconstruct material

integrity relationships.

Repository Continuity ≠ Artifact Integrity Continuity.

Minimum Implementation Framework

A conforming implementation of CRIM must provide the following six
functional capabilities.

  • Artifact Identity and Content State Governance

Capability to identify material software artifacts, classify them,

distinguish artifact identity from content identity, and preserve
relevant version and content references.

The implementation must not rely exclusively on filenames or storage
locations as proof of artifact identity.

  • Artifact Origin, Provenance, and Transformation Governance

Capability to identify material creation events, source inputs, generation

mechanisms, transformation events, actor references, and resulting
artifact states.

The implementation must distinguish asserted provenance from
evidentially supported provenance.

  • Artifact Integrity Evidence and Recognition Governance

Capability to evaluate content integrity, origin integrity, transformation

integrity, version integrity, and supporting evidence within their
respective evidentiary boundaries.

The implementation must not infer creation legitimacy, correctness, or
security solely from cryptographic or repository evidence.

  • Artifact Integrity Gap, Conflict, and Uncertainty Governance

Capability to identify missing provenance, conflicting content references,

unexplained transformations, critical integrity gaps, and material
uncertainty.

The implementation must preserve unresolved conditions rather than
silently normalize them.

  • Artifact Integrity Change, Drift, and Continuity Governance

Capability to preserve artifact history, detect material integrity drift,

reassess changed artifacts, and maintain integrity references across
actors, repositories, tools, and software versions.

The implementation must distinguish current integrity recognition from
historical integrity states.

Canonical Closing Statement

Software artifacts are increasingly created and transformed through

An artifact may be copied, regenerated, refactored, compiled,

becomes uncertain.

A matching hash may establish content correspondence without
establishing legitimate creation.

A successful build may produce an executable artifact without proving
that the correct source inputs were used.

An AI agent may generate working code without preserving sufficient
evidence of how the artifact was formed.

And a software component may remain unchanged while its governing

Canonical Definition

The Autonomous Software Creation Control Module (ASCCM) governs the

conditions under which AI agents, autonomous development systems, and
automated software creation mechanisms may plan, initiate, execute,
modify, coordinate, and complete software creation activities within
identifiable authority, permission, execution, intervention, and
evidence boundaries.

ASCCM establishes the methodological conditions required to recognize

autonomous software creation as a controlled activity rather than an
unrestricted exercise of technical capability.

It governs the relationship between a legitimate software creation

objective, delegated execution authority, autonomous actors,
constituent actions, tool paths, material data and artifact access,
operational execution conditions, intervention capability, and
reconstructable evidence.

ASCCM distinguishes authorization of an overall software creation objective

from authorization of the individual actions used to achieve it,
technical tool availability from permitted tool use, and autonomous
task completion from evidence that execution remained within its
governing boundaries.

It applies to autonomous coding agents, AI-assisted development systems

exercising delegated execution, multi-agent development environments,
automated code generation and transformation pipelines, and hybrid
human–autonomous software creation processes.

Its principal output is:

Governed Autonomous Software Creation Control State

Its foundational distinction is:

Autonomous Software Creation Capability ≠ Autonomous Software Creation

Authority.

Operational Role

The operational role of ASCCM is:

To ensure that autonomous software creation remains bounded by
legitimate objectives, identifiable delegation, permitted constituent
actions, controlled tool and artifact access, effective intervention
conditions, and evidence sufficient to reconstruct material execution
decisions and outcomes.

ASCCM provides the creation-specific control layer for autonomous

development activity.

It governs how autonomous execution remains connected to the authority

under which it operates.

It does not assume that autonomous systems possess independent
authority merely because they can plan, reason, invoke tools, generate
code, or coordinate other agents.

It also does not require every autonomous action to receive individual
human approval.

Instead, it establishes the conditions under which actions may be
permitted within predefined authority boundaries, and when additional
authorization, intervention, or reassessment is required.

objective through a constituent action outside the permitted authority
boundary.

competent reassessment.

unauthorized data-access path.

Canonical Closing Statement

Autonomous software creation is transforming the relationship between
human intention and software execution.

An organization may define an objective while autonomous agents
determine how to achieve it.

Those agents may select tools, inspect repositories, generate code,
install dependencies, access data, execute tests, modify artifacts,
and delegate tasks to other agents.

The distance between the original instruction and the final software

artifact may therefore include many material decisions and execution
actions.

Technical capability makes this possible.

It does not establish legitimate authority for every action.

A successful autonomous system may complete its objective while
exceeding data-access boundaries.

A multi-agent development process may distribute work efficiently
while losing authority continuity.

An agent may follow a technically effective tool path that was never
authorized.

And human oversight may exist formally without providing effective
intervention capability.

Autonomous Software Creation Capability ≠ Autonomous Software Creation

Authority.

Task Authority ≠ Constituent Action Authority.

Authorized Objective ≠ Authorized Tool Path.

Agent Delegation ≠ Authority Expansion.

Human Participation ≠ Effective Human Control.

Task Completion ≠ Governed Execution Completion.

ASCCM establishes the methodological conditions under which autonomous

software creation remains bounded, observable, interruptible where
required, and reconstructable.

It does not prohibit autonomous development.

It establishes the governance requirements that allow autonomous
capability to operate without becoming autonomous authority.

ASCCM transforms autonomous software creation from delegated technical

execution into a governed creation process — ensuring that every
material action remains connected to legitimate authority, controlled
execution boundaries, effective intervention conditions, and evidence
sufficient to reconstruct how software was created.
